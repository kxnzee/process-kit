# Настройка

Вход: причина настройки, personal-only/live, выбранные процесс и подключения (если известны), полученные ответы. Возврат: personalReady, connectionsReady по запрошенным id, сохранённые пути и необходимость перезапуска.

Настройка не ищет процесс и не собирает рабочую задачу. Исходную фразу хранит помощник.
Общие правила — GIGACODE.md. Значения, уже названные человеком, не переспрашивать.
Режим personal-only подготавливает
личную копию для записи процессов/пожеланий, без вымышленных подключений. Live проверяет
только переданные process и подключения. Неизвестные зависимости будущего процесса
не повод настраивать все системы заранее.

Перед изменением подключений прочитай config/team/README.md.

## 1. План до вопросов

Покажи дословно (систему замени, если нужна не Jira):

> Сначала настрою Process Kit. Что сделаю:
> 1) узнаю вашу команду;
> 2) сделаю вам личную копию для ваших процессов в этой папке;
> 3) спрошу, где хранить ваши процессы: только на этом компьютере или ещё в вашем
>    репозитории;
> 4) спрошу проект в Jira, если команда его ещё не указала;
> 5) проверю доступ к Jira.
> Что изменится на компьютере: в этой папке появится ваша личная копия и сохранятся
> настройки команды. В Jira и других системах ничего не изменю.
> Начинаю настройку?

До «да» не меняй файлы и настройки, не задавай вопросы рабочей задачи.
Повторная уже готовая установка не требует этого плана.
Для personal-only покажи короткий соответствующий план: команда, личная копия,
способ хранения и защита отправки; явно скажи, что доступы к системам не проверяются.
Не обещай проверку Jira в режиме, в котором её не будет.

## 2. Проверить копию

Корень — из GIGACODE.md. Прочитай git status --porcelain=v1, текущую ветку и
настройки командного/личного слоя. Несохранённые общие/командные изменения — остановка с объяснением;
не stash, не reset. Личные незавершённые изменения не включай в настройку.
Если my уже существует, не создавай её заново и не перезаписывай config.
Зафиксируй исходную ветку/HEAD и список staged/unstaged до записи. Существующие
изменения человека не присваивай настройке. Изменённый config не является автоматическим
поводом всё заблокировать: отдельно покажи diff и выясни, можно ли продолжить его настройку.
Не включай этот diff в коммит молча и не обходи общие несохранённые изменения.
Коммиту нужны имя и email: используй существующие; иначе спроси и задай --local.
До первого коммита (включая создание команды) установи node tools/kit.js hooks-install.
Ошибка установки блокирует коммит; прежние hooks не затирать, тесты не запускать.

Если уже открыта my и подтверждены команда/хранение, пропусти выбор команды,
создание веток и вопрос хранения. Проверь локальную защиту и только недостающие
поля/доступы. Не возвращайся на origin/master и не меняй основание существующей my.
Нет сети — настройку подтверждённой личной копии можно продолжить локально; нужный
непроверенный доступ вернёт blocked, а не «готово». Неизвестное спрашивай один раз.

## 3. Команда

Скачай сведения: git fetch origin --tags. Нет сети — не заявляй актуальность команд;
существующую my можно использовать, новую установку с неизвестным основанием останови.
Список команд — origin/team-*, идентификаторы и названия из config/team/config.json этих веток.
Спроси один раз: «В какой команде вы работаете?» Варианты: названия / «Моей команды
нет — создать» / «Без команды». Существующий подтверждённый выбор не переспрашивать.

Создание: «Как называется команда и кто её владельцы?». Код — [a-z0-9]+, без дефиса.
Если команда уже есть, используй её, не перезаписывай.
До создания и отправки: «Сейчас создам команду <название> в общем репозитории, чтобы ею
могли пользоваться коллеги. Создать?» Отказ — без изменений.
После «да»: git switch -c team-<код> --no-track origin/master; создай config/team/config.json из config/team/EXAMPLE.json, заполни team.id/name/owners и только командные подключения; коммит только командного конфига; git push -u origin team-<код>.
Проверь удалённую ветку и привязку. Успех: «Команда создана. Попросите администратора
добавить владельцев команды проверяющими.»
Подтверждённый отказ в правах: сохрани заявку в новой outputs-папке, вернись на
зафиксированную исходную ветку/HEAD. Удалять можно только созданную этим вызовом
локальную team-ветку с ровно ожидаемым коммитом, если её содержимое сохранено в заявке
и человек согласовал продолжение без команды. Иначе оставь её и объясни причину.
«Прав на создание команды нет. Заявка: <полный путь>. Пока настрою без команды.»
Сбой сети после push: сначала проверь, появилась ли ветка; неопределённый результат
не повторять и не удалять вслепую.

## Поля личного конфига

EXAMPLE.json в config/my показывает все возможные заполняемые поля и содержит TODO.
Не сохраняй его как готовый config.json без материализации:

- profile.name/email — подтверждённая локальная Git-идентичность; существующую сверить,
  отсутствующее спросить один раз и записать только --local.
- teamId — выбранный код либо null без команды; имя/владельцы команды находятся в team.
- storage.mode — local или repository; storage.repositoryUrl только для repository,
  это подтверждённый адрес mine, отличный от origin. Для local поле удалить.
- taskStores/codeStores — только нужные собственные подключения; учебные записи удалить.
- defaults — только подтверждённые выбранные id/ресурсы; неиспользуемые TODO-ключи удалить.
- preferences — только отдельно согласованные пожелания; {} допустим, не опрашивать без задачи.

Составь полный личный конфиг из подтверждённых ответов, а не подставляй весь шаблон.
Personal-only сохраняет profile/teamId/storage, оставляя подключения=[] и defaults={}.
С командными подключениями также не нужны копии записей: достаточно выбранных id.
Проверь совпадение profile с локальной Git-идентичностью и storage с branch.my.pushRemote/
remote mine. При расхождении не перенастраивай молча — уточни конкретный выбор.

## 4. Личная копия и защита

Основание — origin/team-<код>; без команды — последний стабильный vX.Y.Z, достижимый
из origin/master. Тег выбирать по версии, не по алфавиту и не среди чужих веток.
Нет стабильного тега — остановка настройки и сообщение владельцу поставки.
Создай git switch -c my --no-track <основание>, либо используй существующую my.
Существующую команду my не меняй переключением на другую основу без отдельной миграции.
Создай config/my/config.json из config/my/EXAMPLE.json: teamId=<код> либо null без команды. Существующий файл не перезаписывай; противоречие с выбранной командой — остановка. Источник выбора — my.teamId и team.id.
«Ваши процессы хранить только на этом компьютере или ещё в вашем репозитории?
Если не уверены — только на этом компьютере.»
Локально: убрать upstream my, git config --local branch.my.pushRemote no_push.
Свой репозиторий: mine с подтверждённым адресом, отличным от origin;
существующий mine не менять без согласия; git config --local branch.my.pushRemote mine.
Установи node tools/kit.js hooks-install: защита индекса перед коммитом и защита отправки.
При ошибке не считать защиту установленной. Тесты эта защита не запускает.
Скрипт идемпотентен, сохраняет существующий hook; не редактируй .git/hooks вручную.
После шага: «Готово: личная копия создана, она хранится только на этом компьютере.»
Для mine замени окончание на «в вашем репозитории».

## 5. Настройки и доступ

Personal-only: выбранная команда уже сохранена в config/my/config.json.
Не запрашивай подключения и секреты будущей задачи; верни personalReady отдельно.

Прочитай настройки: node tools/kit.js config --json. В my не изменяй унаследованный team-конфиг.
Заполняй только собственные записи my и личные defaults. Недостающие общие сведения
команды требуют отдельной правки владельцем в team-ветке; не создавай личную запись
с тем же id, чтобы скрыть незаполненное командное подключение. Если человек выбирает
собственный ресурс, создай новый уникальный id. Не запрашивай неиспользуемые системы.
Секреты человек вводит в GigaCode, не в чат и не в файл. Не трогай ~/.gigacode/ и
глобальные настройки Git. В проектных settings только ссылки $secret:.
Проверь нужный MCP безопасным чтением. Есть объявление без ответа — доступ не проверен.
Нет секрета / 401,403 / сбой сети — разные сообщения, см. помощник.
Пока нужного доступа нет, живую задачу не запускать. Перед ожиданием перезапуска
сохрани согласованные настройки по разделу 6 и отчёт с незавершённым доступом;
верни blocked. После добавления секрета нужен перезапуск клиента. Повторный вызов
проверяет доступ и продолжает, не пересоздаёт личную копию и не теряет ответы.

## 6. Проверка, сохранение и возврат

node tools/kit.js check, затем --process <имя> только для выбранного live-процесса.
Personal-only не должен блокироваться сетевыми зависимостями будущей задачи.
Не запускай интеграционные самотесты в рабочей папке как доказательство доступа.
Коммит личной настройки — только config/my/config.json и явно согласованные my-*; командный конфиг в него не включается;
никогда git add . / -A. Перед коммитом проверь чужое staged: используй коммит только
своих точных путей (`git commit --only -- <пути>`) после проверки полного diff.
Нет изменений — нет коммита. Новый процесс сюда не входит.
Создай outputs/<дата>_настройка/что-сделано.md без .run/. Старую папку не перезаписывай.
Отчёт в чат до 8 строк: команда, хранение, доступы, незаполненное и
«Отчёт о настройке: <полный путь>». После каждого шага короткая строка «Готово: …».
Верни помощнику статус готовности и исходную задачу; её выполнение — отдельная операция.
Если config сохранён, но доступ ещё отсутствует, status=blocked, personalReady=true;
никакой успешной проверки доступа не записывай. Новый отчёт не затирает предыдущий.

## Форма заявки

Если по описанному сценарию нужна заявка, создай outputs/<дата>_заявка-<что>/заявка.md
без .run/. Заполни только подтверждённые сведения:

```markdown
# Заявка на <команду или подключение системы>
Назначение: <для какого процесса и какие операции нужны>
Данные: <название, код и владельцы команды либо название системы>
Что нужно: <конкретное действие получателя>
От кого: <подтверждённое имя пользователя>
```

Не оставляй заполнители, не включай секреты и не отправляй заявку автоматически.

## Форма отчёта настройки

В что-сделано.md сохрани фактический результат, включая незавершённые шаги:

```markdown
# Настройка Process Kit, <дата>
1. Команда: <название или без команды>.
2. Хранение личной копии: <локально или подтверждённый репозиторий>.
3. Настройки: <что заполнено и что осталось>.
4. Доступ: <что реально проверено, чего не хватает>.
5. Проверка процессов: <какая проверка выполнена и результат>.
Что изменено на компьютере: <фактические изменения>.
Внешние изменения: <фактические изменения либо ничего не менялось>.
```
