# Конструктор

Вход/возврат — `docs/reference/skill-handoffs.md`. До записи убедись, что открыта
готовая my. Если нет — верни blocked с причиной personalReady, не переключай ветку
и не проводи настройку сам. Согласие на сборку, переданное помощником, уже действительно.

1. Начинай только после согласия на «Собрать его?». Уточни результат, входы, критерии
   и внешние изменения. Не больше трёх вопросов за раз; готовые ответы не повторяй.
2. Перескажи шаги простыми словами. Найди подходящие действия по их контрактам, прежде
   чем создавать новые. Наличие имени в каталоге не доказывает пригодность контракта.
3. Новое в личной копии — my-*. Командную копию в my не создавай: проверка уровня
   отвергнет новый team-<код>-файл. Подготовка командной/общей версии — отдельная
   задача владельца в соответствующей рабочей ветке с согласованными именами и ссылками;
   это не скрытый режим обычной сборки. Исходные my-* сохраняются.
4. Используй docs/templates/process.md и action/ACTION.md. Экшен — одна операция
   с фиксированными входами и одним именованным результатом. Чтение, сопоставление/расчёт
   и оформление — разные шаги. Не прячь процесс внутри query и не добавляй режим,
   меняющий контракт; пагинация и батчи остаются внутри чтения. Один маршрут, явные имена
   действий и выбранных данных; не копируй рецепт действия в процесс. Одни query/template
   можно переиспользовать, если подходят смысл и контракт. Не создавай новые скиллы.
5. Заполни name/version/area/status/description/examples/entry/params/requires.
   requires.actions — прямые действия; context — нужные файлы; taskFields/codeFields —
   только используемые поля выбранных подключений. Для transform сетевых полей нет.
   Эффективный класс действия source/transform/act заполни сам по операции; человеку
   не задавай вопрос о классе. У черновика без адаптера kind=transform;
   act без подключения недопустим.
6. Адреса и секреты не помещай в процесс. Настройки берутся по id taskStore/codeStore;
   критерии отбора — query/rules, форма результата — template, факты — context.
   Нужной системы нет: инструкция подключения существующего MCP либо заявка разработчику
   в отдельной папке outputs; не изобретай инструменты и не создавай подключение по догадке.
7. Контракты consumes/produces должны сходиться, вход от человека задаётся text/input,
   а не вымышленным «артефактом предыдущего шага». Обязательное отсутствует — спроси.
8. Выполни node tools/validate.js. Исправь только созданное тобой; не переписывай чужое
   ради зелёной проверки. Для нового процесса подготовь вымышленный набор, если это
   разумно; пробный прогон без сети и без отправки. Семантику эталона подтвердит владелец.
9. Покажи результат и границы проверки. До записи зафиксируй существующие изменения
   и индекс: чужое staged не должно попасть в коммит. Коммить только свои точные пути;
   уже изменённый человеком файл не включай без согласования его полного diff.
   Нельзя отделить свои правки — blocked, не stash и не reset.
   Коммит — только точные новые/изменённые пути,
   отдельный от настройки. Нет согласованной авторской идентичности Git — не выдумывать.
10. Верни помощнику имя процесса и параметры для отдельного запуска. Не сообщай о живом
    результате, если выполнено лишь создание файлов или демо.
