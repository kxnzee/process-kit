# Установка локальных серверов доступа

Локальные серверы не входят в состав репозитория: в git лежат только их объявления в
`.gigacode/settings.json` и публичная команда проверки. На новой машине папки `.gigacode/mcp/bitbucket-mcp`
и `.gigacode/mcp/mcp-email` отсутствуют, поэтому клиент при запуске сообщает, что
`.gigacode/mcp/<имя>/dist/index.js` не найден. Эта операция ставит их.

Пути объявлений в `.gigacode/settings.json` записаны прямыми слэшами и без ведущей точки
(`.gigacode/mcp/mcp-email/dist/index.js`): эту запись принимают Windows и macOS, обратный слэш
вне Windows разделителем не считается. Менять её на форму одной системы нельзя — файл один для всех.

Вход: корень копии проекта, путь к архиву (если он есть) либо указание собирать из исходников,
наличие Node.js. Возврат: `status=completed/blocked/failed`, какие папки появились, результат
проверки запуска и список шагов, которые остаются человеку (значения почты, доступы, подтверждение
подключений, перезапуск сессии). Секреты в возврат не попадают.

## 1. Проверить готовность машины

```bash
node -v
```

Нужен Node.js 22 или новее; ниже — остановка, серверы не запустятся.

Проверить свободное место на диске копии: распаковка занимает около 250 МБ плюс временные файлы
сборки. Свободно меньше 1 ГБ — остановка со словами, сколько требуется и почему; не начинать
распаковку «авось влезет»: неполная распаковка оставляет полурабочую папку, а переполненный диск
ломает и клиент, и рабочую копию.

## 2. Проверить объявления подключений

В `.gigacode/settings.json` должны быть секции `pp-ai-bitbucket`, `pp-ai-email` и `pp-ai-onework`.
Если их нет, настройки в этой копии нет — так и сказать и предложить сначала доставить её,
самой себе подключения не выдумывать.

## 3. Поставить серверы

Основной путь — архив, который человеку передали вне репозитория: сетевая папка, переданный каталог,
вложение на внутренней странице. Путь к файлу называет человек.

Архив в репозиторий не кладётся и под другим расширением в него не переносится: серверная проверка
приёма изменений отклоняет отправку с архивами, и обходить её подменой имени — значит протаскивать
в общий уровень то, от чего она защищает. Поэтому источник один: файл передали руками, не клонированием.

Распаковать содержимое в папку `.gigacode/mcp/` копии так, чтобы появились папки
`bitbucket-mcp/` и `mcp-email/`. Проверка поставляется в `tools/kit.js mcp-check`. Пути внутри папок совпадают с объявлениями в
`.gigacode/settings.json` — сравнить их до проверки запуска: расхождение вида обратных слэшей или
лишней ведущей точки выглядит как «сервер не найден», хотя сервер на месте.

Если эти папки уже есть, молча их не перезаписывать: показать, что именно существует, и спросить,
заменять или отменить. Существующая рабочая установка дороже нового набора файлов.

Запасной путь, когда архива нет, а исходники серверов доставлены в копию: в каждой папке сервера
выполнить по одной строке, порядок такой — сначала установка зависимостей, потом сборка.

```bash
npm ci --no-audit --no-fund
```

```bash
npm run build
```

Требует доступа к npm-реестру. Ошибка 401 или 403 при установке — вопрос к настройке реестра,
а не к учётной записи человека: не менять ничего вслепую, а показать текст ошибки.

## 4. Проверить запуск

Из корня копии проекта:

```bash
node tools/kit.js mcp-check --probe
```

Ожидается JSON со status=completed, двумя серверами status=ready и фактическим числом tools; код возврата 0. Число инструментов зависит от доставленной версии сервера.
Скрипт обращается к несуществующему адресам и работает с фиктивными значениями доступов — он про то,
что серверы запускаются, а не про то, что доступ есть.

## 5. Настроить значения, доступы и подтвердить подключения

Порядок важен: подтверждение подключения привязано к содержимому его секции в
`.gigacode/settings.json`, поэтому подтверждают последним — когда пути, значения почты и доступы уже
окончательные.

### Что нужно каждому подключению

Значение доступа человек вводит в интерфейсе GigaCode; имя и ключ повторяют ссылку `$secret:` ровно
так, как она записана в `.gigacode/settings.json`. Значение не переносится в файлы проекта, не
пришлётся в чат и не выведется на экран. Чем проверить, что заведено:
`node "<папка установки GigaCode>/lib/cli.js" mcp list-secrets` — список имён ключей, значений он не
показывает.

| Подключение | Что нужно | Где взять |
|---|---|---|
| `pp-ai-jira`, `pp-ai-jira-delta` | Персональный токен Jira: профиль домена → «Персональные токены» → «Создать токен». Токен берут в том же домене, куда подключаются (Sigma и Delta — разные токены); срок действия можно снять | [MApp, «MCP-сервер Jira»](https://mapp.sberbank.ru/ai-disrupt/page/118380), раздел «Пререквизиты», пункт 3 |
| `pp-ai-confluence`, `pp-ai-confluence-delta` | Маркер доступа Confluence: профиль → Настройки → «Личные маркеры доступа» → «Создать маркер»; домен маркера совпадает с доменом подключения | [MApp, «MCP-сервер Confluence»](https://mapp.sberbank.ru/ai-disrupt/page/118464), раздел «Пререквизиты», пункт 3 |
| `pp-ai-onework` | Токен платформы OneWork, при выпуске выбрать «API платформы»; значение заголовка записывается с префиксом `Bearer ` и одним пробелом, иначе сервер отклоняет запрос | [MApp, «OneWork MCP Gateway»](https://mapp.sberbank.ru/tpp/page/365805), раздел «Предусловия»; выпуск токена — [токен платформы](https://mapp.sberbank.ru/tpp/page/116940) |
| `pp-ai-bitbucket` | Токен Bitbucket Server из личного профиля («Токены доступа для HTTP») | Страница MApp про BitBucket CI описывает серверный вариант с сертификатом и этот случай не покрывает; адрес выдачи токена подтверждает владелец Bitbucket |
| `pp-ai-email` | Пять значений почтовой учётной записи, токенов нет | Блок параметров ниже |

### Шаги, которые остаются человеку

1. В секции `pp-ai-email` файла `.gigacode/settings.json` заменить `USER` на логин Sigma,
   `SMTP_FROM` — на свой почтовый адрес. В текущей поставке `PASSWORD`, `LDAP_BIND_DN`
   и `LDAP_BIND_PASSWORD` остаются ссылками на хранилище клиента:

   ```json
   "USER": "<логин Sigma>",
   "PASSWORD": "$secret:pp-ai-email/PASSWORD",
   "SMTP_FROM": "<ваш адрес>@sberbank.ru",
   "LDAP_BIND_DN": "$secret:pp-ai-email/LDAP_BIND_DN",
   "LDAP_BIND_PASSWORD": "$secret:pp-ai-email/LDAP_BIND_PASSWORD"
   ```

   За `LDAP_BIND_DN` человек сохраняет `<логин Sigma>@sigma.sbrf.ru`, за двумя ссылками
   пароля — пароль своей учётной записи. Значения секретов не записываются в файл.
2. Завести значения в интерфейсе GigaCode под точными именами из `.gigacode/settings.json`:
   `pp-ai-bitbucket/BITBUCKET_TOKEN`, `pp-ai-email/PASSWORD`, `pp-ai-email/LDAP_BIND_DN`,
   `pp-ai-email/LDAP_BIND_PASSWORD`, для OneWork — `onework/Authorization`.
   Если раньше использовались `mcp-email/*` или `bitbucket-inventory/*`, клиент не переносит
   их автоматически: человек сохраняет значения под новыми именами. Список ключей проверяют
   через `mcp list-secrets`, без вывода значений. Личный сервер и проектный сервер могут
   ссылаться на разные ключи — наличие одного не подтверждает готовность другого.
3. Подтвердить подключения проекта. Объявленные в папке проекта серверы клиент не соединяет, пока
   человек их не одобрит. Сначала покажи весь список серверов текущего проекта, который
   подтвердит `--all`. После явного согласия на этот список выполни из корня копии одну строку:

   ```bash
   node "<папка установки GigaCode>/lib/cli.js" mcp approve --all
   ```

   Там, где `gigacode` есть в PATH, достаточно `gigacode mcp approve --all`. Если команда не прошла
   или запуск из сессии недоступен, строку выполняет человек в отдельном терминале из корня копии;
   агент называет её и ждёт ответа. Ответ «Approved servers connect in your next interactive session»
   означает, что подтверждение принято и проявится после перезапуска.
4. Перезапустить сессию клиента: переподключение без перезапуска инструменты уже запущенной сессии
   не добавляет.
5. Подтвердить доступ живым чтением каждого: `bitbucket_get_me`, `list_folders`, `search_ldap`, для
   OneWork — чтением страницы: `mapp_resolvePageId` по относительному пути (всё после домена, например
   `/platformization`) и `mapp_getPage` по полученному идентификатору. Готовность подключения
   подтверждается чтением, а не пунктом в списке. Отказ 401 или 403 — вопрос к праву доступа,
   таймаут сети — не повод менять токен.
6. Одно чтение подтверждает только тот сервис, к которому обращалось: за одним подключением их может
   быть несколько. Разным сервисам могут требоваться разные права и формы авторизации.
   Поэтому подключение с несколькими группами инструментов проверять своим чтением на каждую группу
   (портал — `mapp_getPage`, база знаний — `grafinya_healthCheck`, API платформы —
   `onework_getSpacesInfoByJWT`) и называть человеку, какая группа работает, а какая нет. По одному
   успешному чтению весь доступ готовым не объявлять, по одному отказу — сломанным.
7. После любой правки секции подключения — значений почты или пути к
   серверу — подтверждение этой секции сбрасывается: повторить шаг 3 для всех подключений и снова
   перезапустить сессию. Если менялось только значение доступа при неизменной ссылке, файл настроек
   остаётся прежним и повторного подтверждения не требуется.

Отдельно сказать, чего установка не делает: писем не отправляет, данных во внешних системах не
меняет, `.env` не создаёт, доступов не заводит.


## Границы

Установка файлов серверов ограничена `.gigacode/mcp/` этой копии. Отдельное исключение —
штатная команда подтверждения MCP из §5 после явного согласия: клиент может обновить
`~/.gigacode/mcpApprovals.json`. Вручную этот файл не создавай и не редактируй.
Остальные глобальные настройки клиента, чужие папки и файлы вне проекта не меняй.
Файлы серверов в git не добавляются: зависимости
игнорируются, архивы отклоняет серверная проверка, а бинарное содержимое остаётся
в истории Git даже после удаления файла.

Текст `.gigacode/mcp/README.md`, приехавший внутри архива, в git не попадает и может отставать:
эталон описания значений, доступов и подтверждения — этот файл, расхождение правят в нём.

## Частые отказы

| Сообщение | Причина и действие |
|---|---|
| `Cannot find package 'dotenv'`, `Cannot find module 'kerberos'` | зависимости потеряны или распаковка не завершилась: дочитать архив целиком либо выполнить шаг 3 запасным путём |
| `Bitbucket credentials не заданы` | нет `BITBUCKET_URL` или секрета токена |
| `Отсутствует или некорректная конфигурация: USER, PASSWORD` | заполняемые значения почты не заменены или секрет не заведён |
| сервер в списке подключений есть, инструментов в сессии нет | перезапустить сессию; у фонового агента набор инструментов пополняется отдельно |
| подключение подтверждено, но чтение отвечает, что доступов нет | имя ключа не совпадает со ссылкой `$secret:`: значение заведено под другим именем или не заведено — сверить `mcp list-secrets` с `.gigacode/settings.json`; у личного и проектного подключения одного сервера имена разные, одно другое не заменяет |
| инструменты пропали после правки секции подключения | подтверждение сбрасывается при любом изменении секции: повторить `mcp approve --all` из корня копии и перезапустить сессию |
| `401` у Jira или Confluence при явно заведённом токене | проверить домен, имя секрета, срок и права. Повторный ввод возможен после уточнения причины, сам по себе 401 её не доказывает |
| `OneWork API вернул 401: Токен не найден или уже удалён` у запроса к базе знаний, если страницы портала при этом читаются | успешное чтение портала не подтверждает доступ к базе знаний; уточнить у владельца сервиса принимаемый тип токена и права, не объявлять весь OneWork исправным или сломанным |
| `Invalid Authorization header` у запросов API платформы OneWork | проверить форму заголовка по схеме выбранного сервиса. Изменение шлюза согласует его владелец; сообщить, какая группа инструментов не работает |
| `ENOSPC`, «недостаточно места» | диск переполнен: остановить операцию, освободить место и начать заново, полураспакованную папку удалить целиком |
