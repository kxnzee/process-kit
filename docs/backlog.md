# Process Kit — итоговый backlog развития

**Дата согласования:** 15 ноября 2026 года.

**База проверки:** `master`, коммит `d704126c`.

**Назначение:** согласованный объём развития Process Kit и задания для последующей реализации инженером или AI-агентом.

Документ объединяет PK-01–PK-11 с учётом проверки текущей реализации и последующих уточнений. Он описывает будущие изменения и не объявляет их реализованными. Перед началом каждой задачи исполнитель повторно проверяет состояние кода: база и состав возможностей могут измениться.

**Объём ближайшего стабильного выпуска:** все 11 задач. Приоритеты P1–P3 задают порядок работ, а не исключают задачи из выпуска. Первые действия — реальные проверки GigaCode по PK-06 и предварительная проверка двух команд по PK-11. Выпуск по-прежнему требует отдельного поручения.

## 1. Общие принципы

- Сначала изучить существующую реализацию, затем определить минимальный объём изменений.
- Переиспользовать действующие Skills, References, публичный CLI, Controller, Config, Catalog и Run Journal. Не создавать параллельные механизмы с тем же назначением.
- Сохранять уровни `master / team-<код> / my`, владельцев определений, структуру сущностей и принципы исполнения. PK-11 расширяет подключение командных рабочих копий, сохраняя проверки внутри каждой из них.
- Не возвращать обязательный Mentor/Dispatcher, отдельный Agent Runtime или новый агентный цикл.
- Простые операции не должны требовать создания Process или дополнительных обязательных процедур. Формализованное выполнение Process проходит через существующий Controller.
- Пользователь задаёт цель обычным языком. Технические команды и выбор Skills остаются работой агента. Уже полученные ответы и согласия не спрашиваются повторно.
- Подключённая команда или запись Config не доказывает доступ к системе и не предоставляет права менять чужие определения.
- Поддерживать универсальный обмен между `my`, командами и `master`. Доступность источника для чтения и полномочия на изменение назначения проверять раздельно средствами Bitbucket и по правилам файла CODEOWNERS конкретной ветки. Для Move проверять также полномочия на удаление источника. Если пользователь уполномочен работать в нескольких командах, обмен между ними допустим.
- Не вводить прямые зависимости между определениями разных команд. Перенос и адаптация в свою область рассматриваются отдельно от использования исходного определения в его командной копии.
- История, метрики, список подключённых команд и пути рабочих копий хранятся локально у пользователя. Централизованный сбор, автоматическая отправка и глобальное хранилище статистики в этот backlog не входят.
- Пользовательские результаты отделены от служебных материалов Run. Очистка служебных файлов не удаляет результаты, краткую историю и накопленные локальные метрики.
- Для изменений поведения выполнять необходимые проверки и обновлять связанную документацию. Не писать тесты, которые лишь повторяют текст инструкций вместо проверки существенного поведения.
- Сохранять совместимость Windows и Linux и действующей CI-матрицы Node.js 22/24. Для изменений путей, Git worktree, блокировок и очистки отдельно проверять существенное поведение на соответствующих платформах; локальный результат не объявлять свидетельством прохождения CI.
- Локальные тесты, демонстрационные прогоны и реальная приёмка GigaCode — разные виды свидетельств. Успех одного не заменяет другой.
- Реализация задачи не разрешает автоматически коммит, push, merge, выпуск тега или внешние изменения. Выполнять их в пределах отдельного поручения; merge без отдельного поручения не делать.

Пилот по SHA начинается до завершения всего backlog.

## PK-01. Единый Skill обмена изменениями и процессами

**Приоритет:** P1.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** частичная основа есть; универсальный Share и новые операции не реализованы.

**Связи:** каталог PK-03 помогает выбирать Process; PK-11 переиспользует Share для обновления подключённых копий.

### Цель

Дать пользователю одну способность обмена изменениями: передать выбранные материалы, получить обновления, сравнить версии и перенести отдельный Process с необходимыми зависимостями.

### Что уже есть

- Skills `pp-ai-promote-changes-team` и `pp-ai-promote-changes-master`.
- Общая процедура `.gigacode/references/promotion.md`.
- Read-only операция `promote-plan`: общий предок, снимки файлов, кандидаты, конфликты и исключения.
- Подготовка изменений в отдельном Git worktree, проверка назначения, владения и зависимостей.

### Что реализовать

Создать универсальный `pp-ai-share`, переиспользующий существующую процедуру и библиотеки. Заменить два Promotion Skills после переноса их правил и обновления ссылок на них. Не оставлять конкурирующие инструкции одного назначения.

| Операция | Ожидаемое поведение |
|---|---|
| Push All | Подготовить передачу всех выбранных допустимых изменений в разрешённое назначение |
| Push Process | Подготовить передачу выбранного Process с необходимыми зависимостями |
| Pull All | Получить согласованный набор обновлений из доступного источника в разрешённое назначение |
| Pull Process | Получить либо обновить отдельный Process с зависимостями в разрешённом назначении |
| Status | Показать источник, назначение, локальные изменения, доступные обновления и препятствия |
| Diff | Показать конкретные различия выбранных материалов до применения или отправки |

Для первой версии выборочный обмен поддерживает Process целиком: связанные Actions, Adapters, ресурсы, требуемый Context и безопасную часть Config. Универсальный выбор произвольного поднабора отдельных сущностей не является обязательным.

Источник и назначение определяются отдельно. Поддерживать любые разрешённые сочетания `my`, `team-<код>` и `master`, включая прямой обмен команд без промежуточного `master`. Права репозитория и ограничения ветки проверять средствами Bitbucket; владельцев файлов и требования согласования определять по CODEOWNERS именно затрагиваемой ветки. CODEOWNERS не заменяет права Bitbucket. Для разных веток правила могут различаться; не переносить правила из одной ветки в другую по предположению. Переиспользовать существующие подключения и проверки, не создавать собственную систему управления доступом. Если необходимые факты недоступны, сообщить конкретное препятствие и не объявлять изменение разрешённым.

Copy, Move и Reuse включить в первую реализацию как варианты основных операций, без отдельных Skills:

| Вариант | Семантика |
|---|---|
| Copy | Создать самостоятельную копию в разрешённом назначении с корректными именами, владельцем, ссылками и допуском; источник сохраняется |
| Move | Перенести выбранное с удалением источника; проверить полномочия на обе стороны, обратные зависимости и подтверждённую сохранность результата в назначении до удаления |
| Reuse | Использовать существующее определение без дублирования в допустимой области; между командами использовать выполнение в исходном контексте через PK-11, без прямой запрещённой ссылки |

Для Move неполная передача, непринятый необходимый результат или препятствие удалению оставляют операцию незавершённой с явным статусом. Подготовка PR не означает, что перенос принят. Не выполнять merge автоматически. Межкомандный Reuse проверяется совместно с PK-11; до его готовности не создавать альтернативную маршрутизацию.

При переносе определения между владельцами проверить имена, все ссылки и зависимости. Подготовить версию для принимающей области, если исходные командные имена там недопустимы. Затрагиваемые переименования и изменения смысла показать до применения. Простое копирование чужих префиксов не считается корректным импортом.

Состав зависимостей получать существующими средствами. Сохранить действующие исключения секретов, личных настроек, `outputs/`, `.history/` и остальных служебных материалов. Для Config переносить только допустимые определения и безопасные настройки; недостающие значения обозначать как требующие настройки. Новый универсальный сканер содержимого и гарантия отсутствия чувствительных данных в произвольных файлах в эту задачу не входят.

Сохранять трёхстороннее сравнение и защиту более новых файлов назначения. При конфликте объяснить его и предложить решение; не перезаписывать файл молча. Подготовка изменений, локальная публикация определения, Git-коммит, push и merge остаются разными операциями.

Подробные процедуры вынести в условно загружаемые References, например `references/git.md` и `references/processes.md`. Предпочитать штатные Git merge/diff/worktree и существующий `promote-plan`.

### Ограничения

- Не создавать движок синхронизации, отдельный реестр версий или Skill для каждого направления.
- Не менять исходную рабочую копию и чужой индекс ради подготовки передачи. Удаление источника при явно выбранном Move допускается только на согласованном этапе переноса после необходимых проверок.
- «All» означает весь выбранный допустимый набор, а не обход фильтров владения и исключений.
- Полученный или изменённый Process проверяется и допускается существующим lifecycle; перенос `publication.json` сам по себе не доказывает готовность новой версии.
- Получение обновлений не повторяет внешние операции и не изменяет сохранённые Run.

### Приёмка

- Все шесть операций работают через один Skill; направление и область изменения понятны пользователю.
- Copy, Move и Reuse работают как варианты основных операций; тесты различают сохранение источника, разрешённое удаление и использование без копирования.
- Проверки используют права Bitbucket и правила CODEOWNERS соответствующих веток; разрешение в одной ветке не считается разрешением в другой.
- Process переносится с полным допустимым набором зависимостей либо операция явно сообщает недостающее.
- Прямой обмен команд не оставляет запрещённых межкомандных ссылок. Copy и Push/Pull без Move сохраняют источник; Move удаляет только разрешённый источник после проверки результата и зависимостей.
- Конфликты, удаления, устаревший план и изменение назначения обнаруживаются до перезаписи или отправки.
- Личные настройки, результаты, история и секреты не попадают в обмен.
- Существующие проверки назначения, владения и целостности сохраняются; поведение проверено на временных Git-репозиториях.

## PK-02. Локальная история, диагностика и метрики

**Приоритет:** P1.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** частично реализовано.

**Связи:** состав сохраняемых кратких данных согласовать с PK-05; PK-11 может расширить локальный просмотр на подключённые копии.

### Цель

Позволить агенту объяснять сохранённое выполнение, показывать последние запуски, сравнивать два запуска и получать основные метрики. Все данные и вычисления остаются локальными у пользователя.

### Что уже есть

- `.run/trace.jsonl` — события выполнения.
- `.run/state.json` — состояние, эффективные параметры, идентичность, попытки и артефакты.
- `.history/runs.jsonl` — одна актуальная краткая запись на завершённый или зафиксированный как failed запуск.
- `итог.md` и файлы результата для пользователя.
- `pp-ai-diagnose`, `run diagnose`, проверка доступа и безопасный диагностический экспорт.
- Recovery и контроль целостности Run.

Краткая история уже содержит имя Process, время завершения, режим, исход, папку результата и краткий итог. Длительность и категория ошибки отдельными полями не сохраняются; признак проверочного запуска сейчас обозначается текстом в итоге.

### Что реализовать

**Просмотр истории.** Добавить минимальные операции просмотра и фильтрации в существующий публичный интерфейс: последние запуски, выбранный Process, период и исход. Полноту результата обозначать явно. При показе текущих незавершённых запусков использовать их состояние, поскольку краткий журнал завершений их не содержит.

**Последовательность выполнения.** По выбранному Run показывать подтверждённые события, шаг остановки, попытки, завершение и доступный результат. Сначала проверить достаточность существующих state/trace; добавлять только события, действительно отсутствующие для нужного объяснения. Не пытаться восстановить несохранённую переписку или причины по догадке.

**Сравнение.** Для двух явно определённых запусков сравнивать Process, режим, исход, длительность, пройденные шаги и результаты в пределах доступных данных и прав. Учитывать разные определения и условия запуска. После очистки подробностей показывать ограниченное сравнение по краткой истории и сохранённым пользовательским результатам.

**Естественные запросы.** Агент должен понимать «покажи последние запуски», «почему процесс не выполнился», «что происходило перед ошибкой», «сравни два запуска» и «подготовь диагностику для разработчика». Использовать существующий Diagnose и не требовать от человека CLI-команд или ручного сбора журналов.

Разбор завершается конкретным следующим шагом: настройка подключения, допустимое Recovery либо отдельная задача исправления. Предложение исправить или повторить не разрешает само изменение и не отменяет проверки внешнего исхода.

**Основные метрики.** По локальной истории предоставлять:

- число завершённых и зафиксированных как failed запусков за период;
- число и долю success, failed и draft с понятным объяснением этих исходов;
- частоту использования отдельных Processes и время последнего завершения;
- статистику отдельно для local, live, demo и проверочных запусков;
- длительность отдельных запусков и агрегаты по сопоставимым запускам;
- распределение неуспешных запусков по безопасным категориям ошибок.

Для сохранения этих метрик после очистки `.run/` дополнить существующую краткую локальную историю: длительность, отдельный признак проверочного запуска и безопасная категория ошибки. Не создавать второй журнал. Выбрать минимальное расширение схемы и сохранить чтение старых записей; отсутствующие данные считать неизвестными.

Длительность — календарное время от старта до завершения Run, включая ожидание ответов пользователя и перерывы. Отдельный учёт активного времени в первую реализацию не входит. Расчёт опирается на сохранённые временные отметки, а не на оценку модели; для старых запусков без необходимых сведений длительность неизвестна.

Не смешивать демонстрационные и проверочные прогоны с рабочими результатами. Не интерпретировать отсутствие записи как успешное выполнение или отсутствие запусков вообще. При неполных данных показывать период, охват и ограничения подсчёта.

### Хранение и границы диагностики

Вся статистика хранится и вычисляется локально. После PK-11 допускается локальная сводка по доступным подключённым копиям с указанием команды и происхождения Run; это не командная статистика всех пользователей.

Локальная история, локальный разбор и экспортный файл диагностики имеют разные назначения. Расширение истории не расширяет диагностический экспорт. В экспорт по-прежнему попадают только разрешённые безопасные факты и события: без URL, параметров, входов, содержимого артефактов, переписки, технических запросов и сырых ошибок.

Сохранить действующее поведение экспорта. Не добавлять универсальную фильтрацию всех локальных записей или требование гарантировать отсутствие секретов и персональных данных во всей истории.

Количество уточнений, оценка полезности, число созданных/опубликованных процессов и глобальная командная аналитика не входят в обязательный объём. Для них сейчас нет достаточного источника данных; дополнительный сбор заранее не вводить.

### Приёмка

- История доступна агенту через существующую публичную точку входа с проверкой области доступа.
- По сохранённому Run можно объяснить последовательность и остановку, отделив факты от предположений.
- Два запуска сравниваются без повторного выполнения.
- Основные метрики вычисляются локально и различают рабочие, демонстрационные и проверочные запуски.
- Длительность включает ожидание и перерывы; активное время не подменяет календарное. Дополнительные метрики создания/публикации, уточнений и полезности отложены.
- После очистки подробностей сохраняется статистика по краткой истории; недоступные детали обозначаются явно.
- Старые записи читаются без выдуманного заполнения новых полей; повторный finish/recover не увеличивает счётчики одного Run.
- Диагностический экспорт, Controller и Recovery сохраняют действующие ограничения.

## PK-03. Каталог Process и Action

**Приоритет:** P1.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** каталог Process реализован; требуются адресные дополнения и discovery Actions.

**Связи:** PK-01 использует каталог для выбора материалов; PK-11 агрегирует каталоги рабочих копий.

### Цель

Дать агенту возможность находить доступные Processes и переиспользуемые Actions по метаданным, не читая все определения и не загружая их исполняемый код.

### Что уже есть

`node tools/kit.js processes` и `tools/lib/entities/process-catalog.js` возвращают имя, путь, заголовок, описание, примеры запросов, уровень, команду, учебный признак, статус и состояние публикации. Повреждённая видимая запись не скрывает корректные: каталог обозначает неполноту и issues.

Версия самого ответа каталога уже есть. Она отличается от версии Process, которую требуется добавить в запись определения.

### Что реализовать

Дополнить существующий каталог Process полями `area` и версии определения. Сохранить уже реализованные поля, семантику публикации, область видимости и признаки неполноты.

Добавить discovery Actions со следующими метаданными:

- имя, путь и описание;
- класс `source / transform / act`;
- объявленные входы, выходы и контракты;
- объявленные зависимости и адаптер;
- уровень владения и команду, когда применимо.

Каталог строить непосредственно из определений. Метаданные зависимостей означают объявленные связи, а не обещание полного анализа произвольного JS. Не выполнять runtime, branchRule или сетевые проверки ради перечисления.

Встроить использование каталога Actions в Create Process: сначала искать подходящий существующий компонент, затем читать полное определение выбранных кандидатов. Неполный поиск не считать доказательством отсутствия Action и основанием для дубликата.

Выбрать минимальную публичную форму каталога в рамках `tools/kit.js`. Не перегружать существующую операцию исполнения `action` неявным поведением и не создавать ручной реестр сущностей.

Для будущего PK-11 предусмотреть сохранение происхождения записи: конкретный каталог должен однозначно относиться к своей рабочей копии. Межкомандную агрегацию в PK-03 реализовывать не требуется.

### Приёмка

- Агент находит Process и Action по метаданным и затем читает только выбранные определения.
- Версия определения и версия схемы ответа различаются явно.
- Каталог не запускает код определений и не обращается к внешним системам.
- Чужие записи фильтруются в соответствии с действующими проверками каждой копии.
- Повреждённые записи дают понятный признак неполноты, не скрывая корректные.
- Create Process переиспользует подходящий Action; каталог не подменяет проверки запуска и публикации.

## PK-04. Подготовка стабильных релизов и устаревание

**Приоритет:** P1 перед стабильным выпуском; не блокирует пилот по согласованному SHA.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** базовые инструкции есть; подготовка стабильного выпуска требует дополнения.

### Цель

Сделать стабильный выпуск воспроизводимым и понятным: какая версия поставляется, что изменилось, какие изменения несовместимы и как пользователю перейти на новую версию.

### Что уже есть

- Инструкции обновления и создания Git-тега `vX.Y.Z` в README.
- Версии отдельных Processes.
- Статусы `действует / устарел` и предупреждение валидатора для устаревшего Process без `replaced_by`.
- Отдельная процедура пилотной установки по согласованному SHA.

На проверенной базе в локальной копии стабильных тегов нет. Это наблюдение по текущей копии, а не подтверждение состояния всех удалённых хранилищ.

### Что реализовать

Подготовить короткий порядок выпуска: выбор неизменяемой базы, необходимые проверки, описание изменений, известные ограничения, совместимость и отдельное решение о реальном выпуске тега.

Определить правила использования версий платформы и отдельных Processes. Для несовместимого изменения объяснять, что затрагивается: определения, Config, подключения, публикация, сохранённые Run или пользовательские инструкции. Описывать необходимое действие пользователя и возможность возврата к прежней установке.

Сравнивать состав двух версий штатными Git diff/log и существующими метаданными. Подготавливать краткие release notes. Отдельный сервис сравнения релизов не требуется.

Уточнить политику устаревания: когда выставляется статус, как указывается замена, как проверяются потребители и когда допустимо удаление. Переиспользовать `replaced_by`, не вводить параллельное поле той же семантики. Сохранять пользовательскую историю и результаты при удалении определения.

### Ограничения

- Git Push/Pull, конфликтующие обновления и обмен файлами относятся к PK-01.
- Не создавать отдельный Skill релизов, если достаточно существующих инструкций и Git.
- Подготовка релиза не означает автоматического создания или отправки тега.
- Не объявлять живую интеграцию проверенной по локальной публикации Process.

### Приёмка

- По инструкции можно подготовить конкретный релиз с перечнем изменений и свидетельствами проверок.
- Несовместимые изменения и действия пользователя указаны явно.
- Для устаревшего определения понятны замена, ограничения и условия удаления.
- Можно сравнить два релиза без ручного восстановления их состава.
- Пилот по SHA и стабильный релиз остаются разными процедурами; реальный выпуск выполняется отдельно.

## PK-05. Хранение и ручная очистка служебных материалов

**Приоритет:** P2.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** операция обслуживания не реализована.

**Зависит от:** согласованного в PK-02 состава краткой истории, сохраняемого после очистки.

### Цель

Дать пользователю ручное управление удалением подробных служебных материалов без потери результатов, краткой локальной истории и основных метрик. Срок хранения по умолчанию не устанавливается.

### Что уже есть

Run хранит подробности в `outputs/<запуск>/.run/`, пользовательские результаты — рядом с `.run/`, краткую историю — в `.history/runs.jsonl`. Эти данные исключены из Git. Документация уже отделяет очистку `.run/` от удаления результатов и краткой истории.

### Что реализовать

- Показывать объём служебных материалов и отдельно объём сохраняемых результатов.
- Выполнять очистку только по явному запросу пользователя. Не задавать срок хранения по умолчанию и не включать автоматическое удаление. Пользователь может выбрать конкретные завершённые Run или критерий отбора для данной операции.
- Давать предварительный просмотр точных папок/файлов, причин включения и ожидаемого освобождения места.
- Очищать только однозначно распознанные служебные материалы завершённых Run в выбранном пользователем наборе.
- Перед удалением сохранять необходимые краткие данные PK-02 существующим механизмом истории.
- Исключать активные и незавершённые Run, неизвестные внешние исходы, незавершённые транзакции и материалы, безопасность удаления которых не доказана.
- Непосредственно перед очисткой повторно проверять состояние и использовать существующие механизмы согласованного доступа, чтобы запуск не изменился после предварительного просмотра.

Очистка выполняется отдельной ручной операцией обслуживания с предварительным просмотром и в пределах явного поручения. Не добавлять скрытую очистку в обычный запуск, расписание удаления или фоновый сборщик. Незнакомые старые папки, повреждённые данные и ссылки пропускать с объяснением, а не удалять по одному возрасту или названию.

После очистки пользователь должен понимать: итог и основные локальные метрики сохранены, но подробная диагностика, восстановление по удалённым данным и сравнение шагов больше недоступны. История не должна ссылаться на подробности как на существующие.

### Что сохраняется

- `итог.md`, пользовательские файлы и другие результаты вне явно выбранной служебной области.
- `.history/runs.jsonl` и накопленные краткие метрики.
- Все материалы активных, незавершённых и неоднозначных Run.
- Подготовленные пользовательские диагностические файлы вне `.run/`.

### Приёмка

- Предварительный просмотр ничего не удаляет и соответствует правилам реальной очистки.
- Очистка начинается только по запросу и не использует срок хранения по умолчанию; удаляется только выбранный допустимый набор. Активный или изменившийся Run пропускается.
- Результаты и краткая история сохраняются; метрики не теряются и не удваиваются.
- Повторная очистка не повреждает оставшиеся данные.
- Ограничения последующей диагностики явно показаны, а частичная ошибка очистки не выдаётся за полный успех.

## PK-06. Первый запуск и пользовательская приёмка GigaCode

**Приоритет:** P1; начать первой практической проверкой.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** инструкции, локальные проверки и сценарии ручной приёмки есть; требуется фактическая проверка клиента.

### Цель

Подтвердить, что новый пользователь выполняет полезную задачу в GigaCode обычным языком, без знания Skills и CLI, и получает понятный результат либо конкретное объяснение препятствия.

### Что уже есть

- `pp-ai-init`, `setup-status`, настройка личной ветки и работа без команды.
- Правила маршрутизации, продолжения, изменения и отмены поручения.
- Условно загружаемые References и возврат из вспомогательной настройки к исходной задаче.

### Что выполнить

Выбрать один полезный доступный сценарий и провести его в настоящем GigaCode. Можно начать с локального сценария без внешних систем; затем проверить чтение через нужное подключение совместно с PK-07. Не ждать завершения всего backlog.

Основная последовательность: пользователь описывает цель → агент выбирает способность/Process → при необходимости выполняет только нужную настройку → сохраняет ответы → возвращается к цели → выполняет доступный сценарий → показывает результат и ограничения.

Проверить отдельно:

- новую личную копию, существующую настройку и работу без команды;
- повторное поручение без повторной анкеты;
- короткий ответ на ожидаемый вопрос, побочный вопрос и возврат к задаче;
- изменение и отмену поручения без самовольного возобновления отменённой операции;
- создание, проверочный прогон и локальную публикацию Process;
- штатное выполнение и восстановление после прерывания;
- ошибку подключения, неполные данные и неверный результат после completed;
- понятные объяснения существенных действий и предложение безопасной диагностики;
- ожидаемую блокировку защищённых переходов при отсутствии доверенного канала.

Для каждого сценария зафиксировать версию GigaCode, модель, Node.js, SHA, локальные изменения, наблюдаемые действия, результат и доступные свидетельства. Сведения приёмки хранить локально; не расширять ради этого диагностический экспорт.

Найденные проблемы разделять по фактам: инструкция, программная проверка, подключение, поведение модели или ограничение клиента. Исправлять минимально в существующем компоненте. Не добавлять обязательный Mentor и не ослаблять допуск ради прохождения сценария.

### Приёмка

- Доступный сквозной сценарий пройден в реальном GigaCode; путь результата и версия среды известны.
- Пользователь не обязан вручную выбирать Skill, создавать JSON-spec или собирать журнал.
- Настройка не теряет исходную цель и не повторяет уже полученные ответы.
- Изменение, отмена и восстановление проверены по наблюдаемым действиям.
- Обнаруженные дефекты исправлены и перепроверены либо конкретно перечислены как ограничения.
- Локальные тесты и реальное поведение клиента отчётливо разделены; непроверенные возможности не объявлены работающими.

## PK-07. Подключения и доверенные внешние операции

**Приоритет:** P2 в целом; P1 для чтения и защищённых переходов, необходимых выбранному пилоту.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** настройка, описания адаптеров и контракты есть; рабочей доверенной интеграции нет.

**Связи:** приёмка чтения выполняется вместе с PK-06; PK-11 сохраняет отдельный контекст подключений каждой команды.

### Цель

Обеспечить практическую работу через существующие подключения и доказуемое подтверждение защищённых операций без нового механизма исполнения.

### Что уже есть

- Init для настройки существующего подключения и возврата к задаче.
- Create Adapter для описания реальных инструментов, ответов, пагинации и ограничений.
- Adapters Jira, Bitbucket и чтения страниц; Config с выбранными подключениями.
- Actions классов `source / transform / act`.
- Контракты `verifyApproval` и `verifyEffect`, привязка свидетельств к запросу и Run.
- Блокировка повторного выполнения внешней операции с неизвестным исходом.

Текущий `gigacode-run` не предоставляет рабочие `verifyApproval`/`verifyEffect`. Ограничение касается как `act`, так и защищённых пользовательских продолжений. Тестовый trusted-host не является рабочей интеграцией.

Согласованный ближайший объём: сначала реальные подключения и чтение. Рабочую доверенную интеграцию реализовывать по потребности выбранного пилота. Само включение PK-07 в стабильный выпуск не отменяет этого условия и не разрешает объявить заблокированные операции поддержанными.

### Что выполнить: подключения и чтение

Проверить существующий путь: найти подходящее MCP/Adapter → определить нужную запись Config → проверить доступ безопасным чтением → помочь настроить недостающее → продолжить исходную задачу.

Новый адрес или проект не требует нового Adapter, если технический тип системы тот же. Если отсутствует реальный коннектор, оформить конкретную потребность в его разработке. ADAPTER.md не заменяет MCP-сервер и не доказывает наличие инструмента.

На нужных пилоту источниках подтвердить обычный ответ, пустой полный ответ, пагинацию, лимит выборки, частичные данные, отказ доступа и недоступность. Не выдавать неполную выборку за полную и не угадывать подключение по первому серверу в settings.

### Что реализовать: доверенные операции

Сначала определить доступный доверенный компонент среды GigaCode и способ подключения к существующей интеграционной границе. Если необходимых возможностей нет, зафиксировать препятствие; не заменять их заявлениями модели.

Реальный компонент должен:

- подтверждать человека и точную область согласия для текущего запроса;
- проверять привязку approval к Run, ревизии, действию или переходу, параметрам и входам;
- подтверждать исход конкретной внешней попытки по системе или подлинному свидетельству;
- различать `applied / not-applied / unknown`;
- разрешать сохранение результата при подтверждённом applied и новую попытку при подтверждённом not-applied;
- сохранять блокировку при unknown; отсутствие записи в неполном ответе не считать доказательством not-applied;
- отвергать поддельные, устаревшие и повторно использованные свидетельства.

Проверяющий компонент и необходимые ему ключи/полномочия должны находиться вне управления модели, если заявляется технически обязательное подтверждение. Текст «да», `confirmed=true` или доступная самой модели команда подтверждения этим требованиям не соответствуют.

### Ограничения и приёмка

- Controller и существующая граница trust остаются единственным механизмом управляемого исполнения; второй Runtime не создаётся.
- Чтение проходит реальную интеграционную проверку на выбранном источнике с корректной отметкой полноты.
- Для выбранного пилота явно определено, нужна ли доверенная интеграция. Если нужна, соответствующая часть обязательна для его положительной приёмки. Если не нужна, отсутствие интеграции и блокировка защищённых операций отражены в составе возможностей стабильного выпуска.
- Защищённый пользовательский переход и внешняя запись считаются готовыми только после положительных интеграционных сценариев и существенных негативных проверок.
- Неизвестный исход не приводит к слепому повтору; после разрешённого retry нужен новый approval.
- Тестовый хост не подключается как доказательство настоящего согласия, а отсутствие рабочей интеграции не обходится изменением kind/decision.
- Секреты вводятся средствами клиента; не сохраняются в чате, параметрах, истории или диагностическом экспорте.

## PK-08. Предположения и рекомендации по локальной истории

**Приоритет:** P3.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** не реализовано; входит в ближайший стабильный выпуск после накопления достаточной локальной истории.

**Зависит от:** PK-02 и достаточной истории реальных запусков.

### Цель

Уменьшать повторные вопросы и предлагать полезные улучшения по наблюдаемым повторениям, не создавая заранее сложную систему догадок или супервизора.

### Что уже есть

Init позволяет сохранять явно согласованные предпочтения в личном Config или Context. Этот механизм требуется переиспользовать, а не заменять автоматически выведенным профилем пользователя.

### Что исследовать и затем реализовать

Сначала определить по реальным локальным запускам, какие повторения полезны и какие данные для них действительно есть. Начать с одного-двух воспроизводимых случаев, а не универсального движка.

Нужную для приёмки историю накопить в ходе ранних пилотов этого выпуска. Недостаток данных означает незавершённую приёмку PK-08, а не автоматическое исключение задачи из выпуска. Достаточность подтвердить воспроизводимыми примерами выбранных рекомендаций.

Возможные функции:

- предложение параметра по сопоставимым предыдущим запускам;
- учёт явно исправленного пользователем значения;
- объяснение, откуда взялось предположение;
- обнаружение повторяющегося ручного действия;
- предложение улучшить существующий Process/Action или вынести согласованное правило в Context;
- предложение автоматизации повторяющейся задачи, если в клиенте есть подходящая возможность.

Предположение не заменяет явный параметр текущего запроса и не является согласием на внешний эффект. Данные разных команд не смешиваются в общие предпочтения без учёта области применимости. После очистки подробностей рекомендация должна опираться только на реально сохранившиеся сведения.

Расписание и фоновое исполнение не создавать в Process Kit только ради рекомендации. Их реализация требует отдельной подтверждённой потребности и возможностей среды.

### Приёмка

- Для выбранных случаев рекомендация воспроизводится по доступной локальной истории.
- Агент объясняет источник, область применимости и неопределённость предположения.
- Исправление пользователя учитывается; текущий явный ввод имеет приоритет.
- Предложения не применяются автоматически там, где требуется решение или подтверждение пользователя.
- Глобальный сбор, отдельный супервизор и новый runtime не появляются.

## PK-09. Поставка отдельного Process как расширения

**Приоритет:** P3; обязательная задача ближайшего стабильного выпуска с исследовательским этапом.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** не начата; поддержка формата и реальная потребность не подтверждены.

### Цель

Проверить, требуется ли и возможно ли поставлять отдельный Process с зависимостями как самостоятельное расширение GigaCode без полного Process Kit.

### Что исследовать

- Конкретный пользовательский сценарий отдельной поставки и его отличие от Pull Process из PK-01.
- Поддерживаемый GigaCode формат, условия установки и обновления.
- Какие части существующего Controller/CLI обязательны для исполнения.
- Состав Process, Actions, Adapters, ресурсов и контрактов.
- Как задаются требования к Config, Context, подключениям и доверенной интеграции без переноса секретов.
- Как проверяются зависимости, совместимость и действительность допуска после установки.

Сначала подготовить короткий вывод о реализуемости и необходимости. Если формат не поддерживается или задача решается существующим обменом, зафиксировать результат исследования и не создавать упаковщик.

### Условная реализация и приёмка

При подтверждённой потребности и поддержке реализовать минимальную упаковку на основе существующих зависимостей и механизмов исполнения в рамках ближайшего стабильного выпуска. Самостоятельное расширение не должно получать отдельный Runtime или ослабленные проверки.

Исследование завершено, когда есть проверяемый ответ о формате, составе, ограничениях и целесообразности. Если подтверждено отсутствие поддержки или необходимости, PK-09 завершается обоснованным исследовательским результатом без упаковщика; вывод включается в материалы выпуска. Неизвестная поддержка без достаточной проверки не считается доказанным отрицательным результатом. При положительном выводе для завершения PK-09 нужны реализация, установка и запуск переносимого пакета в чистой подходящей среде с явно указанными зависимостями.

## PK-10. Краткое руководство по расширению платформы

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** архитектура описана; нужны компактная навигация по решениям и сквозные примеры.

### Цель

Помочь инженеру или AI-агенту определить, куда добавить новую возможность, и расширить существующий компонент без дублирующей архитектуры.

### Что уже есть

`docs/architecture.md`, `docs/structure.md`, `docs/ownership.md`, `GIGACODE.md`, разделы README для разработчиков, Skills и примеры сущностей. В архитектуре уже есть правило добавления публичной команды и размещения реализации, ресурсов и тестов.

### Что подготовить

Создать `docs/extending.md` или эквивалентный короткий раздел с преимущественно ссылками на существующие нормативные документы.

Включить карту ответственности:

| Компонент | Когда его менять |

## PK-11. Мультикомандная работа пользователя

**Приоритет:** P1.

**Статус требований:** согласованы с уточнениями этого документа.

**Реализация:** не начата; предварительная проверка GigaCode в рамках этой работы не выполнена.

**Основа основной реализации:** PK-01 и PK-03. Предварительная проверка двух команд начинается раньше вместе с PK-06.

**Главное ограничение:** минимальные изменения существующей архитектуры Process Kit.

### Цель

Пользователь открывает одну личную рабочую область Process Kit, подключает несколько доступных ему команд, находит их Processes и Actions и запускает нужные возможности без ручного переключения веток.

Целевой приёмочный сценарий — 10 подключённых команд. Это проверочный масштаб, а не требование ввести жёсткий предел количества команд.

### Что сохраняем

- Уровни `master / team-<код> / my`, владельцев и структуру определений.
- Существующие Controller, Run Journal, Config и публичные операции исполнения.
- Отдельный командный контекст каждой рабочей копии.
- Одну личную область и одну личную ветку `my`, без отдельных личных веток под каждую команду.
- Запрет прямых зависимостей между командными определениями.
- Обычную работу без команды или с одной командой.

Действующая модель предполагает одну выбранную команду на личную копию. В PK-11 нужно адресно расширить способ подключения и выбора рабочих копий. Это не означает, что один Config-resolver должен одновременно объединять настройки всех команд.

### Что изучить до реализации

Init и восстановление личной копии; схемы и разрешение Config; Catalog и область видимости; Ownership и публичный допуск; определение корня рабочей копии; Controller, Recovery, диагностику и хранение истории; Share и Git worktree.

По результатам выбрать минимальное расширение существующих компонентов. Перед изменением схем определить совместимость с текущими личными настройками. Не начинать с нового оркестратора или общего многокомандного Runtime.

### Обязательная предварительная проверка: две команды

До основной реализации маршрутизации проверить в реальном GigaCode один открытый пользовательский проект и две командные рабочие копии с разными подключениями. Git worktree решает размещение файлов, но сам по себе не подтверждает обнаружение MCP-инструментов и Skills клиентом.

Проверка должна подтвердить обнаружение инструментов обеих команд, использование правильного подключения, выполнение через существующий Controller и возврат к незавершённому Run с Recovery в его исходной копии. Использовать действующие средства и минимальный проверяемый способ доступа; не строить полноценный новый механизм до подтверждения возможностей клиента.

Зафиксировать версии среды, SHA копий и наблюдаемый результат. Если нужный доступ из одного проекта не поддерживается, описать конкретное ограничение и остановить зависимую реализацию до выбора минимального работоспособного решения. Успех команд CLI в разных папках не заменяет положительную проверку GigaCode. После успешной проверки двух команд масштабировать тот же подход до десяти.

### Что реализовать

**Подключение команд.** Пользователь указывает доступные команды. Init настраивает или повторно использует подходящие Git worktrees. Командные ветки не сливаются в одну. Список команд, пути копий и необходимые личные сведения хранятся локально, отдельно от публикуемых командных материалов.

Каждой копии соответствует подтверждённая команда и её Config. Если нужная ветка уже открыта в worktree, учитывать существующую копию, а не пытаться занять ту же ветку повторно. Подключение не должно стирать незавершённую работу или менять исходную личную ветку.

Сохранить единый личный профиль и область предпочтений; не требовать десяти независимых личных настроек. При исследовании определить минимальный способ применения личных настроек и подключений в командных контекстах без смешивания командных defaults и без записи локальных путей в публикуемый Config.

**Единый каталог.** Включить общие инструменты, личные инструменты основной области `my` и доступные Processes/Actions всех подключённых команд. Агрегировать метаданные PK-03 из соответствующих копий. Запись сохраняет команду, происхождение и точную рабочую копию. Одинаковые имена общих сущностей и разные версии не должны приводить к молчаливому выбору произвольной копии. Общие записи можно объединять для показа только при сохранении однозначного маршрута исполнения.

Ошибка одной копии даёт явное ограничение каталога, а не скрывает корректные записи остальных. Наличие записи в списке подключений не подменяет существующие проверки области доступа и готовности.

Проверить работу с разными ревизиями копий и схемами ответов CLI. Несовместимая копия даёт понятное препятствие и не подменяется другой версией без решения пользователя. Этот признак учитывается до исполнения выбранной задачи.

**Исполнение.** Добавить минимальную маршрутизацию к нужной рабочей копии. Запуск, следующие шаги, сохранение, диагностика и восстановление одного Run обращаются к той же копии и существующему Controller. Используются её определения, выбранные подключения, Context и правила допуска. Конфиги разных команд не объединяются в один общий набор.

Команду определять по явно выбранному инструменту, текущей задаче и подтверждённому контексту. Если подходящих команд несколько и выбор не определён, уточнить его у пользователя; не угадывать по первой записи каталога и не повторять уже полученный выбор.

Указанные пользователем команды и доступ к источникам не разрешают изменение чужих определений. Рабочий запуск и его локальные результаты отделены от права редактировать или отправлять командные материалы. Подтверждения внешних эффектов остаются обязательными в своём контексте.

**Межкомандные задачи.** Агент может последовательно выполнить самостоятельные Processes разных команд и объединить доступные результаты в личной области. Каждый управляемый запуск проходит через Controller своей копии и имеет отдельный Run. Использование Action допускается в пределах уже существующей семантики Run Action; произвольные цепочки Actions вместо Controller не вводятся.

При недоступности любой команды, необходимой текущей межкомандной задаче, остановить всю текущую задачу, включая оставшиеся независимые части. Сохранить полученные результаты и связи с отдельными Run, явно показать выполненное и препятствие. Уже завершённые Run не переводить задним числом в failed и не откатывать их результаты автоматически. Это правило не скрывает каталог остальных команд и не блокирует другие отдельные поручения. Возобновление идёт после устранения препятствия в пределах действующего поручения и проверок исходного Run, без слепого повтора внешних операций.

Не создавать межкомандный Process с запрещёнными ссылками и не передавать результат в другую систему только по факту его локальной доступности. Для передачи данных должны соблюдаться применимые ограничения и область поручения. Если одному общему формализованному маршруту нужны прямые межкомандные зависимости, это отдельное развитие за пределами PK-11.

**Обновления.** Использовать PK-01 для получения изменений выбранных копий. Обновление одной команды не обновляет молча остальные и не подменяет зависимости активного Run. До изменения показывать конфликты и препятствия.

**История.** Сохранять локальное происхождение каждого Run: команда и рабочая копия. Можно агрегировать локальную статистику PK-02 для этого пользователя без отправки в глобальное хранилище. Не дублировать события запуска в новом центральном журнале; подробности остаются у существующего Run.

**Отключение команды.** Убрать команду из общего каталога и выбора новых инструментов, сохранив worktree, локальные изменения, историю, результаты и привязку существующих Run к исходной копии. Удаление рабочей копии — отдельная явная операция с проверками сохранности данных. Отключение само по себе не разрешает удаление и не подменяет проверку прав при последующем просмотре или восстановлении.

### Что не создавать

- Новый Runtime, Controller, диспетчер задач или отдельный цикл исполнения агента.
- Дополнительные уровни владения и общий набор определений поверх всех команд.
- Новую систему управления доступом или самостоятельную установку Process Kit для каждой команды; worktrees используют существующий репозиторий и механизмы исполнения.
- Слияние всех командных веток в одну личную ветку.
- Прямые зависимости между Processes/Actions разных команд.
- Сложную синхронизацию, фоновое обновление всех копий или глобальное хранилище истории.

### Приёмка

- Пользователь подключает 10 команд, открывает одну личную область и находит доступные инструменты всех исправно подключённых копий.
- До основной реализации пройдена проверка двух команд с разными подключениями в одном GigaCode; затем тот же подход проверен на десяти командах.
- Каталог включает общие, личные и командные инструменты; при неоднозначности команды агент уточняет выбор.
- Выбор и запуск нужного Process не требуют ручного переключения веток или ввода команд пользователем.
- Run исполняется и восстанавливается в исходной командной копии с её Config и существующим Controller.
- Проверено отсутствие смешивания подключений, Context, артефактов и свидетельств подтверждения между командами.
- Недоступность нужной команды останавливает всю текущую межкомандную задачу: оставшиеся части не выполняются, полученные результаты сохраняются. Каталог остальных команд остаётся доступным для других отдельных поручений.
- Совпадающие имена и разные версии имеют понятное происхождение; агент не запускает случайную копию.
- Последовательная задача использует результаты отдельных командных Run и сохраняет общий личный результат без запрещённых зависимостей.
- Подключение и обновление не изменяют чужие определения и не теряют локальные правки.
- Данные и статистика остаются локальными; текущая работа без команды и с одной командой сохраняется.
- Отключение команды сохраняет её копию и данные. Разные ревизии копий и несовместимость интерфейсов обозначаются явно; личные настройки не превращаются в десять независимых профилей.
- Маршрутизация, изоляция и восстановление проверены локально; удобство одной открытой области подтверждено отдельно в реальном GigaCode.

## 3. Порядок выполнения и границы ближайшего стабильного выпуска

### Этап 1. Подтвердить полезный рабочий сценарий

Начать с реальных проверок GigaCode: PK-06, необходимые подключения и чтение PK-07, предварительная проверка PK-11 на двух командах с разными подключениями. Не ждать Share, полного каталога и реализации маршрутизации. Выбрать доступный сценарий, подтвердить возможности клиента и устранить реальные препятствия. Краткое руководство PK-10 готовить по ходу, не превращая его в условие старта пилота.

Если выбранный сценарий требует защищённого пользовательского продолжения или записи, соответствующая доверенная интеграция PK-07 становится P1. При её отсутствии проверяется корректная блокировка; положительная приёмка этой части остаётся незавершённой.

### Этап 2. Подготовить обмен, discovery и мультикомандную работу

После предварительных проверок выполнить PK-01 и PK-03, затем основную реализацию PK-11 с проверкой десяти команд и межкомандного Reuse. Эти задачи делать отдельными логическими изменениями. Последующие задачи выпуска не блокируют данный этап, но остаются в обязательном составе стабильной версии.

### Этап 3. Закрепить локальную наблюдаемость и ручное обслуживание

Выполнить согласованный основной набор PK-02, затем ручную очистку PK-05 без срока по умолчанию. PK-02 можно начать раньше независимо от PK-11: локальная история одной копии полезна сама по себе. Расширенные метрики создания/публикации процессов, уточнений и полезности остаются за пределами согласованного объёма PK-02.

### Этап 4. Завершить оставшиеся задачи выпуска

Завершить PK-07 в согласованном объёме: чтение обязательно, доверенная интеграция — по потребности выбранного пилота с честной фиксацией поддержанных и заблокированных операций. Завершить короткое руководство PK-10, реализовать и проверить PK-08 на накопленной истории, выполнить исследование PK-09 и упаковку при подтверждённых поддержке и потребности. PK-08 и PK-09 не исключаются из ближайшего выпуска по одному признаку P3.

### Этап 5. Подготовить и принять стабильный выпуск

Выполнить PK-04 и итоговую проверку всех PK-01–PK-11. Для каждого пункта зафиксировать результат, свидетельства приёмки и ограничения. PK-08 требует достаточной реальной истории; PK-09 допускает обоснованный отрицательный исследовательский результат, но не непроверенную догадку. Условность PK-07 не позволяет обещать защищённые операции без рабочей интеграции.

Стабильный выпуск готов к отдельному решению о публикации, когда все 11 задач завершены по своим согласованным критериям, существенные проверки Windows/Linux выполнены, реальная приёмка GigaCode подтверждена и состав поддержанных возможностей явно описан. Отсутствие необходимых свидетельств означает незавершённую подготовку выпуска. Пилот по согласованному SHA допускается раньше; выпуск тега и его отправка выполняются только по отдельному поручению.

## 4. Порядок работы исполнителя

Для каждой задачи:

1. Проверить текущую ветку, SHA, локальные изменения и применимые инструкции. Не терять чужую незавершённую работу.
2. Изучить существующие компоненты и отметить, какие требования уже выполнены. В индексированном CodeGraph репозитории использовать его по правилам проекта; самостоятельно индекс не создавать.
3. Определить минимальное изменение и существенные ограничения реализации. Конкретное внешнее препятствие не обходить фиктивной готовностью.
4. Реализовать только порученную задачу с переиспользованием существующих интерфейсов и проверок.
5. Проверить существенное поведение и регрессии затронутых контрактов; общие изменения проверять шире, чем локальные предметные правки.
6. Обновить документы и инструкции у владельцев соответствующих сущностей; не создавать дублирующие нормативные правила.
7. Подготовить отчёт: что изменено, какие критерии выполнены, чем подтверждены, что не проверено и какие действия остались.

Работать отдельными логическими изменениями. Не смешивать несвязанные задачи в один PR. Статус backlog обновлять по фактическому результату: наличие файлов, успешный selftest и описание будущего сценария сами по себе не означают выполненную интеграционную приёмку.
