# Мои правила: техническая или содержательная задача

Данные действия `classify-issuance`. Файл личного уровня: свои формулировки записываю
здесь, рецепт шага не правлю. Рецепт — в `ACTION.md` этой папки, пожелание владельца о
понимании задач — в `POLICY.md`; при расхождении решает рецепт.

**Что здесь главное.** Признаки ниже — **сверка**, а не решение. Решение принимается по
смыслу задачи, с цитатой как основанием. Совпадение слова без смысла задачу не
отбрасывает; смысл без совпадения — не повод молчать (такая задача идёт с пометкой
`reasoned`, а формулировка попадает в список «что дописать в правила»).

## Классы

| Класс | Что означает | Что делает отчёт |
|---|---|---|
| `contained` | для читателя что-то меняется: данные, методы, источники, проверки, ответы системы | печатается как инфо-повод |
| `technical` | только внутреннее устройство: сборка, поставка, журналы, инфраструктура, уязвимости библиотек | отбрасывается, причина — в разделе «Отброшено» |
| `unknown` | по материалу смысл не установлен | печатается с пометкой и вопросом человеку |

## Как решать по смыслу

1. **Что изменится у читателя?** Задаю себе один вопрос: если это изменение доедет до
   внедрения, что он увидит нового или другого — данные, поля, методы, справочники,
   правила проверки, состав источников. Есть ответ — задача содержательная.
2. **Внутреннее устройство** — сборка, библиотеки, уязвимости, журналы, инфраструктура,
   настройки, которые не меняют поведение. Такое читателю не объявляют.
3. **Основание обязательно.** Цитата из заголовка, описания, комментария или связанной
   задачи. Заголовок — полноценное основание: если из него видно, что изменится у
   читателя, класс ставится по нему, и повтор заголовка в описании вопроса не вызывает.
   Если описание пустое — смотрим связанные задачи и комментарии; не помогло — `unknown`
   с вопросом, а не догадка.
4. **Смешанная задача.** «Изменение состава данных реестра + настройка загрузчиков» —
   содержательная: содержательная часть главнее технического обрамления. Техническая часть
   перечисляется внутри строки отчёта, а не отменяет повод. Техническое обрамление само по
   себе поводом не становится: профиль или правила SOWA, аудит, автохилинг — это обрамление,
   содержательной их делает новая данные или новый метод рядом.
5. **Признаки разного класса в одной формулировке.** Решает признак предмета изменения, а не
   случайное слово. «Доработать аудирование запросов согласно новой модели аудита» — аудит
   (журнал), упоминание метамодели основанием для `contained` не считается; такая задача
   идёт со статусом `confirmed` и цитатой предмета, а не `conflict`.
6. **Уже принятые решения** (не пересматривать каждую неделю, а держать как правило):
   - устранение уязвимостей библиотек по SCA — **техническая**;
   - вывод новой реплики самообслуживания — **содержательная** (для читателя это новые
     данные);
   - security patch базовых образов — **технический релиз целиком**;
   - исправление по инциденту на источнике (новые поля, смена формата файла) —
     **содержательная**, если читатель увидит новые данные или изменившееся поведение;
   - аудит запросов, новая метамодель аудита, отправка в Аудит — **техническая**: это
     внутренний журнал обращений;
   - «Автохилинг» (самолечение сервиса) — **техническая**;
   - всё со словом «бизнес» (бизнес-проверки, бизнес-правила, бизнес-логика дата-продукта) —
     **содержательная**; если при этом смысл для читателя не виден, класс всё равно
     содержательная: признак сильнее скудного текста, вопрос не задаётся, а нехватка материала
     остаётся в обосновании задачи;
   - правила валидации запросов и ответов SOWA и профиль SOWA — **техническая**: это обвязка
     обмена. Рядом объявлен новый метод источника — метод первичен, задача содержательная.

## Когда сомневаюсь

- Два прочтения одинаково возможны → `unknown` с вопросом: «что именно меняется у
  читателя?». Вопрос задаётся один раз и коротко.
- Расхождение с правилом → статус `conflict`, задача уходит в список разбора и печатается
  с пометкой; решение остаётся за человеком.
- Признак сработал, а смысла нет (слово в названии топика, отсылка к другому продукту) →
  признак не учитывается; в `understanding` записывается, почему.

## Если признаков не нашлось

Класс ставится по пониманию, а не по «не нашлось ни слова»: понимание ясное —
`contained` или `technical` со статусом `reasoned`, и формулировка попадает в список
«что дописать в правила». Понимания нет — `unknown` с вопросом. Молча не отбрасывается
ничего.
