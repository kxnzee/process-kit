# Адаптер: Bitbucket Server (kind = `bitbucket-server`)

Как говорить с системой кода этого типа. Критерии отбора — в данных действия-источника
`actions/run-query/queries/<имя>.md` (командные и личные варианты — рядом, с префиксом уровня).

## Операции

MCP-сервер берётся из `codeStores[].mcpServer` в `config/sources.json`: имя сервера,
подключённого в сессии, вписывает команда при настройке. Вызовы строятся от этого имени:
`mcp__<mcpServer>__<имя>`; при `mcpServer = bitbucket-code` выходит `mcp__bitbucket-code__<имя>`.

Если инструмент не объявлен — загрузить через `tool_search`
(`select:mcp__<mcpServer>__bitbucket_list_pull_requests,...`, например
`select:mcp__bitbucket-code__bitbucket_list_pull_requests`). Сервера нет в сессии —
остановиться и сообщить; клонировать репозиторий вместо API **запрещено**.

| Capability | Инструмент | Зачем |
|---|---|---|
| `listPullRequests` | `bitbucket_list_pull_requests` | список PR (`state=MERGED`, `direction=INCOMING`, `at=<целевая ветка>` опционально) |
| `getPullRequest` | `bitbucket_get_pull_request` | данные одного PR, если в списке не хватает полей |
| `getPullRequestDiff` | `bitbucket_get_pull_request_diff` | дифф PR; `path` — фильтр по файлу |
| `listCommits` | `bitbucket_list_commits` | коммиты; фильтр `path` — искать правки под наблюдаемым путём |
| `getCommitChanges` | `bitbucket_get_commit_changes` | пофайловый состав коммита (merge-коммит: `since=` родитель) |

Все операции — чтение (`read`); записи в Bitbucket адаптер не предоставляет.
Координаты брать из конфига: `repositories[].projectKey`, `repositories[].slug`.
Префикс `refs/heads/` передавать не нужно.

## Пробный прогон

Без обращения к системе: действия-источники берут выборку из `tests/<имя>/fixture.json`
по параметру `dataFile`, сети не касаются и помечают прогон как демо. Для этого адаптера
годится фикстура с готовыми PR (`pullRequests[]`) и их диффами — ответы
`bitbucket_list_pull_requests`, `bitbucket_get_pull_request_diff` и `bitbucket_list_commits`
читаются из неё в том же виде, что и из сервера. Прогон ничего не пишет в Bitbucket: только
чтение фикстуры и файлы в `outputs/<имя>/.run/`.

## Пагинация

Ответы по 25 (`pullRequest.pageSize`), признак продолжения — `pagination.nextPageStart`,
признак конца — `isLastPage: true`. Читать страницы до конца окна; в отчёт положить число
просмотренных страниц и PR.

## Извлечение ключа задачи из PR

Смотреть три поля: `title`, `fromRef.displayId`, `description`. Искать паттерном
`pullRequest.keyExtraction.pattern`. Типичные форматы команды, у которой ключ стоит в
заголовке: `FIX <КЛЮЧ-1>: …`, ветки `bugfix/<КЛЮЧ-2>`,
`feature/<тема>/<КЛЮЧ-3>-короткое-имя`, в описании — ссылка на задачу.

**Ложные привязки.** Релизные метки совпадают с паттерном ключа: PR вида
`FIX <тема>: правка из branch/<КЛЮЧ-4> в master`, где `<КЛЮЧ-4>` — ветка релиза, а не
задача. Поэтому применять `pullRequest.keyExtraction.ignorePatterns` и игнорировать
совпадения, стоящие сразу после `branch/`. Ключ, полученный только из имени приёмной
ветки, считать неподтверждённым.

Один ключ может давать несколько смерженных PR (например, отдельно в основную ветку и в
релизную) — в отчёте это строки одного ключа, а не дубликаты на выброс.

## Признак правок под наблюдаемым путём

Наблюдаемый путь приходит из `params.watchPath` запроса. Порядок проверки PR:

1. `bitbucket_get_pull_request_diff` — искать заголовки файлов `diff --git a/<путь>/...`;
   большой дифф читать по одному `path`, если ответ усечён (усечение отличать от «файлов нет»).
2. Если diff недоступен или усечён неотличимо — `bitbucket_get_commit_changes` по
   `toRef.latestCommit` с `since=` предыдущей вершиной приёмной ветки; пагинация обязательна.
3. Альтернативный угол: `bitbucket_list_commits` с `path=<путь>` за окно — множество
   коммитов, реально трогавших артефакты; сопоставить с коммитами PR.

Пустой результат — это «правок нет», а не «не проверено». Статус «не проверено» ставить
только когда вызов не выполнился или данных не хватило.

## Поля выдачи, на которые опирается отчёт

`id`, `title`, `state`, `author`, `fromRef.displayId`, `fromRef.latestCommit`,
`toRef.displayId`, `toRef.latestCommit`, `closedDate` (unix ms — переводить в дату),
`reviewers[].name/.status`. Привязки к задаче в выдаче Bitbucket **нет** — только извлечение ключа.

## Статус проверок этого адаптера

| Факт | Статус |
|---|---|
| `state=MERGED`, пагинация 25/`nextPageStart`, состав полей PR, коллизия релизных меток | подтверждено на первой инсталляции (координаты — в командном конфиге, не здесь) |
| поведение `bitbucket_get_pull_request_diff` на больших диффах и точный формат усечения | не проверено |
| имена приёмных веток и релизного паттерна | у каждой команды свои — `acceptTargetBranches` и `ignorePatterns` в конфиге |
