# Отдельный агент и восстановление

Процесс перечисляет в `params.agentSteps` имена шагов, которым клиент даёт отдельный
контекст. Пустой список или его отсутствие — исполнитель выполняет шаг сам.

1. Координатор вызывает разрешённый `run begin` (для act — с проверенным approval), затем запускает одного агента
   на этот шаг. Передаёт корень проекта, output, текущий pending.id/attemptId и полученную
   карточку save целиком (step/artifact/extension/next), ACTION.md, нужные queryFile/adapterFile,
   id подключения и только необходимые pending.params. State.json целиком не пересылается.
   Если next уже вернул model существующей попытки, повторный begin не вызывается.
   Для разрешённого act после одного внешнего вызова исполнитель получает next →
   reconcile с effectRequest и передаёт запрос доверенному хосту; save требует его
   receipt с applied. Исполнитель не выдаёт proof сам и не повторяет эффект;
   без проверенного исхода действует правило reconcile ниже.
2. Агент читает систему, сохраняет артефакт штатной командой `node tools/kit.js run save`
   своим spec-файлом с переданным attemptId (журнал проверяет контракт, отбор и хеши) и возвращает сводку не длиннее
   пяти строк: счётчики, полноту чтения с причинами и путь артефакта.
3. Сырые ответы систем, диффы, тексты и перечни файлов в контекст координатора не
   переносятся. Координатор не пересохраняет артефакт и не пересобирает его из сводки:
   следующий шаг читает сохранённый файл.
4. К прогону одновременно обращается один исполнитель. Следующий шаг — включая другого агента —
   начинается только после `save` предыдущего; параллельные записи `state.json` запрещены.
5. Локальные вычисления (`evaluate-data`, `compose-report` через `run execute`) агенту не
   отдаются: внешних данных в них нет, экономии контекста тоже.
6. Решения развилки, `finish`, `fail` и сверка результата с задачей человека остаются за
   координатором. Агент не выбирает переход, не правит настройки и не пишет итог.
7. Если отдельный контекст недоступен до передачи работы, координатор выполняет
   разрешённую карточкой операцию сам и сообщает ограничение в summary и ответе.
   Если агент уже запущен и завершился ошибкой, сначала останови/дождись его завершения,
   затем вызови `run next`; при прерванной записи или lock — `run recover`.
   Продолжай только по возвращённой карточке существующего output и attemptId:
   сохранённый шаг не выполняй заново; pending source/transform продолжай в той же
   попытке, сверив наличие результата и исход чтения. Не пересоздавай Run или begin.
   Для pending act сначала reconcile: неизвестный исход запрещает повтор эффекта.
   Save допускается только с проверенным applied; retry — только с проверенным
   not-applied доверенного хоста, затем требуется новое разрешение по карточке.
   Ошибка агента и отсутствие ответа сами по себе не доказывают not-applied.
   Без доверенной сверки остановись с точным препятствием и сохрани pending.


## Продолжение существующего Run

После ответа или устранения препятствия продолжай действующее поручение без нового
формального согласия. После явной отмены/замены нужно новое решение; при нескольких
кандидатах уточни точный output. Используй публичный next/recover: Controller проверяет
identity, файлы, хеши, параметры, артефакты и стек. Не заменяй это ручной сверкой по датам
или last_step, не пересчитывай today и не вызывай core API.

Если состояние повреждено, сохрани файлы и передай факты Diagnose. Новый запуск можно
обсуждать после разбора уже выполненных действий; неизвестный эффект требует reconcile
даже при намерении создать другой Run. Публикация определения через definition publish
не является run publish: последнее копирует сохранённый артефакт после finish.
