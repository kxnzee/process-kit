# Архитектура Process Kit

Один репозиторий, уровни разделены ветками: `master` — общий уровень, `team-<команда>` —
командный, `my` — личный. Клиент GigaCode открывает репозиторий как обычную папку
проекта; про уровни он не знает. В исходной реализации на стенде использовалась схема: расширения GigaCode
работают только в CLI и перезаписывают `~/.gigacode/`, поэтому расширения нет —
есть файлы в папке проекта.

```
process-kit/                       ← ветка master (общий уровень)
├── GIGACODE.md                    ПРАВИЛА модели: уровни, структура, имена, контекст
├── README.md                      для человека + раздел «Для разработчика»
├── docs/ARCHITECTURE.md           устройство системы (этот файл)
├── .gitignore                     outputs/, .history/, всё, что клиент пишет сам
├── .gigacode/
│   ├── settings.json              MCP-серверы; токен — ссылка $secret:<имя>/<ключ>
│   ├── hooks/pre-push             запрет отправки личной ветки в origin
│   └── skills/                    ПЛОСКО: pp-ai-mentor, pp-ai-dispatch, pp-ai-guide, pp-ai-init,
│                                  pp-ai-diagnose, pp-ai-run-process, pp-ai-run-action,
│                                  pp-ai-create-process, pp-ai-create-action, pp-ai-create-adapter, pp-ai-promote-changes-team,
│                                  pp-ai-promote-changes-master
├── processes/<имя>/PROCESS.md      шапка-манифест и маршрут; данные внутри папки
├── actions/<имя>/                 действия: ACTION.md + queries/, templates/, rules/
├── adapters/<имя>/ADAPTER.md                      механика систем: jira/, bitbucket/
├── context/<master|team|my>/<тема>/CONTEXT.md        термины и общие правила
├── config/
│   ├── master/                    общие безопасные defaults
│   ├── team/                      командные настройки и EXAMPLE.json
│   └── my/                        личные настройки и EXAMPLE.json
├── tools/
│   ├── kit.js                     единый CLI и каталог команд
│   └── lib/                       внутренние модули по назначению
├── tests/                         тестовый код и run.js, запуск через kit.js test
├── outputs/                       результаты запусков (не версионируется):
│                                   ОДНА папка на запуск, имя без пробелов
│   ├── <ГГГГ-ММ-ДД>_настройка/    что-сделано.md
│   ├── <ГГГГ-ММ-ДД>_<задача>/     итог.md + файлы для человека
│   │   └── .run/                  run.md, trace.jsonl, <NN>-<шаг>.*, state.json
│   └── <ГГГГ-ММ-ДД>_заявка-<что>/ заявка.md (нет прав создать ветку или систему)
└── .history/                      runs.jsonl — журнал прогонов; cache/ (не версионируется)
```

Командная ветка `team-<команда>` и личная `my` повторяют структуру и добавляют файлы
со своим префиксом в те же папки. Командная ветка хранит `config/team/config.json`. Личная добавляет `config/my/config.json`; master поставляет общие настройки и примеры сущностей.

## Что чем не является

| Каталог | Что это | Кто читает |
|---|---|---|
| `.gigacode/skills/pp-ai-*` | служебные скиллы, команды «/» | GigaCode — регистрирует сам |
| `actions/` | вызываемые функции с аргументами и результатом | исполнитель по имени из процесса |
| `processes/` | маршруты шагов | диспетчер (подбор), исполнитель |
| `adapters/`, `config/` | подключения к системам | исполнитель |
| `context/` | факты и пожелания | исполнитель — только при явном подключении |

Действие не регистрируется клиентом, поэтому вложенность `actions/<имя>/queries/`
ограничением GigaCode не задевается. Скиллы, наоборот, лежат строго плоско.

## Уровни

| Уровень | Ветка | Кто правит | Префикс файлов | Видит |
|---|---|---|---|---|
| общий | `master` | разработчик набора через PR из `master-*` | нет | только свои файлы |
| командный | `team-<команда>` от `master` | команда через PR | `team-<команда>-` | свои + общие |
| личный | `my` от команды или от `master` | сам человек, обычно локально | `my-` | свои + командные + общие |

**Ссылки только вверх:** `my` → `team-*` → `master`. Вниз — никогда: общий или командный
файл, ссылающийся на имя, которого нет в его собственной ветке, — ошибка раскладки;
исполнитель останавливается и называет файл и ссылку.

Уровень определяется по текущей ветке (`git branch --show-current`), файлы ищутся в
рабочей копии. Рабочие ветки — `master-<имя>` (общий уровень, правки через PR) и ветка
команды от `team-<команда>`; имя рабочей ветки команду не называет — её берут из
настроек master/team/my через tools/lib/config/config.js или из `--team <код>`. Ветка, которая не называет
команду и не определена в настройках master/team/my, — предупреждение проверки: префиксы файлов
уровня в ней не проверены.

Клиент про уровни не знает: все клиенты читают одну и ту же папку и один и тот же
`GIGACODE.md`. Процессы, экшены и адаптеры различаются префиксами папок. Конфиг и контекст разделены папками master/team/my; содержимое настроек зависит от окружения.

## Сценарии приложения и исполнители

Сценарии приложения отделены от предметных processes/ и actions/. Их инструкции
живут в плоских папках .gigacode/skills/. Ответственность разделена:

| Часть | Вход | Ответственность и возврат |
|---|---|---|
| pp-ai-mentor | Запрос и ответы человека | Общение, уточнения и согласия; передача задачи диспетчеру, объяснение результата |
| pp-ai-dispatch | Задача, факты, ответы, согласия, предыдущий результат | Выбор сценария приложения и исполнителя; итог или конкретный вопрос ментору. Маршрут активного процесса не выбирает |
| Операционные скиллы | Одна операция и нужные входы | Процедура, проверенный результат, изменения или препятствие; возврат диспетчеру |
| Субагент при наличии в клиенте | Выбранный скилл и минимальный пакет задачи | Выполнение в отдельном контексте; возврат по тому же контракту |
| tools/ | Аргументы конкретной операции | Факты, выполнение и проверки; без выбора скилла |

Ментор знает интерфейс диспетчера, а не каталог операций. Диспетчер получает через
`node tools/kit.js skills` только name, description и путь фактических SKILL.md,
затем читает полную инструкцию выбранного скилла. Каталог одинаков для LF и CRLF,
не требует POSIX-оболочки и не возвращает тела инструкций.
Назначение модулей находится в их описаниях; второй полный каталог здесь не поддерживается.
Скилл задаёт способ работы, субагент — отдельный контекст исполнения. Клиент должен
действительно предоставлять делегирование; наличие SKILL.md его не устанавливает.
Обычная последовательная операция может выполняться текущим агентом без нового вызова.

Это разделение инструкций, а не программный контроллер диалога. Автоматический
SessionStart-hook и собственный runtime субагентов не устанавливаются. Нативная
регистрация/изоляция субагентов зависит от клиента и проверяется отдельно.

Пакет передачи содержит исходную задачу, цель операции, нужные факты и пути входов,
ответы и действующие согласия. Возврат содержит статус, проверенные факты, изменения,
пути результатов, недостающее или препятствие. Пакет остаётся в диалоге и не создаёт
новый журнал переписки. Отдельный контекст не изолирует общие файлы: запись последовательна.

Скиллы не вызывают соседние скиллы и не дублируют их процедуры. Диспетчер сохраняет
continuation при needs-action и возвращает конструктору процесса результат конструктора
действия. Completed означает завершение только этой операции. При blocked без новых
сведений повторного вызова нет. Вопрос человеку и итоговое объяснение ведёт ментор.

Общие границы принадлежат GIGACODE.md; единственный порядок переходов — pp-ai-dispatch;
детали каждой операции — её скиллу. Пользовательская памятка — README.md, раздел
«Как работать в этой папке». Изменение знакомства не требует менять рабочие процессы.

### Проверенное состояние настройки

Когда выбранной операции нужна личная готовность, настройщик вызывает
node tools/kit.js setup-status. Команда читает локальный Git, настройки и hooks без
сети и записи. Она возвращает personal.state, personalReady, известные выборы
profile/team/storage, состояние защиты, счётчики объявленных подключений и issues.
Адреса, имена, email, содержимое настроек и сырые ошибки в проекцию не входят.
Доступ к внешним системам остаётся not-checked; without-team отличается от unknown.

Код не выбирает операцию или Markdown-файл. Ветку по состоянию выбирает pp-ai-init:
ready — только недостающее; missing — новая копия; invalid/incomplete/outside-personal —
проверка существующей настройки; unknown — остановка затронутой настройки. Подробности
находятся в references/ этого скилла и читаются только при выбранной операции.
Для объяснения требований к подключению готовой копии достаточно краткого плана
самого SKILL.md. После изменений состояние проверяется заново. Приветствие, демо
и разбор сохранённого запуска не требуют обязательной проверки личной настройки.

## Четыре уровня модели

| Уровень модели | Вопрос | Где живёт | Правило изменения |
|---|---|---|---|
| Процесс | в каком порядке и когда что выполнять | `processes/` | меняются шаги и ветвления; действия не трогаются |
| Действие | что делает один шаг | `actions/<имя>/ACTION.md` | контракт (`consumes`/`produces`) стабилен; общие материалы — у экшена, специфические запросы/правила/шаблоны — у вызывающего процесса |
| Адаптер | как говорить с системой | `adapters/` | новая система = новый адаптер; процессы не правятся |
| Координаты | где именно лежит | `config/master/`, `config/team/`, `config/my/` | меняются хосты, проекты, лимиты, дефолты |

Верхний уровень знает нижний **только по ссылке**: имя файла или `id` системы.
Контекст — отдельная сущность фактов и договорённостей; адаптер и координаты вместе
описывают подключение. Уровни модели в таблице — границы ответственности файлов.

## Принцип декомпозиции

1. **source / transform / act** — три класса действий; сеть есть только у `source`
   и `act`, поэтому отчёт логику можно проверять на фикстурах без систем.
2. Сценарий раскладывается в цепочку независимых блоков. Для отчёта SDD:
   `run-query` (задачи) → `read-code-evidence` (код) → `evaluate-data` с правилом процесса (расчёт) →
   `compose-report` (отчёт) → `branch` → `evaluate-data` (данные письма) →
   `compose-report` (тело письма) → `prepare-mail-draft` (черновик по просьбе).
   Почтового подключения в поставке нет: черновик не отправляется.
3. В процессе хранятся только ссылки и параметры шага — текст действия не дублируется.
4. Действие — одна законченная операция, фиксированные входы и один именованный
   результат. Пагинация/батчи остаются внутри чтения; границы операций определяются контрактами функций, а не количеством инструментальных вызовов. Контракты SDD — processes/sdd-stories-report/reference.md.

## Форма процесса

Процесс — Markdown: шапка (`name`, `version`, `area`, `status`, `description`,
`examples` или `example`, `requires`, `entry`, `params`; `title` — заголовок для человека) и раздел «Шаги», где у шага есть `действие:` / `процесс:` /
`branch:`, `параметры:`, `артефакт:`, `следующий:`. Маршрут читается из этих полей, а не
из порядка подразделов. Шаги разбираются общим tools/lib/entities/process-model.js. Исполнитель — модель;
`tools/lib/validation/validate.js` проверяет механические свойства: шапки, ссылки, маршрут, циклы,
доступность входных артефактов и зависимости. Смысл рецепта подтверждает владелец;
зелёная структурная проверка не заменяет пробный прогон в GigaCode.

## Маршрут

- Шаги — именованные узлы; старт в `entry`, дальше по `следующий:`.
- Развилка — узел `branch`: упорядоченные правила `когда:` по артефактам выполненных шагов
  плюс `default`.
- Шаг может указывать на другой процесс (`процесс:`) — подпроцесс, глубина ограничена master.execution.maxProcessDepth, циклы
  запрещены.
- Каждый шаг кладёт результат в артефакт с именем `артефакт:` и пишет его файлом в
  каталог прогона.

Источник страницы может использовать действие `read-page` с `adapter: environment-tool`:
в live агент читает страницу доступным инструментом среды и сохраняет адрес и текст
артефактом; в demo — только явно выбранную фикстуру. Это не подтверждает доступность
конкретного инструмента. Существующие source/act с подключением сохраняют свои правила.

## Обратная связь по запуску

При первом обращении диспетчер передаёт краткое знакомство в pp-ai-guide и продолжает
понятную задачу. Для вопроса о работе с приложением guide использует полный инструктаж.

Разбор запуска начинается при обнаруженном агентом сбое, жалобе пользователя на результат
или просьбе объяснить выполнение. При сбое исполнитель сам фиксирует остановку и
возвращает точный output и факты диспетчеру. Диспетчер без технической команды от
пользователя передаёт их в pp-ai-diagnose. Этот модуль создаёт диагностику; при жалобе
он выбирает связанный с ней запуск, уточняет неоднозначность и сопоставляет нужные
события, результат и контракты. Если reportFile уже передан, использует существующий файл.
Завершённый запуск при этом не переводится в failed и не выполняется повторно.
Пользователь не вызывает служебные команды и не собирает журнал. Агент объясняет
подтверждённое и предполагаемое, при нехватке данных предлагает файл разработчику;
передача остаётся решением пользователя. Разбор не разрешает исправлять платформу.

Операция журнала `run diagnose` с параметром output создаёт рядом с результатом отдельный
файл диагностики. Он содержит состояние, идентификаторы шагов, безопасную проекцию
событий, приблизительную категорию ошибки и версию текущей рабочей копии. Повторный
вызов не перезаписывает прежний файл. Пользователь сам проверяет и передаёт файл;
автоматической отправки нет. Входы, параметры, сырые ошибки, артефакты и переписка
не копируются. Категория не доказывает причину, а текущий коммит не доказывает версию
на момент запуска. Разработчик сопоставляет факты с кодом и контрактом, уточняет
недостающие данные и только затем определяет исправление. Агент разработчика отделяет
подтверждённое от предположений, сравнивает ожидаемый результат процесса с фактическими
событиями, локализует и воспроизводит проблему, затем исправляет причину и проверяет
затронутый сценарий. Не меняет тесты только ради прохождения и не заявляет исправление
без подтверждения; при нехватке данных указывает, чего именно не хватает. Ошибка до создания папки
прогона или несохранённое содержимое диалога этим отчётом не восстанавливаются.

## Изоляция шага

Пакет входа (рецепт действия, адаптер, данные действия, артефакты по `consumes`, значения
параметров) собирается для шага отдельно; наружу отдаётся только `produces` файлом
`outputs/<запуск>/.run/<NN>-<шаг>.<ext>`; соответствие логического имени файлу
записывается в state.artifacts. Сырые ответы систем, диффы и шаблоны в общий контекст
прогона не переносятся: в диалоге остаётся сводка шага не длиннее пяти строк.
Шаги чтения внешних систем процесс объявляет списком `params.agentSteps` — такой шаг
координатор исполняет через отдельного агента клиента; агент сам сохраняет артефакт командой
save и возвращает только сводку. К журналу прогона при этом обращается один исполнитель,
локальные вычисления в агента не отдаются. Если отдельный контекст не поддерживается,
исполнитель фиксирует ограничение и не заявляет техническую изоляцию.
Порядок делегирования описан в `.gigacode/skills/pp-ai-run-process/SKILL.md`.

Папка запуска одна на прогон: `outputs/<ГГГГ-ММ-ДД>_<коротко>/` в корне папки, служебные
файлы — в её `.run/` (`run.md` с маршрутом и причинами остановок, `trace.jsonl`,
`<NN>-<шаг>.*`, `state.json`). Артефакт каждого шага пишется в `.run/`, включая последний:
полный след прогона нужен, чтобы любой шаг можно было проверить отдельно. Результат
последнего шага команда finish сохраняет побайтно вторым файлом в корень папки запуска.
Исходный артефакт остаётся в .run/, повторное выполнение действия не требуется. Если процесс
объявляет для человека ещё один файл (отчёт рядом с черновиком письма), он добавляется
командой publish после finish; итог перечисляет оба. `итог.md` пишется всегда, даже если
прогон остановился, датируется местным днём прогона словами и
перечисляет только файлы, лежащие рядом с ним.

Правило про два файла последнего шага записано явно (`GIGACODE.md`, «Где лежат
результаты», и шаг вывода исполнителя) и проверяется механически: `tools/lib/validation/validate.js`
сообщает об артефакте шага в корне папки запуска, об отсутствии файла для человека и об
упоминании служебной подпапки в итоге. Причина — опыт первого прогона: без явного имени
файла правило «результат в папку запуска» исполнитель понял по-своему.

## Конфиг и контекст

Настройки master/team/my читаются tools/lib/config/config.js. В master — общие defaults,
в team — метаданные команды и общие подключения/ресурсы, в my — выбор teamId,
собственные подключения и личные defaults. Массивы не перезаписываются: id уникальны.
Приоритет выбора: явный аргумент → my → team → master. teamId=null исключает team.
Механика и поля — config/team/README.md.

## Токены

`.gigacode/settings.json` описывает MCP-серверы; на месте токена в поставке стоит ссылка
на секрет вида `$secret:<имя>/<ключ>` (`$secret:pp-ai-jira/x-jira-token`). Значение подставляет
сам клиент GigaCode: человек заводит секрет штатным способом в CLI, VS Code или десктопном
приложении, клиент использует ссылку при подключении; после изменения настроек может потребоваться перезапуск сессии.
Отдельного файла доступов в проекте нет; в репозитории токенов нет.
Командная и личная ветки `settings.json` не меняют, свои личные серверы человек добавляет
в глобальные настройки GigaCode, а глобальную `~/.gigacode/` агент только читает.
Готовность подключения определяется по факту: сервер объявлен в сессии и ответил на одно
проверочное чтение.

## Защита

Хука GigaCode нет. Защита — правила веток Bitbucket (прямой push в `master` и `team-*`
запрещён, слияние через PR, запрет force push и удаления), `.gitignore` для `outputs/`
и `.history/`, запрет отправки личной ветки средствами git:
`git branch --unset-upstream`, `git config branch.my.pushRemote no_push`, pre-push hook
в `.git/hooks/`, устанавливаемый tools/lib/git/install-hooks.js с сохранением прежнего hook.
Локальный hook — дополнительная защита: серверные ограничения настраивает владелец,
наличие файла hook не доказывает, что ограничения Bitbucket включены. `tools/lib/validation/validate.js` дополнительно проверяет, что `outputs/` и
`.history/` не попали в git (`git ls-files`): данные человека версии не подлежат.

## Как устроен прогон

1. Ментор `/pp-ai-mentor <задача>` передаёт запрос диспетчеру; тот подбирает процесс
   по шапкам в `processes/` и выбирает инструкцию исполнения.
2. Исполнитель `/pp-ai-run-process process=<имя>` читает шаги, для каждого берёт
   `actions/<имя>/ACTION.md`, данные, систему из `config/`, адаптер и
   нужный context по манифесту.
3. Результат шага — файл, он идёт входом в следующий шаг, и так до конца маршрута.

Демонстрационный прогон без систем:
`/pp-ai-run-process process=<имя> dataFile=processes/<имя>/fixture.json` — источники читают выборку из
фикстуры и помечают прогон как демо.

## Обновление

Общий уровень приезжает тегом `vX.Y.Z` на `master`: `git fetch --tags origin`,
`git merge vX.Y.Z`. Командный — `git merge origin/team-<команда>`. Свои файлы имеют свои
имена, что уменьшает число конфликтов, но не исключает изменения общих зависимостей.
Перед слиянием — просмотр изменений и согласие пользователя; конфликты разрешаются
явно, без автоматического reset. После слияния — node tools/kit.js test.

Экшен — функция с аргументами, результатом и ошибками; процесс связывает вызовы.
Запросы run-query и read-code-evidence передаются как `queryFile` из папки вызывающего процесса; `parameters` содержит аргументы запроса.

## Разрешение сущностей

Requires описывает целые сущности: actions/processes именами, context/config уровнями
master/team/my. Шаги используют объявленные экшены и подпроцессы. Внутренние ресурсы
экшена принадлежат его папке, ресурсы сценария — папке процесса. tools/lib/entities/entities.js
возвращает entities (точки входа и темы контекста), connections (выбранные записи и
адаптеры), files (снимок) и missing. Агент читает нужные сущности, не весь снимок.
Конфиги выбираются кодом только из объявленных уровней; execution master всегда
используется механизмом запуска. Конфликты контекста требуют решения человека.

Одиночные локальные transform вызываются через kit.js action без постоянного процесса.
Агент процесса остаётся координатором: run next сообщает следующий шаг, run execute
вызывает только локальные функции runtime. Сетевые инструменты исполняет агент. Вычислимую ветку выбирает код; семантический
выбор предлагает агент, а подтверждение человека передаётся явно. Структурированный текст может формироваться и проверяться rendererFile
процесса; успешный save тогда подтверждает перенос проверяемых фактов из данных.


## Контроллер и допуск определения

Контроллер — существующий `tools/lib/runtime/run-journal.js`: start, operation и execute.
Operation(next) выдаёт разрешённую операцию, operation(begin/save/enter/leave/finish/fail)
проверяет переход и фиксирует состояние, operation(recover) завершает прерванную запись.
Отдельного агентного цикла, сервиса, менеджера субагентов или API GigaCode в ядре нет.
GigaCode исполняет ACTION.md и вызывает стандартные Node.js-команды по карточкам.
Публичный run вызывает небольшой tools/lib/integrations/gigacode-run.js. Он передаёт
ядру явный список файлов окружения и функцию их отпечатка; в live добавляет
.gigacode/settings.json и исключает только permissions из сравнения. В библиотечном
контроллере нет имени клиента и разбора его настроек; без адаптера он работает без
файлов GigaCode. Это один интеграционный вызов, без реестра плагинов.
Единственный пользовательский вход остаётся pp-ai-mentor; pp-ai-dispatch выбирает
сценарий приложения, pp-ai-run-process ведёт весь запуск через контроллер.

У процесса остаются running/completed/failed. Состояние этапа выводится из курсора,
pending и событий: следующий ещё не начат, pending начат, step_completed завершён.
Ожидание сверки внешнего эффекта представлено pending и операцией reconcile; отдельный
дублирующий реестр статусов шагов не вводится. Агент не передаёт целевой status.

| Операция | Условия принятия |
|---|---|
| choose | running, нет pending, текущая развилка; target разрешён кодом/решением, для user вне default confirmed=true |
| begin / enter | running, нет pending, узел соответствует курсору либо разрешённой ветке |
| save | running, текущий pending и attemptId; выход, контракт и next соответствуют определению |
| leave | конец подпроцесса, нет pending, есть результат и родительское продолжение |
| finish | конец корневого маршрута, нет pending, есть проверенный результат |
| fail | запуск не завершён успешно; причина сохраняется |
| retry | текущий attemptId, подтверждение отсутствия эффекта; физического результата ещё нет |
| publish | completed; копируется только сохранённый артефакт |
| recover | проверяемая локальная блокировка и согласованная незавершённая запись |

`process-definition.js` переиспользует processModel, объявления сущностей и контракты
действий. Один набор проверяет шапку, маршрут, подпроцессы, обязательные артефакты на
каждом входящем пути и наличие результата на каждом выходе. Его вызывают check,
start, операции контроллера и допуск определения. Нельзя обойти эти проверки пропуском
предпускового вызова агента.

У определения по умолчанию требуется публикация; явно пишется `publication: required`.
Все три определения поставки (example, sdd-stories-report, info-povod) переведены
на этот порядок и имеют свидетельства local/demo-проверки всех маршрутов. Значение
legacy поддерживается только для явной миграции старых пользовательских копий; в
определениях поставки его нет. Общая валидация обязательна и для старого формата. Поле status (действует/устарел)
сохраняет смысл применимости и не является статусом проверки.

Жизненный цикл определения: draft (нет актуального допуска) → validated → tested →
published. `node tools/kit.js definition <validate|test|publish|status> <spec.json>` —
небольшой интерфейс внутри существующего kit.js. Он не создаёт отдельный CLI-продукт.
Validate пересоздаёт свидетельство после проверки определения, даже если прежний
publication.json повреждён. Validate принимает process, params и необязательный mode=demo; test — process и outputs;
publish/status — process. Публикация означает локальный допуск определения, без Git,
отправки, внешнего сервиса и без вызова экшенов самим инструментом.

Свидетельство `processes/<имя>/publication.json` создаёт код. В нём — статус,
хеши выбранных определений, ресурсов actions/processes/context, область проверки и
имена проверочных прогонов. Runtime/config не включаются в допуск бизнес-определения;
их целостность отдельно защищена снимком каждого запуска. Допуск проверяется
также у каждого подпроцесса; legacy-родитель не разрешает неопубликованного ребёнка. Проверочные прогоны
создаются с definitionTest=true только в local/demo; live для них запрещён. Test
принимает лишь завершённые актуальные прогоны данного процесса и требует покрытия
всех целей каждой развилки, включая подпроцессы. Это проверка local/demo, а не
свидетельство интеграции GigaCode или доступа к провайдеру.

Изменение защищённого файла делает допуск неактуальным. Новая выбранная зависимость
также требует проверки перед обычным запуском. Фикстура demo исключается из выпуска;
её точные байты защищает снимок проверочного запуска. Введённые человеком runtime-данные
и секреты в свидетельство не копируются. Самостоятельная правка допуска или присвоение
legacy не защищены от агента, имеющего запись в файлы; это не криптографическая граница.

Ветвление без branchRule остаётся семантическим: LLM выбирает объявленную цель и
передаёт непустой decision, код проверяет допустимость, а не истинность рассуждения.
Для вычислимого условия используется существующий JS-ресурс процесса:
`branchRule: rules/branches.js`, экспорт choose({step, params, artifacts}) → {target, reason}.
Модуль синхронный, без сети и записи, получает уже сохранённые значения артефактов.
Choose фиксирует выбор отдельно от begin и позволяет переходить между развилками;
next возвращает точный текст раздела из модели, без сопоставления по префиксу имени.
Контроллер вычисляет выбор и отклоняет другую цель даже при прямом begin/finish.
У развилки можно явно задать decision: code/model/user. Code требует branchRule;
model проверяет предложение агента по объявленным целям. User требует confirmed=true
для перехода за пределы безопасной default-цели и непустой decision с фактическим
ответом человека. Это проверка структуры подтверждения, не доказательство происхождения
сообщения; агент не должен выдумывать согласие. В next это decisionMode и
requiresConfirmation. Свободный текст условия не исполняется.

В SDD wantsMail — явный параметр намерения человека; plainCount проверяет код.
В info-povod первый выбор вычисляется по methodologyCheck=yes/no; значение ask
отклоняется до создания запуска. Последующее продолжение после сводки — decision=user,
поскольку человек должен увидеть результат сверки, прежде чем согласиться.
StepStatus в карточке показывает pending/running/blocked/completed/failed и выводится
из единственного сохранённого состояния, без второго журнала статусов.

## Состояние и результаты запуска

Инструкция исполнителю и spec операций находятся в `.gigacode/skills/pp-ai-run-process/SKILL.md`.
Журнал сохраняет факты и проверяет переходы; MCP исполняется агентом, вычислимые
развилки — кодом. Смысловые решения и подтверждения человека проходят проверку формы.

## Каталог запуска

Один запуск — новая outputs/<YYYY-MM-DD>_<коротко>/ от корня Git. Дата — местный день
запуска, не период данных. Короткое имя: 1–4 слова строчными буквами/цифрами через
дефис, до 40 символов. При совпадении добавляется -2, -3 вне лимита слов.
Для demo используется префикс проба-. Каталог не переиспользуется новым запуском.

```text
outputs/<дата>_<задача>/
  итог.md
  <файл результата>.md
  .run/
    inputs/input.md
    01-<шаг>.json
    02-<шаг>.md
    state.json
    run.md
    trace.jsonl
```

Inputs/input.md создаётся только при inputText. Каждый завершённый шаг имеет один
служебный артефакт; номера едины для вложенных вызовов. Artifacts связывает логические
имена с физическими файлами непосредственно в .run/. Finish побайтно копирует последний
артефакт в корень каталога. Промежуточные результаты сохраняются в .run/.
Имена человеческого результата проверяются validResultName на переносимость Windows;
итог.md и префикс NN- зарезервированы. Проверка завершения запрещает pending и stack.

### Идентичность и целостность

| Поле identity | Значение |
|---|---|
| process / mode | Корневой процесс и local/live/demo |
| params | Эффективные параметры корня; today уже разрешён |
| overrides | Явные аргументы отдельно от defaults |
| extraFiles | Явно добавленные зависимости |
| definitionTest | Проверочный local/demo-прогон определения, не обычный рабочий результат |
| hashAlgorithm | sha256 |
| files | Пути выбранных файлов → SHA256 байтов |

Алгоритм рабочего журнала — SHA256; ручные снимки с другим алгоритмом не поддерживаются.
Start снимает определения, внутренние ресурсы экшенов, выбранные ресурсы процесса,
темы объявленных уровней контекста, нужные конфиги/адаптеры и служебный код.
Внешний текст сначала копируется в inputs/input.md, затем включается в снимок.
Execution master читается в любом режиме. Конфиги подключений выбираются из объявленных
уровней; local/demo не требуют реальных систем. Секреты в параметры не включаются.

Перед операцией проверяются хеши исходных файлов, scopeParams, artifactHashes и
recordedArtifacts. Состав зависимостей собирается повторно: новый ресурс экшена или
новая тема контекста меняет снимок и требует нового запуска. При enter сохраняются
область родителя и продолжение; leave возвращает результат под псевдонимом вызова.
При отсутствии снимка, несовпадении или неизвестном стеке безопасное продолжение
не доказано. Внешний эффект подтверждается ответом системы, а не статусом state.

### События, итог и история

Begin фиксирует pending.id и step_started перед действием; возвращённый save содержит
attemptId. Save принимает результат только этой попытки и проверяет контракт.
Внешний act требует effect.status=confirmed и фактический reference подтверждения.
После прерывания next/recover возвращает reconcile, не новый внешний вызов. Если
эффект не произошёл и это подтверждено, retry с effect.status=not-applied и reference
снимает pending; следующий begin выдаёт новый id. Неизвестный исход не разрешает повтор.
Reference — запись предоставленного подтверждения, а не независимое доказательство
со стороны провайдера; достоверность проверяется средствами GigaCode и внешней системы.

Run-storage сохраняет единственную незавершённую transaction.json: ожидаемые хеши
исходного состояния/trace и подготовленные новые байты. События собираются в памяти,
отклонённая операция их не записывает. Затем атомарными заменами сохраняются trace,
state и checkpoint с ревизией и хешами; run.md, итог и история — восстанавливаемые
проекции. Transaction удаляется после их успешной записи. Это локальное восстановление
файловой операции, не event sourcing и не новое хранилище.

При прерывании обычная операция требует run recover. Он принимает только исходные
или подготовленные байты, завершает ту же запись и восстанавливает проекции, без
повторного исполнения действия. Checkpoint обнаруживает несогласованные правки state
и trace. Прерванный save до подготовки transaction можно повторить только с тем же
физическим содержимым; другой результат или retry с уже существующим файлом отклоняется.
Гарантии относятся к прерыванию процесса и проверенным сбоям файловых операций;
fsync-протокол для потери питания и сетевые файловые системы не заявлены.

Блокировки публикуются атомарно вместе с PID, именем компьютера и идентификатором
владельца; восстановление использует тот же протокол и после собственного прерывания
также может быть продолжено. Работающие владельцы не вытесняются. Только явный recover может снять блокировку
проверенно завершившегося локального процесса, включая блокировку истории. Работающий,
неизвестный или удалённый владелец требует отдельного разбора. Ручное удаление locks
не является штатным восстановлением. История не дублирует запись одного output.
Прежние запуски без schemaVersion=2 сохраняют прежний формат; отсутствие checkpoint
у версии 2 — ошибка. Изменившийся служебный код или определение в снимке по-прежнему
требует нового запуска; диагностическое чтение старого журнала доступно отдельно.

Чувствительные данные не должны попадать в параметры, события и диагностические
сообщения. Хеши обнаруживают несогласованную правку, но не препятствуют согласованной
подмене всех файлов агентом с доступом на запись. Контроллер также не может заставить
LLM вызвать инструмент или подтвердить фактическое внешнее действие без провайдера.

Итог.md создаётся при start и обновляется журналом. В нём — задача, дата, исход,
краткое выполненное, источник данных, сведения о внешних изменениях и конечный файл.
Summary позволяет передать фактическое описание выполненного. Объём и период отчёта
проверяются по его данным; журнал не вычисляет эти сведения вместо экшена.
Для demo итог помечает пробный прогон и тестовые данные; отчёт содержит ДАННЫЕ ДЕМО.

Finish/fail обновляют .history/runs.jsonl: одна актуальная строка на output, без
дублирования при повторном завершении. Outcome — success/failed/draft; draft не
означает отправку. Индекс не хранит разговоры, предпочтения или сырые ответы систем.
История — внутренний модуль, отдельного CLI нет. Журнал обновляет её сам при
finish/fail. При повреждении/блокировке индекс не затирается;
результат может уже существовать, ошибка сообщается отдельно. Locks не удаляются
автоматически чужим запуском.

### Другие результаты и обслуживание

Настройка сохраняет outputs/<дата>_настройка/что-сделано.md. Заявка сохраняет
outputs/<дата>_заявка-<что>/заявка.md. У них нет .run/; формы содержатся в создающих
их скиллах. Имя каталога само по себе не доказывает выполнение настройки или отправку.

Outputs/ и .history/ исключены из Git, переноса и requires. Очистка .run/ — отдельная
явная операция обслуживания; результаты и история не удаляются заодно. Неоднозначные
старые каталоги не объединяются и не переносятся по догадке. Предпочтения находятся
в config/my или context/my по своему назначению, отдельно от истории запусков.


Если `date` не передан, start выбирает текущий местный день. Период данных и generatedAt
фикстуры не определяют дату папки. Ответы журнала возвращают outputDir/summaryFile/resultFile;
summaryFile находится рядом с результатом, вне .run/. Источник в итоге определяется
по фактическому inputText или локальным файлам.

## Инструменты

Единственная публичная точка входа: `node tools/kit.js --help`.
Машинный каталог: `node tools/kit.js --json`. Каталог содержит назначение, аргументы
и характер изменений каждой команды. `node tools/kit.js skills` возвращает актуальные
описания скиллов без их инструкций; это чтение, а не выбор маршрута или запуск.
Реестр команд находится в kit.js; отдельный список
скриптов агенту собирать не нужно. Прежних путей и совместимых обёрток нет.

### Выбор команды

| Задача | Команда |
|---|---|
| Выполнить одиночную локальную функцию без процесса | action |
| Найти сущности, темы контекста и подключения процесса | entities |
| Получить описания скиллов без тел инструкций | skills |
| Сохранить шаги и результат процесса | run |
| Проверить и допустить версию определения | definition |
| Посмотреть настройки и причины отсутствия подключения | config |
| Безопасно прочитать состояние личной настройки | setup-status |
| Проверить структуру или готовность процесса | check |
| Запустить тесты при разработке | test |
| Установить защиту локального Git при настройке | hooks-install |
| Получить план переноса изменений | promote-plan |

Одиночная локальная утилита вызывается через action. Исполнитель процесса использует entities и run, а check — для предпусковой проверки.
Test не входит в рабочий запуск. Hooks-install меняет локальные hooks Git, run пишет
состояние и результаты; его операция publish добавляет файл для человека из уже
сохранённого артефакта завершённого прогона. Action возвращает результат и при заданном resultFile сохраняет
его в новой папке outputs/. Entities, skills, config, setup-status и check читают данные. Promote-plan не копирует,
не коммитит и не отправляет изменения. Согласия на внешние действия не выводятся
из наличия команды. Инструкция исполнителю находится внутри его SKILL.md.

### Правило расширения

Новую публичную команду добавляй только для самостоятельной технической задачи,
которой ещё нет среди существующих команд. Укажи purpose, usage и scope в kit.js.
Общую реализацию клади в соответствующую группу lib/; её наличие не создаёт новую
публичную команду. Предметную операцию оформляй экшеном, ресурсы сценария — внутри
процесса. Тесты размещай в tests/, общее техническое описание — в этой архитектуре, инструкции сущностей — рядом с ними.

### Проверка Windows

.github/workflows/check.yml запускает полный набор на windows-latest и ubuntu-latest,
Node.js 22 и 24. Запуск автоматический для push/PR, также доступен workflow_dispatch.
CLI-тесты используют каталог с пробелами и кириллицей; проверяются запись результата,
установка hooks и вызов прежнего hook. Проверка имён устройств и Windows-ветки shell
входит в набор. Локальный успех на macOS не заменяет зелёный Windows job для нужного
коммита. На Windows без права создавать файловые symlink пропускается только
соответствующий тест; проверка повреждённого конфига выполняется всегда.
Workflow проверяет опубликованный снимок, не незакоммиченные изменения.


### Внутренние модули

В `tools/lib/` код разделён по ответственности: actions — вызов и поддержка экшенов,
config — настройки, contracts — проверка выходов, core — пути и Markdown,
entities — сущности и снимки зависимостей, runtime — контроллер, запись и история,
integrations — граница вызова из GigaCode,
git — hooks и перенос, validation — структурные проверки. Это реализации команд,
а не дополнительные инструменты для выбора агентом. Каталог команд поддерживает kit.js.

`run next` возвращает фактический следующий шаг; `run execute` вызывает только
объявленное локальное вычисление, без MCP, act и выбора ветки. Вызов execute для
шага агента не меняет состояние запуска: ошибка подсказывает begin и save, а для
уже начатого шага — save. При ошибке вычисления
журнал пытается записать failed. После start исполнитель продолжает до completed
или failed; целостность снимка проверяется перед операциями.

Одиночный локальный transform вызывается через `kit.js action`. Без value возвращается
needs-model с рецептом; повторный вызов с value проверяет результат. Сохранение через
resultFile создаёт новую папку outputs/ с результатом и .action.json: schemaVersion,
action, port, resultName, sha256, mode. Валидатор проверяет контракт и хеш; перезапись
запрещена. Журнал и история процесса для одиночного экшена не создаются.

## Границы приёмки

Автоматическая приёмка проходит во временных копиях без внешних систем. В
tests/processes/publication.selftest.js проверяются создание свидетельств, все исходы
развилок трёх определений и последующий обычный запуск. Helper используется только
этим тестом и разработчиком для выпуска свидетельств; рабочий runtime его не загружает.
Model-выходы при такой приёмке синтетические, помечены как demo и не подтверждают
чтение методики, смысловую классификацию или доступ к Jira. Данные fixture остаются
рядом с процессами, в tests — только код проверки.

Контроллер проверяет у сверки методики полноту разделов, суммы счётчиков и сведения
об источнике; у классификации — состав входных задач, счётчики, выбранные правила,
подключение и пределы чтения. Эти проверки дополняют JSON-контракты и не подменяют
интеллектуальную работу агента.

Сквозной GigaCode-прогон исключён пользователем из текущей приёмки. Проверка другой
моделью в иной среде отмечается отдельно; она не доказывает работу GigaCode. По
доступным локальным старым outputs причин прежних закрытых прогонов установить
нельзя, если отсутствуют их state/trace. Подтверждённые дефекты кода и ограничения
доказательств в таком случае перечисляются отдельно, без выдуманных причин.

В info-povod прежние agentStepGroups и предварительный параллельный запуск будущих
чтений удалены: каждый шаг начинается только после разрешённого begin. Изоляция
объёмного материала допускается для текущего шага, если клиент поддерживает отдельный
контекст. Меняется порядок чтений, а не состав данных или форма отчёта; собственного
планировщика параллельных задач в Process Kit нет.
