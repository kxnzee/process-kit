# RocKit

Рабочая папка для GigaCode: задачу пишешь словами, ассистент подбирает готовый процесс,
выполняет его шаги и кладёт результат в папку запуска вместе с итогом. Свои процессы и
действия добавляются файлами-описаниями — код ядра менять не нужно.

Устройство системы и правила раскладки: [ABOUT.md](ABOUT.md),
[docs/architecture.md](docs/architecture.md), [docs/structure.md](docs/structure.md).

**Вариант переиспользования: FrameWork.** Переиспользуется ядро: 11 служебных
скиллов, единый CLI `tools/kit.js`, правила раскладки и валидатор. Поверх ядра каждая
команда и каждый человек добавляет свои процессы, действия, описания систем, контекст и
настройки — своим именем в своей ветке, не трогая чужие файлы. Подключают не одну
функцию, а способ описывать и воспроизводить повторяемые прогоны, поэтому это не
библиотека, не скрипт и не сниппет.

## Суть решения

Типовой прогон аналитика или разработчика — «собери задачи из Jira, возьми методику из
Confluence, посчитай отклонения, собери отчёт, подготовь письмо» — каждая команда делает
руками и по-своему. Порядок действий живёт у автора в голове и теряется вместе с ним.

RocKit описывает такой прогон один раз и делает его повторяемым:

- **процесс** (`processes/<имя>/PROCESS.md`) — маршрут из шагов; подбирается по имени,
  описанию и примерам, а не по выученной команде;
- **действие** (`actions/<имя>/ACTION.md`) — законченный шаг с контрактом входов и
  выходов; переиспользуется разными процессами, чтение систем, локальный расчёт и
  внешние изменения разделены по классу действия;
- **описание системы** (`adapters/<имя>/ADAPTER.md`) — как говорить с Jira, Confluence,
  Bitbucket или корпоративной адресной книгой;
- **настройки уровня** (`config/master`, `config/team`, `config/my`) — откуда брать
  данные и значения по умолчанию; уровень задаётся веткой, приоритет фиксирован;
- **папка запуска** (`outputs/<ГГГГ-ММ-ДД>_<слова>/`) — `итог.md`, файлы для человека,
  служебные артефакты шагов в `.run/`, журнал прогонов в `.history/`. Прогон можно
  повторить и восстановить постфактум, чем он закончился — видно из файла, а не из памяти
  чата.

## Для кого

- **Менеджер или Delivery** с повторяющимся отчётом или проверкой по Jira, Confluence,
  выгрузкам: оформляет их процессом своего уровня и перестаёт делать вручную.
- **Команда**, которой нужен общий маршрут плюс свои предметные проверки, без спора из-за
  одного общего файла на всех.
- **Аналитик**, которому нужна согласованная проверка (например валидация Change
  Request или отчёт по спецификациям) как обычный шаг работы, а не отдельный скрипт у
  каждого.

Не подходит, если нужна служба с эндпоинтом или библиотека для вызова из чужого кода:
результат прогона — файлы в папке запуска, а не интерфейс.

## Функциональные блоки

Состав указан для этой версии общего уровня. Актуальные каталоги — `node tools/kit.js skills` и `node tools/kit.js processes`.

| Блок | Что внутри | Кто правит |
|---|---|---|
| `.gigacode/skills/rk-*` | 11 служебных скиллов: консультация, настройка, запуск процесса или отдельного действия, диагностика, конструкторы процесса, действия и описания системы, два переноса изменений, установка локальных MCP | только общий уровень |
| `.gigacode/settings.json` | подключения к системам; токен — ссылка вида `$secret:<имя>/<ключ>`, значений доступа в репозитории нет | общий уровень; личный выбор — `config/my/config.json` |
| `processes/<имя>/` | 4 общих процесса и учебный образец `example`; рядом `queries/`, `rules/`, `templates/`, `renderers/`, `fixture.json` | все уровни |
| `actions/<имя>/` | 14 общих действий и образец; данные и контракты шага лежат в папке действия | все уровни |
| `adapters/<имя>/` | 4 описания систем (`jira`, `bitbucket`, `wiki-page`, `mail-contacts`) и образец | общий уровень; команда добавляет свою новую систему |
| `context/<master/team/my>/<тема>/CONTEXT.md` | термины, правила формулировок, предметные уточнения | все уровни |
| `config/<master/team/my>/` | общие безопасные defaults, настройки команды, личный выбор и свои подключения | по уровням |
| `tools/kit.js` | единый CLI: `processes`, `skills`, `definition`, `action`, `entities`, `run`, `config`, `setup-status`, `mcp-check`, `check`, `test`, `hooks-install`, `promote-plan` | только общий уровень |
| `tests/` | наборы самотестов раскладки, контрактов и маршрутов | только общий уровень |
| `docs/`, `about/` | архитектура, раскладка, презентация и примеры результатов | только общий уровень |
| `outputs/`, `.history/` | результаты и журнал прогонов — в git не попадают | не версионируется |

### Зачем это другим командам

Ценность не в четырёх готовых отчётах, а в том, что
повторяемая рутина становится файлом: её рецензируют, переносят между уровнями и
переиспользуют действиями. Команда получает свои отчёты, не форкая чужую кодовую базу и не
ожидая релиза общего уровня, — править нужно только свои файлы. Одинаковый класс
полезности проверяйте на своём кейсе: если прогон описывается двумя-тремя действиями и
одним шаблоном результата, он окупается; если ему нужны новые сетевые интеграции — дороже.

## Быстрый старт

Нужен Node.js 22 или 24 и Git. Клиент GigaCode открывает эту папку как обычный проект.

```bash
git clone https://stash.sigma.sbrf.ru/scm/p4d/pp_ai.git rockit
cd rockit
```

1. Откройте папку `rockit` в GigaCode — CLI, VS Code или приложение. Полный порядок
   установки и подключения проектных доступов — [about/instraction.html](about/instraction.html).
2. Напишите «Как начать?» или «Что ты умеешь?». Агент посмотрит состояние копии,
   покажет примеры задач и подскажет ближайший шаг. Если хотите сразу настроить
   личную копию, напишите «Настрой RocKit» или выберите `/rk-init` в GigaCode CLI.
   Готовую задачу можно поручить сразу, например «Покажи отчёт за неделю».
3. Для пробы попросите: «Покажи демо проверки Change Request без обращения к системам».
   Агент выполнит процесс на демоданных; результат помечается «ДАННЫЕ ДЕМО».
4. Результаты появляются в `outputs/<дата>_<задача>/`; агент даст ссылку на готовый файл.

В GigaCode CLI введите `/`, чтобы выбрать скилл по имени. Например, `/rk-mentor`
открывает знакомство, `/rk-init` — настройку, `/rk-run-process` — запуск процесса,
`/rk-create-process` — создание процесса. Обычная просьба ведёт в тот же скилл.

Для обычного запуска не нужно вручную выполнять предпроверки. Команды для разработки
и проверки определений описаны в [руководстве разработчика](ABOUT.md#проверка-раскладки).

Настройка проекта меняет его папку: локальные значения `git config`, hook в `.git/hooks`,
файл `config/my/config.json` и установленные локальные MCP. Отдельно, после вашего
явного согласия, GigaCode сохраняет подтверждения проектных подключений в своём
пользовательском хранилище. Остальные глобальные настройки не меняются. Токены
добавляются через клиент GigaCode и в чат не запрашиваются.

При обновлении настроенной копии имена проектных MCP-серверов и ссылки на секреты
должны совпадать с `.gigacode/settings.json`: теперь используется префикс `rk-`.
Обновите `mcpServer` в своих выбранных подключениях, сохраните секреты под именами
из актуальных `$secret:`-ссылок через клиент GigaCode и выполните согласованное
подтверждение подключений с перезапуском сессии. Значения секретов в файлы и чат
не переносятся. Доступность новых имён проверяется отдельно; переименование не
доказывает рабочий доступ. Физический адрес Git-репозитория ниже сохраняется.

## Промышленная эксплуатация

В промышленную эксплуатацию решение не выведено и средством вывода в промышленную
эксплуатацию не является. Рассчитано как **личный и командный инструмент**: рабочие прогоны
человека и команды в его же системах, с результатом в файлы.

Команды переиспользуют общие процессы и добавляют свои определения в командных ветках.
Пример результата командного процесса —
[отчёт по SDD](about/examples/team-irbis-sdd-stories-report.html).

## Проверки и качество

```bash
node tools/kit.js test      # наборы самотестов: раскладка, контракты действий, маршруты процессов, уровни владения
node tools/kit.js check     # раскладка открытой ветки
node tools/kit.js check --process <имя>   # предпусковая проверка значений конкретного процесса
```

На запуск самотестов агентом действует [глобальное ограничение](GIGACODE.md#глобальное-ограничение-на-запуск-самотестов).
Самотесты на общем уровне проверяют структуру файлов, точность ссылок
процессов на действия, уровни владения, границы контрактов действий и сохранность артефактов
запуска, используя временные git-репозитории. **Процент покрытия тестами не измеряется**:
инструмента покрытия в поставке нет, наборы запускаются как обычные скрипты Node.js, а
сами проверки проверяют контракты и раскладку, а не строки кода. Пункт остаётся открытым —
если вам важны метрики качества кода, покрытие придётся считать отдельным инструментом
(например c8) и считать заново на своей ветке.

Локальные Bitbucket/email MCP доставляются отдельно через `rk-install-local-mcp`. Проверка файлов и запуска — `node tools/kit.js mcp-check --probe`; готовность доступа подтверждается отдельным чтением выбранного сервиса.

Значения доступов в репозитории не живут: в `.gigacode/settings.json` только ссылка
`$secret:<имя>/<ключ>`, а защита от случайной отправки личной ветки в общий адрес
ставится командой `node tools/kit.js hooks-install`.

## Метки решения

**Метки не заведены** — ни в репозитории, ни в Confluence, ни в M-app. Пункт чек-листа
требует действий: метки имеет смысл ставить там, где решение будет найдено — на страницу
решения в Confluence и в каталоге M-app (в Bitbucket меток репозитория нет как класса).
Предлагаемый набор для обсуждения: `gigacode`, `процессы`, `скиллы`, `ИИ-агент`,
`отчётность`, `валидация`.

## Открытые пункты и ограничения

- Чтение репозитория по адресу банка выдаётся по запросу — массового переиспользования без
  обращения к контрибьюторам не получается.
- В промышленную эксплуатацию не выведено; счёт — личные и командные прогоны.
- Покрытие тестами в процентах отсутствует.
- Метки и канал общения не заведены.
- Локальный почтовый MCP доставляется отдельно; процессы готовят черновики и ссылки на письма, отправку человек выполняет сам.
- Демонстрационные прогоны строятся на вымышленных данных и помечаются соответствующе.
