# Process Kit

Process Kit — рабочая папка для GigaCode: ассистент берёт задачу, написанную словами, находит
подходящий процесс из готовых шагов и выполняет его. Готовые шаги — это процессы, действия
и описания систем; вы добавляете свои, не трогая чужие.

Устройство системы описано в [архитектуре](docs/ARCHITECTURE.md).

## Установка

1. Склонируйте репозиторий:
   ```bash
   git clone <адрес репозитория> process-kit
   ```
2. Откройте папку `process-kit` в GigaCode (CLI, VS Code или приложение) — как обычный
   проект.
3. Напишите задачу обычными словами: «покажи отчёт за неделю», «что ты умеешь».

Дальнейшую настройку ведёт ассистент. Для первой сетевой задачи он уточнит недостающее:
какая вы команда, где вести личные процессы, в каком проекте Jira ваши задачи. Перед
началом он покажет план и дождётся вашего «да», после каждого шага скажет, что сделано, и
положит отчёт о настройке в папку `outputs/` (полный путь ассистент назовёт в чате).
Глобальные настройки компьютера он не меняет: только эту папку.

## Как работать в этой папке

Пишите агенту обычными словами. Команды и устройство репозитория знать не обязательно.

| Что нужно | Что написать |
|---|---|
| Познакомиться с возможностями | «Покажи, какие задачи здесь можно решать» |
| Получить краткий инструктаж | «Объясни, как работать с этой папкой» |
| Выполнить задачу | Опишите нужный результат, источник данных и период, если он важен |
| Попробовать без реальных систем | «Есть ли демо этой задачи на вымышленных данных?» |
| Собрать свой сценарий | «Хочу регулярно получать такой результат…» и опишите его |
| Разобраться с ошибкой | «Не получилось» или «В этом результате неверно…» |
| Понять ход выполнения | «Объясни, как получился этот результат» |

В ответе о возможностях агент показывает блок «Готовые процессы»: читает определения
процессов в вашей копии и кратко объясняет, какой результат даёт каждый доступный
общий, командный или личный процесс. Это актуальный список из файлов, а не заранее
заданный набор названий. Учебные, устаревшие и чужие процессы не перечисляются.

Агент уточняет недостающее и ведёт
настройку, только когда она нужна. Личная копия хранит ваши материалы; команда даёт
доступ к общим материалам команды. Работать без команды тоже можно. Наличие настройки
не гарантирует доступа к внешней системе — агент проверяет нужное для конкретной задачи.

Перед внешним изменением агент показывает, что собирается сделать, и получает согласие.
В демо используются вымышленные данные без обращения к системам. Готовый результат
и полный путь к нему агент показывает в чате; файлы находятся в `outputs/`.

При сбое агент сам фиксирует остановку и разбирает её. Если вы заметили неверный
результат, опишите расхождение; при нескольких результатах агент уточнит нужный.
Самостоятельно собирать журнал или вызывать диагностику не требуется. Если нужна
помощь разработчика, агент предложит отдельный диагностический файл без переписки,
URL и содержимого запросов. Вы решаете, передавать ли его; автоматически он не отправляется.

Все результаты работы лежат в папке `outputs/` в корне проекта — **одна папка на один
запуск**:

```
outputs/
├── 2026-10-29_настройка/           настройка: что-сделано.md
├── 2026-10-29_сводка-просрочки/    задача: итог.md и файлы для человека
│   └── .run/                       служебные файлы прогона: журнал, шаги, состояние
└── 2026-10-29_проба-сводки/        пробный прогон на вымышленных данных
```

- имя папки — дата и короткое имя задачи через дефис, без пробелов; повторный запуск
  получает `-2`, `-3`, прежняя папка не перезаписывается;
- `итог.md` есть в каждой папке запуска: что сделано, чем закончилось, откуда данные;
- в `.run/` лежат служебные файлы прогона, человеку они не нужны;
- прямо в `outputs/` файлов нет — только папки запусков;
- журнал всех прогонов — в `.history/`; `outputs/` и `.history/` в git не попадают.

Доступы к подключённым системам (Jira, Bitbucket) добавляются в самом GigaCode — в CLI и в
десктопном приложении одинаково; токенов в чате ассистент не спрашивает, и присланный не
использует. Токены хранятся в настройках GigaCode, в файлах лежит только ссылка на них вида
`$secret:pp-ai-jira/x-jira-token`. После добавления доступа перезапустите программу.

Новый сценарий перед обычным запуском проходит проверку структуры и пробные маршруты.
Помощник выполняет эти проверки сам; изменение сценария требует повторной проверки.
Если выполнение прервалось при внешнем изменении, помощник сначала выясняет его
результат в системе, чтобы не отправить сообщение или не создать задачу повторно.

Почтового подключения в поставке нет: письмо готовится только как черновик.
Локальное редактирование текста и демо не требуют подключения к системам.

## Обновление

Общая часть приходит тегом, командная — веткой команды. Обычные команды git:

```bash
git fetch --tags origin
git merge v0.2.0                 # версия общей части
git merge origin/team-<команда>  # изменения команды (если вы в её ветке)
```

Свои файлы названы по-своему (`my-…`), что уменьшает конфликты имён. Но обновление
может изменить общие зависимости; перед слиянием просмотрите изменения. Git покажет
конфликты, если они возникнут, и решение
(оставить оба куска, свой, чужой) принимаете вы. После слияния запустите
`node tools/kit.js check` — он скажет, если раскладка разъехалась.

Нужен ли перезапуск клиента после обновления — см. заметку в конце этого раздела.
Если вы добавили новый файл в `.gigacode/skills/`, клиент может подхватить команду «/»
только после перезапуска сессии: наведите «/» и посмотрите, видно ли имя. Если нет —
перезапустите клиент.

## Где хранить личную ветку

Ветка `my` — ваша: изменения видны только вам.

- **локально** (по умолчанию) — ничего делать не нужно, ветка живёт только на вашем
  компьютере. При переустановке её нужно сохранить или перенести (`git bundle` / копия
  папки);
- **в форке** общего репозитория — если хотите работать с нескольких машин или сделать
  PR с личной правкой;
- **в своём репозитории** — если у вас есть отдельный репозиторий для личных изменений.

Личную ветку не отправляйте в общий репозиторий команды: она ваша, а не общая.

## Что нельзя

- держать токены в файлах проекта: доступы добавляются в настройках GigaCode и в
  репозиторий не попадают;
- отправлять ветку `my` в общий репозиторий (`git push origin my`);
- править чужие файлы (без префикса `my-` или префикса команды) — свои изменения
  делайте своим файлом с префиксом;
- писать адреса, проекты и имена людей в общую часть — они живут в конфиге и в файлах
  команды.

Защита от случайной отправки личной ветки:

```bash
git branch --unset-upstream                  # ветка my не связана с удалённой
git config branch.my.pushRemote no_push      # git push откажется отправлять my
```

Для установки pre-commit (секреты в индексе) и pre-push с сохранением прежних hooks выполните
`node tools/kit.js hooks-install`. Исходный скрипт — `.gigacode/hooks/pre-push`,
в `.git/hooks/pre-push` устанавливается вызывающая его обёртка. В общий адрес
защита не пропускает:

- отправку `my` — понятным текстом «Личную копию нельзя отправить в общий репозиторий»;
- служебные заметки (`refs/notes/*`);
- перезапись истории без fast-forward; hook проверяет изменения ссылок, а не
  наличие флага --force, который Git ему не передаёт;
- удаление веток (`git push <адрес> --delete <ветка>`).

Отправка своей ветки и отправка в собственный репозиторий остаются разрешёнными.
Защиту ставит `pp-ai-init`; файлы в .git/hooks не версионируются.
Серверные ограничения веток дополняют hook: его можно обойти через --no-verify.
Отправляйте только конкретную ветку: `git push <адрес> <ветка>`.

# Для разработчика

Репозиторий один, уровни — ветки. Клиент GigaCode про уровни ничего не знает: он читает
ту папку, которую открыли.

| Уровень | Ветка | Кто правит | Префикс файлов |
|---|---|---|---|
| общий | `master` | разработчик набора | без префикса; способности — `pp-ai-` |
| командный | `team-<команда>`, ответвление от `master` | команда, через PR и ревью | `team-<команда>-` |
| личный | `my`, ответвление от командной ветки или от `master` | сам человек | `my-` |

Стабильные версии общей части — теги `vX.Y.Z` на `master`.

## Основная ветка

В скиллах имя основной ветки не пишется руками: агент берёт ветку, на которой человек
оказался сразу после клонирования (`origin/HEAD`), иначе `master`. Отдельной настройки
нет: правки общего уровня идут с ветки `master-<имя>` через PR, и до слияния человек
остаётся в своей ветке — это нормальное состояние, уровень у неё общий.

## Режимы скиллов

Агент выбирает подходящий skill по name/description, затем читает полную инструкцию.
Mentor нужен для знакомства и консультации; остальные способности применяются напрямую.
Понятная задача не требует обязательного инструктажа или настройки всех систем.
Для управляемой работы приоритетен подходящий опубликованный процесс. Обычные разовые
операции, включая разрешённую правку файла, не обязаны становиться процессом.
Продолжения, короткие ответы, изменения и отмены учитываются в контексте исходной цели.


Правила общения, согласий и продолжения поручений находятся в GIGACODE.md.
Технические подробности допустимы по запросу и когда нужны для решения. План и результат
объясняются понятным языком; обязательного перечня запрещённых слов нет.

## Что меняет настройка на компьютере

Только открытую папку:

- в `.git/config` этой папки — при необходимости `branch.my.pushRemote` и
  `user.name`/`user.email`, если их нет и человек явно сообщил свои значения;
- `.git/hooks/pre-push` в этой папке;
- ветки внутри этого репозитория; командные настройки в `config/team/config.json` и личные в `config/my/config.json`.

В git могут появляться записи без описания (refs/notes/ai). Это служебные заметки
GigaCode. Они ни на что не влияют и не отправляются в общий репозиторий.

Глобальные настройки не меняются: ни `~/.gitconfig`, ни `~/.gigacode/`, ни глобальные
hooks (`core.hooksPath`), ни credential helper, ни профиль оболочки. `git config`
используется только без `--global` и `--system`.

Настройки разделены на master/team/my: [поля и приоритет](config/team/README.md).

## Ручная настройка (что делает `pp-ai-init`)

Клонирование, открытие папки — минимум; дальше обычно всё делает помощник. Вручную те же
шаги:

```bash
git fetch origin

# обновить/собрать конфиг подключений в командной ветке
git checkout team-<команда>
cp config/team/EXAMPLE.json config/team/config.json    # только в рабочей ветке команды, если файла нет

# личная ветка
git checkout -b my --no-track origin/team-<команда>      # или последний тег origin/master
git branch --unset-upstream
git config branch.my.pushRemote no_push
node tools/kit.js hooks-install
```

Доступы к системам в репозитории не живут: токены хранятся в настройках GigaCode, в файлах
лежит только ссылка на них вида `$secret:pp-ai-jira/x-jira-token`; значение добавляется в
настройках самого GigaCode — в CLI и в десктопном приложении одинаково; после перезапуска
сессии сервер работает. Проверка в настройке — «сервер объявлен в сессии и ответил на одно
чтение», без чтения значений. Имя секрета и ключ для фразы человеку берутся из ссылки в
`.gigacode/settings.json`, а не выдумываются.

Все команды выше действуют только на эту папку: `git config` — без `--global` и
`--system`, hook — в `.git/hooks` этого репозитория.

`validate.js` берёт уровень из имени текущей ветки: `master` и `master-<имя>` —
общий, `team-<команда>` — командный, `my` — личный, `promote/master/<тема>` — общий,
`promote/team-<команда>/<тема>` — командный. Команда для рабочей ветки команды берётся
из настроек master/team/my через tools/lib/config/config.js или из
`--team <код>`. Ветка, которая не называет команду и не определена в настройках master/team/my, —
предупреждение: префиксы файлов уровня в ней не проверены, и это сказано в отчёте.


## Правило имён

Пути ниже показывают примеры именования, а не список существующих сущностей.

- Общие файлы — без префикса. Отчётный процесс (последний шаг — `compose-report`) — с
  постфиксом `-report`: `processes/sdd-stories-report/PROCESS.md`. Демоданные лежат рядом:
  `processes/sdd-stories-report/fixture.json`.
- Общий экшен получает специфические данные процесса явно. Для run-query процесс
  передаёт `queryFile: processes/<имя>/queries/<запрос>.md` и объект `parameters`.
  Общие правила функции остаются в её папке; контракт не зависит от имени процесса.
- Общие способности — десять `pp-ai-*`: Mentor, Init, Run Process, Run Action,
  Create Process, Create Action, Create Adapter, Diagnose и два переноса изменений.
  Фактические name/description/пути: `node tools/kit.js skills`.
- Командные — с префиксом команды, то есть именем ветки целиком: в ветке `team-sws` это
  `processes/team-sws-weekly-report/PROCESS.md`, `context/team/domain/CONTEXT.md`,
  `actions/team-sws-jira-search/ACTION.md`.
- Личные — с префиксом `my-`: `processes/my-standup/PROCESS.md`, `context/my/preferences/CONTEXT.md`.
- Подпапок по уровням нет. У каждой сущности своя папка; общий, командный и личный
  варианты процессов, экшенов и адаптеров отличаются префиксом имени папки. Для контекста используются context/master, context/team и context/my без префиксов тем. Скиллы — строго плоско: `.gigacode/skills/<имя>/SKILL.md` (вложенные скиллы
  клиент не видит).
- Чужие файлы не правятся, а дополняются своими. Если общий файл всё же изменён, конфликт
  при обновлении решает тот, кто правил.

## Создание сущностей

Перед созданием прочитай инструкцию соответствующей сущности: [процесс](processes/example/README.md), [экшен](actions/example/README.md), [адаптер](adapters/example/README.md), [контекст](context/README.md), [настройки](config/team/README.md). В каждом — поля, шаблон и проверка. [Результаты и состояние запуска](docs/ARCHITECTURE.md) создаются штатными утилитами.

`pp-ai-create-action` определяет границы нового экшена и после согласования создаёт
его файлы. Применяется по просьбе создать экшен или при сборке процесса,
когда имеющихся экшенов недостаточно. Правила находятся целиком в его SKILL.md.

`pp-ai-create-adapter` создаёт описание технического доступа к системе: реальные
операции, схемы ответов, пагинацию и ограничения. Настройка подключения и проверка
живой системы учитываются отдельно; порядок целиком находится в SKILL.md.

## Что куда класть

| Папка | Что | Уровни |
|---|---|---|
| `.gigacode/skills/pp-ai-*` | десять обнаруживаемых способностей; процедуры у владельцев, общие правила в GIGACODE.md | только `master` |
| `processes/` | процессы: шапка (`name`, `title`, `description`, `example`, `entry`, `params`) и шаги-ссылки | все |
| `actions/<имя>/` | действия: `ACTION.md` + `queries/`, `templates/`, `rules/` | все |
| `adapters/` | как говорить с системой | `master`; команда — только новую систему |
| `context/*/CONTEXT.md` | термины, командные и личные правила | все |
| `config/team/EXAMPLE.json` | шаблон адресов проектов с `TODO` | только `master` |
| `config/master/` | общие безопасные defaults | общий уровень |
| `config/team/config.json` | команда и общие подключения/ресурсы | team-* и наследующая my |
| `config/my/config.json` | выбранная команда, собственные подключения и личные defaults | только my |
| `outputs/` | результаты запусков: одна папка на запуск, в ней `итог.md` и `.run/` | не версионируется |
| `.history/` | журнал прогонов `runs.jsonl` и кэш | не версионируется |
| `tools/` | рабочие утилиты и валидатор; запуск проверок — `node tools/kit.js test` | только `master` |
| `tests/` | тестовый код по сущностям; проверки SDD — в `processes/sdd-stories-report/` внутри tests | только `master` |

Процесс, действие и данные действия **не** являются скиллами: новый шаг не создаёт новый
скилл. Скилл уровня (`team-<команда>-*` или `my-*`) — исключение, только когда нужна отдельная
команда «/», которую нельзя выразить процессом.

## PR через `master-*`

```bash
git checkout -b master-<короткое-имя> --no-track origin/master
# правки
node tools/kit.js check
git commit -am "кратко: что и зачем"
git push -u origin master-<короткое-имя>
```

Дальше — PR в `master`. В рабочем контуре владелец должен запретить прямой push в `master` правилом ветки. Командная ветка
принимает PR по тому же принципу.

## Выпуск тега

```bash
git checkout master && git pull
git tag -a v0.2.0 -m "v0.2.0: что изменилось"
git push origin v0.2.0
```

## Создание командной ветки

```bash
git checkout master && git pull
git checkout -b team-<команда> --no-track origin/master
mkdir -p context
```

## Проверка раскладки

```bash
node tools/kit.js test               # основные проверки архитектуры и контрактов
node tools/kit.js check                # раскладка и структура файлов открытой ветки
node tools/kit.js check --json         # тот же отчёт машинным форматом
node tools/kit.js check --team sws     # рабочая ветка команды: команда не в имени ветки
node tools/kit.js check --process sdd-stories-report     # предпусковая проверка значений
```

`validate.js` проверяет только структуру: где лежит файл, как он называется, из чего
состоит его шапка, на что он ссылается, что лежит в папке запуска. Язык, формулировки и
жаргон он не оценивает — это задача агента по `context/master/writing-style/CONTEXT.md`.

Отчёт в два уровня: `E` — ошибка, из-за неё код выхода 1; `W` — предупреждение, на код
выхода не влияет. Отдельные проверки: `--only <сущность>` — одна группа (имена групп даёт
`--json` в поле `entity`, полный список — в `RULES` внизу `validate.js`); `--root <папка>` —
другой корень, нужен самопроверке.

Режим `--process <имя>` — предпусковая проверка значений: он смотрит только те поля
настроек через `tools/lib/config/config.js`, на которые ссылаются шаги названного процесса, их действия и данные
действий, и говорит, что из этого не заполнено. Поля, к которым процесс не обращается, не
проверяются — незаполненное второе подключение не блокирует работающий первый процесс.
Без имени процесса режим не запускается: «проверить все поля сразу» для предпусковой
проверки не годится. Полный прогон этого правила не выполняет.
Самопроверки в `tests/` сгруппированы по папкам корня и проверяют маршруты
и зависимости процессов, границы уровней, входы и выходы действий, вложенные процессы
и сохранность артефактов. Запуск: `node tools/kit.js test` (Node.js 18+ и Git, включая Windows).
Проверки используют временные Git-репозитории. На Windows для проверки прежних hooks
используется shell из Git for Windows.

Что проверяется механически: новый скилл без префикса вне `pp-ai-*`, действие, оформленное
как скилл (или файл действия вместо папки), неправильный `kind`, процесс со ссылкой на
несуществующее действие, подпроцесс, шаг или `entry`, нарушение уровня владения, отсутствие входного файла сущности, реальные team/my-настройки в общей ветке, отсутствующее подключение, на
которое ссылаются настройки команды, значение доступа в `.gigacode/settings.json` вместо
ссылки `$secret:<имя>/<ключ>` и токен открытым текстом в любом файле проекта.

Папки запусков он тоже проверяет, чтобы ошибку раскладки ловил скрипт, а не человек:

- файл прямо в `outputs/` — ошибка, там только папки запусков;
- имя папки с пробелами или без даты — ошибка;
- артефакт шага (`02-compose-report.md` и подобные) в корне папки запуска — ошибка:
  шаг пишет его в `.run/`, в корень попадает только результат последнего шага;
- в папке запуска нет файла для человека, кроме `итог.md` (его не скопировали из `.run/`) —
  ошибка;
- `итог.md` упоминает служебную подпапку — ошибка; файл рядом не перечислен — предупреждение;
- `outputs/` или `.history/` попали в git — ошибка.

После обычного запуска пользователь получает итог и готовые файлы. Агент использует
контракт экшена и явно переданный шаблон процесса, проверяет факты текущего шага; запускать
тесты репозитория для каждой рабочей задачи не нужно. Полные проверки — для разработки,
диагностики и переноса изменений.

## Настройка Bitbucket

Выполняет администратор репозитория (или владелец проекта). Порядок:

1. **Branching model** (Repository settings → Branching model): задать префиксы рабочих
   веток `master-` и `team-`. Development — `master`, Production — `master`.
2. **Branch permissions** на `master`:
   - `Branch permissions` → Add: `Prevent all changes` для всех, разрешить только через
     `Pull request` (`Merge via pull request`);
   - `Prevent deletion` и `Prevent rewriting history` (запрет force push) включены.
3. **Branch permissions** на `team-*`: те же три запрета. Обязательные одобрения
   (`Required approvals`) — по желанию команды.
4. **Форки** (Repository settings → Fork permissions или настройка проекта): уточнить, к
   проекту или к репозиторию привязано разрешение, и можно ли из форка открыть PR. Если
   форки разрешены — PR из форка возможен в тот репозиторий, куда он форкнут (`team-*` или
   `master`); правило PR при этом действует.
5. Проверить результат: обычным push в `master` и в `team-*` — должен быть отказ.

## Перезапуск клиента

После обновления файлов текущей ветки новый **процесс** или **действие** подхватывается
сразу: их читает исполнитель по имени, клиент их не регистрирует. Новый **скилл** в
`.gigacode/skills/` регистрирует сам клиент, поэтому проверяйте: наберите «/» и посмотрите,
виден ли новый скилл. Не виден — перезапустите клиент (VS Code — перезагрузить окно,
приложение — переоткрыть папку, CLI — заново запустить `gigacode`).

SDD-процесс связывает run-query, read-code-evidence, evaluate-data, compose-report и
необязательный prepare-mail-draft. Запросы, расчёт, контракт оценки и шаблон принадлежат
процессу и передаются общим функциям явно. Черновик письма не отправляется.
[Контракт](processes/sdd-stories-report/reference.md), [структура](docs/STRUCTURE.md).

Для разрешения зависимостей процесса: `node tools/kit.js entities <имя> local` (либо
режим demo/live; последний необязательный аргумент — JSON-файл параметров).
Requires объявляет целые сущности: actions/processes по именам, context/config по
уровням master/team/my. Команда возвращает точки входа, каталоги тем и подключения;
внутренние файлы вручную перечислять не нужно.

Публичные команды доступны через `node tools/kit.js --help`, машинный каталог —
`node tools/kit.js --json`. Внутренние модули tools/lib/ не являются отдельными
инструментами для выбора агентом. [Команды и устройство CLI](docs/ARCHITECTURE.md).

Одиночный локальный экшен можно вызвать через `node tools/kit.js action <spec.json>`
без создания процесса. Для выполнения процесса после start доступны карточки
`run next` и штатные локальные вычисления `run execute`; они не заменяют решения
агента и не вызывают MCP. Структурированные отчёты могут использовать rendererFile
с проверкой фактов в папке процесса.

Для разработчика: [ручная приёмка в GigaCode](docs/GIGACODE-ACCEPTANCE.md) — создание,
выполнение, восстановление и границы проверяемого подтверждения.

## Каталог и границы автоматизации

`node tools/kit.js processes` возвращает метаданные доступных определений, scope,
complete и issues. При неизвестной рабочей ветке область можно явно выбрать через
--level master|team|my, для team также --team <код> с проверкой настроек.
Учебные, устаревшие и черновые записи отличаются от рабочих опубликованных.
Published означает актуальность имеющегося свидетельства, не доступ к системе:
полную готовность проверяет start. Неполный каталог не доказывает отсутствия процесса.
Перечисление не обращается к системам и не исполняет код определений.

`node tools/kit.js definition inspect <spec.json>` с `{"process":"<имя>"}` читает
факты даже о частичном определении без исполнения его JS и без записи файлов.
Необязательные level/team выбирают ту же область, что и каталог. Inspect сообщает
статические зависимости, проблемы владения и актуальность имеющегося свидетельства;
полноту динамических зависимостей и готовность запуска он не доказывает.
`definition status` сохранён для совместимости: выполняет глубокую проверку,
может загружать код определения (branchRule) и отклоняет неполные определения.
Для безопасного просмотра применяй inspect. [Контракт ответа](docs/ARCHITECTURE.md).

«Создай черновик» допускает неполное определение с ограничениями; обычное «создай процесс»
ориентировано на готовое опубликованное. Локальный допуск не равен коммиту, push,
рабочему запуску или внешнему эффекту. Если проверочный маршрут требует защищённого
act или продолжения user-ветки, без доверенной интеграции публикация может остановиться
после validate: definitionTest не отключает verifyApproval/verifyEffect. Тестовый хост
не заменяет реальное согласие. Подробнее — docs/ARCHITECTURE.md.

Interaction Routing — правила поведения агента, не принудительный классификатор.
Полноценная проверка discovery, Event/Intent и композиции в GigaCode остаётся в бэклоге.
После потери чата создание восстанавливается по файлам с обозначением неизвестного;
исполнение Run — по Controller. Отмена не гарантирует прерывания инструмента или отката эффекта.

При обновлении: прежние pp-ai-dispatch и pp-ai-guide удалены; знакомство включено в Mentor,
другие способности выбираются напрямую. Уже начатый запуск связан с хешами кода и может
не продолжиться после обновления. Завершите его заранее или сохраните совместимую копию;
не меняйте журнал вручную и не повторяйте действие с неизвестным исходом.
