# Исполнитель

Вход: задача либо process=<имя>, параметры и режим; при продолжении — точный output.
Возврат: outcome=success/failed/draft, output, пути результата и итог.md, фактические
внешние изменения и ограничения. Draft означает черновик, а не отправленное письмо.
Вопрос о требованиях не разрешает запуск или запись.

## Когда читать методики

- До первого вызова CLI прочитай [cli-spec.md](references/cli-spec.md): подготовка
  временного spec, поля команд, режимы, параметры и имена результатов.
- Если нужны отдельный агент, восстановление после его ошибки или продолжение после
  прерывания, прочитай [delegation-and-recovery.md](references/delegation-and-recovery.md).
- При изменении, отмене или неоднозначной связи сообщения с поручением прочитай
  [interaction.md](../../references/interaction.md).

## Выбрать процесс или продолжить Run

Для status/продолжения используй известный output через next; при прерванной записи
или lock — recover. Не ищи другой процесс и не вызывай новый start ради ответа о ходе.
Явно отменённое или заменённое поручение возобновляй только по новому решению человека.

Для нового запуска:

1. Вызови `node tools/kit.js processes`. Учитывай scope, complete и issues: код 0
   не гарантирует полноту. --level/--team выбирай только по известной области.
2. Сопоставь результат, входы, режим, предметную область и разрешённые действия.
   Прочитай существенные условия определения: сходства имени недостаточно.
   При равных вариантах уточни одно существенное различие.
3. Для автоматического подбора исключи educational, устаревшие и неопубликованные
   записи. Явный учебный example допустим с обычными проверками. Явно названное
   недоступное/устаревшее/неопубликованное определение не подменяй другим: объясни препятствие.
4. Подходящий опубликованный Process имеет приоритет, когда сохраняет смысл задачи
   и разрешённые действия. Обязательность задают поручение, регламент или политика.
   Иной маршрут/контракт требует отдельной адаптации и публикации.
5. Если подходящего нет, верни факты и ограничения поиска общему агенту по GIGACODE.md.
   Неполный каталог не доказывает отсутствия. Не собирай ручную цепочку Tools/Actions.

## Подготовить и начать

1. Уточни только недостающие входы. Определи local/live/demo и точный источник данных.
   Для «последнего результата» выбери предыдущий output до start; при неоднозначности спроси.
   В demo используй только выбранный dataFile, без сети и без готовых expected-ответов.
2. Передай подтверждённые явные аргументы в params/explicitParams. Не вычисляй вручную
   defaults, приоритеты, хеши и стек: это делает Controller. Дата данных не является
   датой запуска; date указывай только по явному требованию к дате самого Run.
3. Вызови `node tools/kit.js run start <spec.json>`. Это обязательный публичный допуск:
   он проверяет владение, публикацию, параметры и готовность до первого действия.
   Не вызывай внутренние экспорты tools/lib из собственного Node-скрипта.
   check/entities — глубокие инструменты разработки, не обязательный обход перед start.
4. Если start отклонён, действие не начинай. Недостающие постоянные настройки передай
   Init с исходной целью и продолжи после устранения препятствия; параметры одного
   запуска уточни сам. Не подменяй отсутствующий ресурс соседним и не меняй инструменты.
   Если папка не создана, так и сообщи; не выдумывай output.
5. Сохрани возвращённые output, outputDir, summaryFile и state.params. Читай нужные
   entities/readFiles и выбранные topics, а не весь files-снимок. В live используй
   возвращённые connections с adapterFile/mcpServer/settings; не выбирай подключение
   по списку серверов. До обращения к системе проверь доступность нужного MCP-инструмента.
   Transform не требует сети; environment-tool не доказывает наличия инструмента среды.

Отсутствие подключения — препятствие готовности выбранного процесса, а не основание
подменять его. Не включай definitionTest и не меняй publication ради рабочего запуска.

## Выполнять по карточке

После start вызывай `node tools/kit.js run next <spec.json>` с {"output":"<output>"}.
Выполняй только возвращённую операцию, затем снова next. Карточка и pending.params
определяют текущий узел, в том числе внутри подпроцесса; маршрут не вычисляется по памяти.

| Карточка | Действие |
|---|---|
| execute | Передай spec в run execute. Локальная функция сама делает begin/save; предварительный begin не нужен. MCP и act так не выполняются. |
| begin | Вызови run begin с данным spec, сохрани pending.id и карточку save. Для source/transform затем next → model. Для act после проверенного approval выполни один вызов по pending.params, затем next → reconcile для сверки и save с проверенным effect. До успешного begin рецепт не выполняется. |
| model | Попытка уже начата. Выполни ACTION.md и вызови save с возвращёнными полями, текущим attemptId и фактическим content. Повторного begin нет. |
| choose | Отдельный run choose, затем next. Для code — единственная цель; для model — объявленный target и непустой decision. Семантическое суждение проверяет агент. |
| approval-required | Это ожидание, не внешнее действие. Передай approvalRequest доверенному хосту. С проверенным receipt вызови begin по spec карточки, добавив approval, затем следуй строке begin. При verificationAvailable=false сообщи блокировку. |
| reconcile | Не повторяй act. Доверенный хост сверяет effectRequest текущего attemptId; applied разрешает save, not-applied — retry, unknown оставляет pending. |
| enter / leave | Выполни указанную операцию по spec. End ребёнка не завершает родителя. |
| finish | Сохрани главный файл через finish; затем требуемые дополнительные артефакты — через publish. |
| done | Проверь status. Только completed означает техническое завершение; failed не разрешает следующий шаг. |

Для act нужен проверенный approval до begin и verifyEffect=applied для save.
Текст «да», confirmed=true, status/reference от агента и тестовый хост не заменяют receipt.
Если работа после begin act прервалась или исход не подтверждён, next/recover вернут
reconcile: неизвестный исход запрещает повтор. После единственного разрешённого вызова
также получи next → reconcile: только эта карточка содержит effectRequest для сверки.
Save требует проверенного receipt доверенного хоста, а не заявления исполнителя об успехе.
Retry требует verified not-applied, затем новый begin — новое approval. Если система
поддерживает идемпотентность, используй pending.id как ключ этой же попытки.
Продолжение user-развилки требует проверенного approval и непустого decision;
без verifyApproval разрешён только end корневого процесса, не end подпроцесса.
Begin/enter/execute/finish/leave не выбирают ветку вместо choose.

Если шаг отмечен в agentSteps, используй отдельный контекст только при поддержке клиента
и по методике делегирования. В одном Run пишет один исполнитель; будущий шаг начинается
после save предыдущего. Передавай полученную карточку save, не восстанавливай поля по памяти.

## Ошибка, отмена и восстановление

При прерванной записи или lock вызови recover; locks и журнал вручную не меняй.
После recover продолжай по карточке того же output/attemptId. Если save ещё pending,
повтори save с тем же content, а не само внешнее действие. Другой физический результат
не подставляй. Сохранённый шаг не выполняй заново после ошибки отдельного агента.

Известный окончательный сбой фиксируй fail с безопасной причиной и проверь failed.
Для pending act это возможно только с verified not-applied; неизвестный эффект оставь
для reconcile. Если execute сам зафиксировал failed, не вызывай следующий шаг.
Вызов execute для шага без локального вычисления сохраняет состояние: следуй подсказке
begin/save. Если целостность нарушена и fail отклонён, сохрани файлы и сообщи, что остановка
не записана. Не обещай выполнить позже то, что разрешённая карточка позволяет завершить сейчас.

Отмена прекращает новые действия в названной области; прерывание вызова и откат не
гарантируются. Не создавай run cancel или разговорные статусы в журнале. Параметры,
снимок и артефакты после start не переписывай. Новый Run при изменённых входах возможен
только после разбора уже выполненных действий; он не разрешает повтор неизвестного эффекта.

При сбое или жалобе примени pp-ai-diagnose с точным output и безопасными фактами.
Не вызывай fail для completed и не запускай процесс повторно ради объяснения результата.
Пользователь не должен выполнять fail/diagnose или собирать журнал. Обычное исполнение
не разрешает править tools/tests, запускать selftest или писать собственный renderer.

## Завершить поручение

Finish копирует последний артефакт побайтно, создаёт итог.md и запись истории. Не дописывай
JSONL или историю вторым вызовом. Пути бери из ответа, итог.md находится рядом с .run/.
При нескольких файлах сверь раздел «Что сохранить» определения; главный — finish,
остальные — publish после него. Ошибку истории сообщи отдельно, не удаляя готовый файл.

Проверь содержание результата по задаче: период, факты, полнота, форма, критерий «коротко».
Примеры задают форму и не предоставляют фактические значения. Техническое completed не
доказывает правильность бизнес-результата. В ответе — краткий итог, фактическая отправка
или её отсутствие, ограничения и «Результат: <полный путь>/итог.md».
После ответа или устранения препятствия продолжай исходное действующее поручение
без повторного согласия; завершение вспомогательного Skill не завершает всю задачу.
