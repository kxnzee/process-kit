# Настройка установки

Вход — открытая папка проекта (только что склонированная или уже настроенная) и, если
настройка вызвана из задачи, — сама задача человека, к которой нужно вернуться. Выход —
папка, в которой помощник может сразу выполнять задачу, короткий отчёт человеку и файл
«что-сделано.md».

Модель и правила — в `GIGACODE.md` проекта. Что важно для настройки:

- **основная ветка** нигде не пишется руками: ветка после клонирования (`origin/HEAD`) →
  `master`; отдельной настройки для неё нет;
- личный уровень человека — ветка `my`; командный — `team-<команда>`; свежий клон
  (основная ветка) — нормальное начальное состояние, с которого начинается настройка;
- в git уходят только `config/sources.json` и файлы `my-*`; `.gigacode/settings.json`
  не добавляется никогда;
- **только открытая папка:** настройки git пишутся без ключей глобального и системного
  уровня, `pre-push` — в `.git/hooks` этой папки, домашний каталог с настройками git и
  клиента не трогается;
- ничего не перезаписывать: существующие значения, ветки и настройки остаются как есть.

**Как говорить.** По-русски, с первой фразы. Человеку — только слова процесса, действия,
подключения, контекста и команды. Не произносить и не показывать: ветка, master, team-,
префикс, скилл, конфиг, sources.json, адаптер, фикстура, MCP, PR, слияние, коммит, имена
файлов, команды «/», а также имена команд git. Вместо «переключаю ветку» — «создаю вашу
личную копию», вместо «config/sources.json» — «настройки подключений»; вместо
«координаты» — «адрес проекта, где брать данные».

## Шаг 0. План и согласие

Все вопросы настройки собираются **до** плана и задаются **один раз**. Если человек уже
назвал команду или другой ответ раньше (в задаче или в первом сообщении) — не спрашивать
это снова, использовать ответ. Перед каждым вопросом проверить, нет ли ответа уже
в разговоре.

Если человеку не показывали план в этой настройке — показать его дословно и дождаться
«да» (подставь только варианты, где они нужны):

> Сначала настрою Process Kit. Что сделаю:
> 1) узнаю вашу команду;
> 2) сделаю вам личную копию для ваших процессов в этой папке;
> 3) спрошу, где хранить ваши процессы: только на этом компьютере или ещё в вашем
>    репозитории;
> 4) спрошу проект в Jira, если команда его ещё не указала;
> 5) проверю доступ к Jira.
> Что изменится на компьютере: в этой папке появится ваша личная копия и сохранятся
> настройки команды. В Jira и других системах ничего не изменю.
> Начинаю настройку?

На «нет» — ничего не менять (никаких команд и файлов), сказать, что настройку можно
провести позже, и вернуть управление помощнику. Создание новой команды с отправкой в общий
репозиторий согласуется отдельным «да» на шаге 2.

Настройка — только настройка: процессы для задачи человека здесь не ищутся, не читаются и
не собираются. Сборку процесса вызывает помощник отдельно и только после своего
предложения.

## Шаг 1. Где мы

1. Корень проекта — открытая папка (`GIGACODE.md`, `processes/`). Нет — сказать, что
   открыта не та папка, и остановиться.
2. **Незакоммиченные изменения** — `git status --porcelain`. Правки только в файлах с
   префиксом `my-` не мешают. Любая другая правка (общий процесс, действие, чужой файл
   команды) — **остановиться**: ничего не менять, не переключать ветку, не отправлять.
   Сказать человеку простыми словами: «В папке есть несохранённые изменения в общих
   файлах — боюсь их потерять при переключении. Сохраните их или скажите, что с ними
   делать.»
3. `git branch --show-current`:
   - `my` — личная копия уже есть, сразу к шагу 4;
   - `master-<имя>` — незавершённые правки общего уровня: сказать человеку одной фразой
     «В папке сейчас недоделанная правка общих файлов — сначала её нужно закончить или
     отдать на проверку. Скажите, когда будет готово, и я продолжу.», остановиться и
     ничего не менять. Личная копия создаётся только с чистой ветки;
   - `master` и `team-<команда>` — нормальное начальное состояние: если локальная ветка
     `my` уже есть (`git rev-parse --verify my`) — она принадлежит другой основе, поэтому
     копировать её на текущую ветку нельзя молча: спросить одним вопросом «У вас уже есть
     личные файлы от прошлой настройки — перенести их на текущую версию?» и по «да» —
     `git switch my`, `git merge --no-ff origin/HEAD` (`origin/team-<код>` для команды),
     разрешить конфликты только в сторону личных файлов (`my-*`) и вернуться на
     основание; по «нет» — оставить старую `my` как есть и сказать, что позже можно
     спросить снова. Ветки `my` нет — шаг 2;
   - другое имя — спросить, какого уровня эта ветка, и ничего не менять.

   Ветку `my` создаёт настройка в шаге 3, поэтому её отсутствие в свежем клоне —
   норма.

## Шаг 2. Команда

1. `git fetch origin` — сказать одной строкой: «Сейчас скачаю сведения о командах
   Process Kit, ваши файлы это не изменит.» Нет сети — сказать одной фразой и работать
   с тем, что есть локально.
2. Собрать `origin/team-*` (`git for-each-ref --format='%(refname:short)' refs/remotes/origin/ | grep '^origin/team-'`).
   Название каждой команды — из `TEAM.md` этой ветки (`git show origin/team-<x>:TEAM.md`,
   первая строка с названием); файла нет — из имени ветки (код латиницей перевести в
   название словами).
3. Если `processkit.team` уже задан и такая ветка есть — не спрашивать, идти к шагу 3.
4. Иначе спросить: «В какой команде вы работаете?» Варианты:
   - команды по названиям (имена веток человеку не показывать, только названия);
   - «моей команды нет — создать»;
   - «без команды».
5. **Создать команду.** Спросить название команды (одно-два слова) и кто её владельцы.
   Код — короткая латиница (`sws`, `sales`). Ветка создаётся **без привязки** к основной,
   строго в таком порядке:
   ```
   git switch -c team-<код> --no-track origin/master
   # создать TEAM.md и config/sources.json из шаблона
   git add TEAM.md config/sources.json
   git commit -m "Новая команда: <название>"
   ```
   Нужны `user.name`/`user.email` для коммита — не задавать их глобально: спросить человека
   и задать для этой папки, или сказать, что их нужно задать.

   Затем сказать человеку дословно: «Сейчас создам команду <название> в общем репозитории,
   чтобы ею могли пользоваться коллеги. Создать?» и дождаться «да». Только после «да»:
   ```
   git push -u origin team-<код>
   ```
   - **Отправка прошла** — проверить `git branch -vv`: у `team-<код>` должно быть
     `[origin/team-<код>]`. Сказать человеку: «Команда создана. Попросите администратора
     добавить владельцев команды проверяющими.» Запомнить
     `git config --local processkit.team team-<код>`.
   - **Отправка отклонена** (нет прав) — не обходить (никаких форков, других адресов,
     force push). Вернуть рабочую копию в исходное состояние:
     ```
     git switch origin/master          # обратно на основную ветку
     git branch -D team-<код>          # -D: ветка не слита с основной, -d откажется
     ```
     Подготовить `$ROOT/outputs/<ГГГГ-ММ-ДД>_заявка-команда-<код>/заявка.md`: название,
     код, владельцы, просьба создать ветку `team-<код>` и добавить владельцев
     проверяющими.
     Сказать человеку: «Прав на создание команды нет. Заявка: <полный путь к заявка.md>.
     Пока настрою без команды.» Дальше — как «без команды»: команда
     не остаётся на компьютере и не привязывается к основной ветке.
6. Запомнить выбор: `git config --local processkit.team team-<код>` или
   `git config --local processkit.team none`. Без `--local` значение уйдёт в глобальную
   настройку и в этой папке его не будет: проверка раскладки читает `.git/config`.

## Шаг 3. Личная копия

1. Основание: `origin/team-<код>`, если команда выбрана; иначе последний тег на основной
   ветке, а если тегов нет — сама основная ветка. Основная ветка — та, на которой человек
   оказался после клонирования: в команде git это `origin/HEAD`, если он не разрешается —
   `master`; её имя ни разу не произносится человеку и не пишется в файлы `my-*`.
2. `git switch -c my --no-track <основание>` (`origin/team-<код>`, если команда выбрана;
   последний тег основной ветки, если без команды). Ветка `my` уже есть — переключиться
   на неё, а не создавать заново. Привязку к удалённой ветке не создавать: сразу после
   создания `git branch --unset-upstream my 2>/dev/null || true`. Строку о результате
   сказать после пункта 3, когда выбран способ хранения: «Готово: личная копия создана,
   она хранится только на этом компьютере.» (или «… она хранится в вашем репозитории.»).
3. Спросить одной фразой: «Ваши личные процессы хранить только на этом компьютере или
   ещё в вашем репозитории?» По умолчанию — **только на компьютере**.
   - **Только на компьютере:** `git branch --unset-upstream my` (если upstream есть),
     `git config branch.my.pushRemote no_push` и установить `pre-push`.
   - **В своём репозитории:** спросить адрес, `git remote add mine <адрес>`,
     `git config branch.my.pushRemote mine`; `pre-push` ставится так же и запрещает
     отправку `my` в `origin` (в `mine` — разрешает).
   Установка `pre-push` одинаковая: если `.git/hooks/pre-push` нет — скопировать
   `.gigacode/hooks/pre-push`; если есть — не затирать: сохранить текущий файл рядом
   (`pre-push.before-process-kit`) и дописать в начало рабочего файла строку вызова
   сохранённой копии, чтобы прежний hook продолжал работать.

   Что делает `pre-push`: в общем репозитории отклоняет отправку `my` (текстом «Личную
   копию нельзя отправить в общий репозиторий»), служебные заметки (`refs/notes/*`),
   принудительную перезапись (`--force`, `--force-with-lease`, `--mirror`, `+refs/…`) и
   удаление веток; обычную отправку своей ветки и отправку в свой репозиторий разрешает.
   Отправка — только конкретной ветки (`git push <адрес> <ветка>`).

   После установки проверить hook: `node tools/check-prepush.js` — он прогоняет hook на
   наборе случаев и ничего не отправляет. Проверка не прошла — сказать человеку одной
   фразой и не считать защиту установленной.

## Шаг 4. Подключения (адреса проектов, где брать данные)

1. `config/sources.json` есть (пришёл из командного уровня или из прошлой настройки) —
   подтверждённые значения в нём **не перезаписывать**. Значения `TODO`, пустые строки и
   `TODO` в массивах подтверждёнными не считаются: их спросить по пунктам 3–4 и вписать
   только названное. Спрашивать нечего — перейти к шагу 5.
2. Нет — скопировать `config/sources.template.json` в `config/sources.json`.
3. Найти значения `TODO` (поля `TODO`/пустые строки/`TODO` в массивах) и спрашивать их
   **языком задачи**, по одному вопросу на значение, не больше трёх за раз. Пример:
   «В каком проекте Jira ваша команда ведёт задачи?», «Как называется доска вашей
   команды?». Текущее значение показывать как вариант по умолчанию; вариант «не знаю,
   оставьте» допустим всегда.
4. Вписывать только то, что человек назвал. Остальные `TODO` оставлять `TODO` и
   упомянуть в отчёте. Адреса проектов не выдумывать ни по соседним полям, ни по примерам
   из описаний систем. Типы задач и статусы конкретной инсталляции подтверждаются живым
   чтением (шаг 5), а не догадкой: до подтверждения они остаются открытыми.
5. КЭ команды (modules): КЭ, которые относятся к этой команде. Спросить
   прямо и не привязывать к отчётам: «Какие КЭ относятся к вашей команде? Назовите их так,
   как вы их называете между собой, и назовите код.» КЭ команды нужны не только отчётам,
   поэтому вопрос про отбор не задавать. На каждый КЭ попросить код вида CI00000000;
   название нужно только человеку и в отчёты не выводится — не знает, оставить TODO, а
   код вписать. Коды не придумывать. Нет КЭ — оставить пустой список и сказать одной
   строкой, что отбора по КЭ не будет.

## Шаг 5. Доступы

Доступами заведует клиент GigaCode (CLI, VS Code, десктопное приложение): человек
добавляет секрет штатным способом, а в `.gigacode/settings.json` лежит только ссылка на
него вида `$secret:<имя>/<ключ>`; клиент подставляет значение по ссылке, и после
перезапуска программы сервер работает. Файла доступов в проекте нет — не создавать
его, не просить заполнить, не придумывать альтернативный файл и не править
`settings.json` самому.

1. Прочитать `.gigacode/settings.json`: какие `mcpServers` объявлены. Для каждого сервера
   запомнить имя секрета и ключ из ссылки `$secret:<имя>/<ключ>` в его заголовках —
   только чтобы назвать их человеку в фразах ниже. Ссылку **не править** и ошибкой не
   считать: значение подставляет клиент. Имя секрета и ключ не выдумывать.
2. Для каждого подключения из `sources.json` взять его `mcpServer` и сверить с серверами,
   **объявленными в сессии**. Инструмент не появился — `tool_search` по
   `select:mcp__<сервер>__<capability-инструмент>`; после загрузки его нет — сервера нет.
3. **Сервер объявлен и проверочное чтение прошло** (одно чтение: например, доступные
   проекты или одна задача по известному ключу) — подключение готово, сказать «Jira
   подключена» / «Bitbucket подключён» по названию из `displayName`.
4. Причина отказа — из двух случаев, каждый своей фразой:
   - **секрет не добавлен** (сервер не объявлен в сессии или не отвечает из-за отсутствия
     значения): «Нет доступа к Jira. Добавьте в настройках GigaCode секрет <имя> с ключом
     <ключ> и перезапустите GigaCode.»
   - **секрет есть, но система отказала**: «Доступ к Jira не подошёл или устарел. Обновите
     токен в настройках GigaCode (секрет <имя>, ключ <ключ>) и перезапустите GigaCode.»
     Вторая фраза — только когда система ответила отказом (в инструментах Jira и
     Confluence — «401 Unauthorized» или «403 Forbidden», в Bitbucket — «401» или
     «403» в ответе на проверочное чтение). Нет сети, таймаут, ошибка 5xx, сервер не
     объявлен — это первый случай, а не второй.

   Имя системы и слова «секрет <имя> с ключом <ключ>» подставляются из ссылки в
   `settings.json` для этой системы. Не писать «истёк токен», если доступ не добавлялся.
5. **Токен в чате.** Токен не просить. Если человек прислал его сам — не использовать, не
   сохранять, не вставлять в файлы и не проверять им ничего; ответить первой фразой из
   пункта 4 ещё раз: «Нет доступа к Jira. Добавьте в настройках GigaCode секрет <имя> с
   ключом <ключ> и перезапустите GigaCode.»
6. Значения, стоящие в настройках и в окружении, не читать, не печатать и не сравнивать —
   только факт «сервер работает / не работает» и причина: секрет не добавлен или система
   отказала.

## Шаг 6. Самопроверка

Проверить механически, по файлам, рабочую копию ветки: запустить проверку и разобрать
её вывод.

1. Есть `tools/validate.js` — выполнить `node tools/validate.js`. Скрипт проверяет
   раскладку и структуру: где лежит файл, как он назван, из чего состоит шапка, на что
   он ссылается, что находится в папках запусков. Строки `E` — ошибки (код выхода 1),
   `W` — предупреждения. У каждой строки указаны файл и номер строки.
2. Нет `tools/validate.js` (старая установка) — сделать ту же проверку глазами: у каждого
   шага процесса действие (или подпроцесс) существует, `entry` совпадает с шагом, данные
   действия лежат в его папке; и сказать человеку, что проверка раскладки в его копии
   старая.
3. Что означают ошибки, с которыми чаще всего приходит человек:
   - у шага процесса действие (или подпроцесс) не существует, `entry` не совпадает с
     шагом, `следующий`/`goto` ведёт на несуществующий шаг;
   - данные действия (`queries/`, `templates/`, `rules/`) не найдены;
   - у действия неверный `kind` или его папка оформлена как скилл;
   - подключение `adapters/<система>.md` для записи из настроек команды не найдено;
   - «значения»: значение в настройках подключений, на которое ссылается процесс, не
     заполнено. Эта проверка запускается только с именем процесса
     (`node tools/validate.js --process <имя>`) — полный прогон её не делает: иначе
     незаполненное второе подключение мешало бы первому работающему процессу;
   - файл лежит без префикса своего уровня или в подпапке.

   Для процессов по умолчанию (`defaults.process`) и для тех, с которыми человек работает,
   стоит запустить и проверку значений: она называет, какого именно значения не хватает.
4. Что ошибкой **не** является и что чинить при настройке не нужно: язык, формулировки
   и стиль текстов — их оценивает не скрипт; предупреждения `W` настройку не блокируют.

Ошибки — исправлять только в своих файлах (префикс `my-`); чужие назвать человеку и
не править. Сломанное называть простыми словами: **название процесса и шаг** и что
именно не так, без имён файлов проекта.

## Шаг 7. Сохранить

Перед коммитом — `git status --porcelain`. В коммит добавлять только
`config/sources.json` и файлы, имя которых начинается с `my-`:

```
git add config/sources.json          # только если этот файл меняла настройка
git add $(git status --porcelain | awk '$1 ~ /^(\?\?|A|M|AM|MM)$/ {print $2}' | grep -E '(^|/)my-[^/]+$')
git commit -m "Настройка Process Kit"     # если есть что коммитить
```

Если в изменениях есть другие файлы `processes/*`, `actions/*` или любые чужие файлы —
**не добавлять** их и не удалять, а записать в отчёт: чьи они и что с ними делать.

`.gigacode/settings.json` не добавлять никогда. Общие и командные файлы не коммитить.
Отправка личной ветки — только в адрес своего репозитория и только если человек его выбрал.

После коммита: отчёт для человека и файл «что-сделано.md» — шаг 8 — и одна строка
«Настройка готова» помощнику, чтобы он вернулся к задаче человека.

## Шаг 8. Отчёт и «что сделано»

1. Файл `$ROOT/outputs/<ГГГГ-ММ-ДД>_настройка/что-сделано.md` — простыми словами, по
   шагам: что узнал, что создал на компьютере, что спросил и что вписал, какие системы
   подключены и какие ждут доступа, что осталось сделать и как, нужен ли перезапуск
   программы. В нём — что запускалось и что изменено (свои слова: «создана личная копия»,
   «сохранены настройки подключений»), без команд и имён файлов проекта.
   Настройки команды описывать по факту одного из трёх: «настройки подключений созданы»,
   «настройки подключений дополнены: спросил N открытых значений, M остались открытыми»,
   «настройки подключений уже заполнены, не менял». Открытые значения перечислять словами
   человека («проект в Jira», «доска»), а не полем настройки.
   Подпапки `.run/` в этой папке нет: настройка — не прогон процесса. Создавать папку
   настройки с `mkdir -p` и класть в неё только этот файл: других файлов и подпапок в
   `$ROOT/outputs/<ГГГГ-ММ-ДД>_настройка/` быть не должно.
2. В чат — до 8 строк, без запрещённых слов и без имён файлов:
   - команда (или «без команды»);
   - какие системы подключены, какие ждут доступа;
   - что осталось сделать — одной строкой на пункт, действием человека;
   - нужен ли перезапуск программы и почему;
   - «Отчёт о настройке: <полный путь к что-сделано.md>».
3. Вернуть управление помощнику: настройка закончилась, **исходная задача человека
   выполняется дальше**, без повторного вопроса «что вы хотели». Одна строка для
   человека: «Настройка готова. Теперь вернусь к вашей задаче: <задача человека>» — и
   управление помощнику. Если настройку проводил сам человек, без задачи, этой строки нет.

## Чего настройщик не делает

- не ищет и не читает процессы ради задачи человека, не вызывает конструктор процессов:
  настройка — отдельный этап, сборка процесса начинается только после отдельного «да»
  человека на предложение помощника;
- не опрашивает системы сверх одного проверочного чтения и не запускает процессы;
- не перезаписывает существующие настройки, ветки и готовые значения;
- не правит общие и командные файлы, не правит глобальные настройки git и клиента: ни
  домашний файл настроек git, ни домашний каталог настроек клиента — эти места только
  читаются;
- не задаёт глобальные настройки git, не включает глобальные hooks: всё пишется только в
  открытую папку;
- не просит и не принимает токены в чате, не выводит значения из файла с доступами;
- не обходит отказ отправки в общий репозиторий и не отправляет личную ветку в общий
  адрес;
- не предлагает человеку вызвать себя: настройку запускает помощник.
