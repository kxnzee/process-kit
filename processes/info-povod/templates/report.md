# Форма отчёта «Инфо-поводы Release Notes»

Форму собирает `renderers/report.js` из `report-data`; этот файл описывает её для человека и
для шага сборки. Текст отчёта — один Markdown: он же файл прогона. Вторая форма —
`renderers/report-html.js`, одностраничник шага `render-html`: он
собирается из текста того же markdown-рендера и содержимого не меняет. Различается только
оболочка, и таблица в ней повторяет текстовую форму: две колонки окон,
имя ИТ-услуги жирной первой строкой каждой ячейки, КЭ строкой ниже, релиз жирной ссылкой, задачи
строками с «•». Переносы `<br>` становятся абзацами, ссылки markdown становятся ссылками, а строка
счётчиков «Бизнес задач…» — карточками. Разделы те же и в том же порядке; `vertical-align` в
markdown-форме по-прежнему не делается.

## Порядок разделов

1. Заголовок `# Инфо-поводы`; при демо первой строкой — **ДАННЫЕ ДЕМО**.
2. Три строки условия прогона: дата прогона и оба окна (окна — в формате `дд.мм-дд.мм`),
   сколько релизов отдано каждой инсталляцией задач (`Релизы: <метка> — релизов <число>`)
   и сколько строк таблицы остались без инфоповода — только подписи-причины: `только
   технические`, `пустой состав`, `состав прочитан не полностью`.
3. Отдельным абзацем — три числа состава: `Бизнес задач` (всё показанное в таблице, то есть
   содержательные вместе с задачами без класса), `Технических задач` и `из них без класса`.
   Третье число входит в первое: первые два складываются в число классифицированных задач,
   три числа подряд — не три независимые категории. Число релизов, учётных пар «релиз × КЭ»
   и КЭ в отчёте в шапке не печатаются:
   релизы видны в таблице, а смысл пары «релиз × КЭ» объясняет раздел «Оговорки прогона».
   Все эти счётчики остаются в данных расчёта (`counters`) и в журнале прогона.
4. Одна таблица двух колонок — как в сценарии Release Notes:

   | Текущие инфоповоды | Планы на следующую неделю |
   |---|---|

   Строка таблицы — ИТ-услуга релиза: имя печатается одинаковой строкой в обеих колонках и
   берётся дословно из значения поля «ИТ-услуга» задачи; если поля нет, строка — КЭ релиза.
   Внутри ячейки, по каждому релизу окна (релиз выводится ровно один раз, даже если у него
   несколько КЭ):
   - строка `КЭ: <имена через ;>` — все КЭ этого релиза дословно из поля «КЭ» (вида
     `SBP.IRBIS.Открытые данные(3296913)`), по ним читатель сверяется с реестром;
   - жирная строка релиза: `[<ключ> «<название релиза>» — <статус> — Внедрение дд.мм](<ссылка>)`
     или `[<ключ> «<название релиза>» — <статус> — плановая дата ПРОМ дд.мм](<ссылка>)`
     (плановая дата впереди даты прогона); название берётся дословно из заголовка задачи
     релиза — без него ключ ничего не сообщает, а подписи «Нет инфоповодов…» и
     «Технический релиз…» читаются именно по нему;
   - ниже маркированные строки содержательных задач: `[<ключ>](<ссылка>) — <заголовок> — <описание>`;
   - вместо списка — одна строка основания, и у трёх случаев они разные:
     `Нет релиза этой ИТ-услуги в окне` (у услуги нет релиза в этом окне),
     `Нет инфоповодов: в релизе нет связанных задач` (релиз есть, состав прочитан и пуст),
     `Технический релиз: <ключи ссылками>` (задачи есть, все технические — каждый ключ даёт
     ссылку на задачу в Jira), либо
     `Состав релиза прочитан не полностью — см. раздел «Проверить не удалось»`;
   - задача без класса остаётся в списке обычной строкой: её ключ и заголовок, без пометок —
     сама задача названа в разделе «Вопросы».
5. `## Вопросы` — список того, что решает человек. У строки короткая подпись причины (одно из
   четырёх): `правило против чтения задачи`, `опора только на слабый признак`,
   `смысл задачи не установлен`, `нет плановой даты внедрения`. Каждая строка самодостаточна:
   `[<ключ задачи>](<ссылка>) «<формулировка задачи>» (релиз [<ключ релиза>](<ссылка>))` — дальше
   подпись причины, что известно (чего не хватило в тексте задачи), затем `Что нужно решить:` и
   сам вопрос. Задача с вопросом остаётся в таблице строкой своего релиза и остаётся в счётчике
   своего класса: вопрос про уверенность в классе, а не про то, учтена ли задача. Пустой
   раздел — «нет записей».
6. `## Проверить не удалось` — объекты, где чтение оборвалось: это «не проверено», а не «нет».
7. `## Оговорки прогона` — окно шире буквы сценария, демо-условие, отсутствие ссылки,
   совпадение ключей в двух инсталляциях, пустое поле «ИТ-услуга».
8. `## Как читать этот отчёт` — шесть коротких строк о смысле пометок.

Исключённые объекты отдельным разделом не печатаются и в сводку не попадают: дата вне окон,
тип задачи `Bug` и КЭ вне периметра учитываются только в данных расчёта (`excluded`,
`counters.excludedCount`) — без них нельзя проверить знаменатель.

## Ограничения формы

- `|` в тексте заменяется на `/`, переводы строк внутри ячейки — `<br>`: иначе таблица
  разъезжается в терминале и на странице отчёта.
- Пустая выборка даёт одну строку `Нет релизов в окнах` в обеих колонках — отчёт без строки был
  бы неотличим от сбоя сборки.
- Имя ИТ-услуги и имя КЭ не сокращаются и не переформулируются: по КЭ читатель сверяется с реестром.
- Пустое поле «ИТ-услуга» не порождает отдельную строку: релиз без услуги группируется по своему КЭ,
  пустота поля попадает в оговорки.
- Ссылки — только на задачи из выбранных подключений, собранные по
  `taskStores[].issueUrlTemplate`; адресов связанных систем в отчёте нет.
- Html-форма собирается из текста этой формы и сверяется собственной проверкой байт в байт: блок,
  которого она не знает, выходит абзацем и остаётся видимым — молча потерять строку она не может.
  Новый блок или новая подпись в markdown-форме требует случая разбора в `renderers/report-html.js`
  и строки проверки в `tests/processes/info-povod/html-form.selftest.js`.
