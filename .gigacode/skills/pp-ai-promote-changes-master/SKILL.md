# Перенос изменений в общую ветку

Вход — открытая папка и просьба человека перенести правку в основную ветку набора (всё или
выборочно). Выход — ветка с перенесёнными файлами и запрос на изменения в основную ветку,
либо честный отказ с причиной. Модель и правила уровней — в `GIGACODE.md` проекта; здесь
только порядок действий.

**Что этот скилл не делает:** не правит содержимое файлов, не сливает запросы на изменения,
не переносит в командную ветку (это `pp-ai-promote-changes-team`), не переносит координаты
подключений и файлы команд, не трогает чужие файлы.

**Как говорить.** По-русски, с первой фразы. Человеку — слова изменения, общего уровня,
запроса на изменения. Не произносить: ветка, master, team-, префикс, скилл, конфиг,
sources.json, адаптер, MCP, PR, коммит, имена файлов, команды «/». Вместо «ветка master» —
«общий уровень набора», вместо «git push» — «отправлю в хранилище», вместо «PR» — «запрос
на изменения».

## Шаг 0. План и согласие

Показать короткую карточку и дождаться «да»:

> Я соберу наработки в вашей папке, разделю их по уровням и покажу список. Дальше вы
> скажете — переносить всё подходящее или только выбранное. Изменения уйдут в общий уровень
> набора, то есть станут видны всем командам, — поэтому запрос на изменения отправлю только
> после отдельного «да». В вашей папке я ничего не изменю.

## Шаг 1. Где мы и что менялось

1. Открытая папка — корень проекта.
2. Основная ветка определяется по правилу из `GIGACODE.md`: ветка после клонирования
   (`origin/HEAD`), иначе `master`. Имя основной ветки руками не пишется.
3. Список изменённого: `git status --porcelain` — новые и изменённые файлы открытой папки
   плюс коммиты текущей ветки, которых нет в основной ветке
   (`git log --oneline origin/<основная>..HEAD`). Ничего нет — сказать «переносить нечего».
4. `git fetch origin` — нужен свежий вид основной ветки. Сеть недоступна — остановиться и
   сказать об этом.

## Шаг 2. Отнести каждый файл к уровню

Уровень определяется **именем и местом**, а не намерением человека. Порядок проверки,
первый подошедший признак решает:

1. **Общий уровень** — это и есть цель переноса: `GIGACODE.md`, `README.md`,
   `ARCHITECTURE.md`, `tools/*`, `config/sources.template.json`, `.gigacode/settings.json`,
   `.gigacode/hooks/*`, `.gigacode/skills/pp-ai-*/`, а также `processes/`, `actions/`,
   `adapters/`, `context/`, `tests/<имя>/` — **без префикса уровня**.
2. **Командный уровень** — файл с префиксом `<команда>-` (имя команды — из `TEAM.md`, а
   если его нет — любое имя, совпадающее с именем командной ветки `team-<команда>`),
   `config/sources.json`, `TEAM.md`. В общую ветку **не переносится никогда**.
3. **Личный уровень** — файл с префиксом `my-`. Не переносится никогда.
4. **Нераспознанное** — имя без префикса в месте, где префикс ожидается, файл в неожиданном
   каталоге, служебные каталоги агента (`runs/`, `.gigacode/worktrees/`), локальные файлы
   редактора. В выбор не попадает; человеку — одной строкой, что и почему.

Файлы, подпавшие под пункты 2–4, в список выбора не попадают вовсе: правка общего уровня не
должна тянуть за собой чужое. Если изменений в общем уровне нет — сказать, что переносить
наверх нечего, и назвать, если что-то принадлежит другому уровню.

**Отдельная проверка до показа списка:** если в общий уровень попал файл, который по
правилам в нём не живёт, — `config/sources.json` (координаты), `TEAM.md`, любой файл с
префиксом команды или `my-`, — такой файл из переноса исключается и называется человеку
причиной. Это и есть ошибка раскладки, из-за которой правка потом «не доезжает» до нужного
уровня.

## Шаг 3. Показать и спросить: всё или выбранное

Показать список простыми словами — что это и что изменится для остальных команд:

```
Перенесу в общий уровень набора (увидят все команды):
  1. правила набора
  2. служебный скилл конструктора — правило «ссылка вместо значения из настроек»
  3. скрипт проверки раскладки
Не перенесу (чужой уровень):
  - настройки подключений вашей команды
  - отчёт по спецификациям — это уровень команды
Не перенесу (сломает общий уровень):
  - процесс отчёта ссылается на действие вашей команды — сначала его нужен общий вариант
  - в описании процесса названа ваша система
```

Спросить одним вопросом: «Перенести всё из списка или только часть? Назовите номера».
Всё — берётся весь список общего уровня; часть — только названные. Ничего не выбрано —
закончить без переноса. Раздел «сломает общий уровень» — не выбор, а объяснение: такие файлы
в перенос не попадают, пока ошибка не исправлена (проверка шага 6a).

## Шаг 4. Завести рабочую ветку

1. Имя ветки: `promote/master/<краткая тема>`; сегмент `master` задаёт уровень назначения;
   тема — из сути изменений, две-четыре латинские части через дефис, например
   `promote/master/sdd-stories-report`. Ветка с таким именем уже есть — уточнить у
   человека.
2. Ветку завести **от основной ветки после обновления**, а не от текущей рабочей копии:
   - `git fetch origin`;
   - `git branch -f <ветка> origin/<основная>`;
   - работать с ней только через отдельный рабочий каталог (`git worktree`): открытая
     папка и её текущая ветка не переключаются ни при каком раскладе.
3. Рабочий каталог держать **вне открытой папки** — во временном каталоге машины:
   `git worktree add /tmp/<имя> <ветка>`. Клиентский файловый страж не пускает запись
   наружу — запасной путь внутри открытой папки: `.gigacode/worktrees/<имя>` (служебный
   каталог, в перенос не попадает). Черновая ветка живёт только пока идёт перенос.
4. После отправки убрать за собой: `git worktree remove /tmp/<имя>`, затем
   `git branch -d <ветка>` — ни временных каталогов, ни черновых веток после себя
   не остаётся. Перенос не отправлен — спросить человека, убирать рабочее место или
   оставить до следующего шага.
5. Несохранённые изменения открытой папки не переключать и не прятать (`stash`).

## Шаг 5. Перенести выбранные файлы

1. Скопировать в ветку только выбранные файлы — те же пути, то же содержимое.
2. Проверить состав ветки на то, чего в общем уровне быть не должно:
   - нет `config/sources.json`;
   - нет `TEAM.md`;
   - нет файлов с префиксом команды и с префиксом `my-`;
   - нет каталога прогонов и рабочих каталогов агента.
   Нашлось — убрать из ветки и сказать человеку, что именно и почему.
3. Сообщение об изменении — одной строкой: что перенесено и зачем.
4. Открытая папка и текущая ветка человека не переключаются.

## Шаг 6. Проверить

1. Прогнать `node tools/validate.js` **в ветке переноса** (прежнее имя `node tools/check-layout.js`
   принимает те же аргументы): уровень она узнаёт из имени
   рабочего места (`promote/master/…`). Ошибки — остановка; это особенно важно здесь:
   правка общих файлов расходится по всем командам сразу.
2. Проверить ссылки: общий файл не должен ссылаться на имя, которое есть только в
   командной или личной ветке. Нашлось — ошибка раскладки: такой файл в общий уровень не
   идёт, о нём говорится человеку отдельной строкой.
3. Для правки служебного скилла — проверить, что в нём нет команд, меняющих настройки
   всего компьютера: раскладка проверяет это сама, но ошибку надо назвать до отправки.

## Шаг 6a. Проверить переносимые процессы и действия на уровневость

Проверка раскладки этого не видит: она смотрит наличие файлов и разрешимость имён, а не
**чей** уровень упомянут в содержимом. Поэтому до показа итога пройти каждый переносимый
файл из `processes/` и `actions/` и проверить два условия.

**Условие 1. Нет упоминаний командного и личного.**

| Что искать | Где | Почему ошибка |
|---|---|---|
| имя команды из `TEAM.md` (и варианты написания в верхнем, нижнем регистре) | `processes/<имя>.md`, `actions/<имя>/ACTION.md`, его `queries/`, `templates/`, `rules/` | общий файл не должен знать о конкретной команде |
| префикс уровня в ссылках: `<команда>-…`, `my-…` | поля `query:`, `template:`, `rule:`, `процесс:`, `действие:` | имя с префиксом в общей ветке не разрешается — это ошибка раскладки |
| названия систем, команд и проектов словами (например, проект и хранилище команды в параметрах шага) | `description`, `title`, `example`, `params`, таблицы данных | общий файл должен быть без координат организации |
| пути и значения, живущие только в командной ветке: `config/sources.json` **как место значения**, `TEAM.md` | параметры шагов, `params` процесса | на координаты ссылаются путём (`defaults.taskStore`), а не пересказывают их |

**Как искать.** Словарь собирается до просмотра файлов, из открытой папки: имя команды и
его варианты — из `TEAM.md`; проекты, названия хранилищ и подключений — из координат
подключений (`config/sources.json`); термины — из контекстных файлов команды
(`context/<команда>-*.md`). Каждое слово ищется во всех переносимых файлах, без учёта
регистра, по всему тексту — включая шапку (`title`, `description`, `example`), `params` и
таблицы параметров. Имя команды и имя её проекта — разные слова: поиск по одному имени
команды проект пропускает. Нашлось — файл переносить нельзя, место и слово называются
человеку.

Ссылка на файл данных с префиксом команды (`query: <команда>-sdd-stories`) — **всегда ошибка**,
даже если такой файл есть рядом в ветке переноса: в общую ветку он не поедет, и ссылка
повиснет. Такой файл либо не переносится вовсе (он командный), либо переносится вместе с
общим файлом данных под общим именем — решает человек, но по умолчанию переносится только
сам процесс, а ссылка должна указывать на общее имя.

**Условие 1а. Имя переносимого файла — без префикса уровня.**

Проверяется каждое имя, которое попадает в общую ветку, — и сам файл, и папка действия:

| Что проверять | Правильно | Ошибка |
|---|---|---|
| процесс | `processes/sdd-stories-report.md` | `processes/<команда>-sdd-stories.md`, `processes/my-stories.md` |
| действие | `actions/run-query/ACTION.md` | `actions/<команда>-run-query/ACTION.md`, `actions/my-query/…` |
| данные действия | `queries/sdd-stories-report.md`, `templates/sdd-stories-report.md` | `queries/<команда>-sdd-stories.md`, `templates/my-report.md` |
| адаптер, контекст, вымышленная выборка | `adapters/jira.md`, `context/common.md`, `tests/<имя>/fixture.json` | те же имена с `<команда>-` или `my-` |

1. Разрешены только буквы, цифры, точка, дефис и подчёркивание; имя начинается с буквы или
   цифры. Пробелов, кириллицы и заглавных в общем уровне не бывает.
2. Префикс команды и `my-` в имени — **ошибка**: такое имя либо принадлежит другому уровню и
   в общую ветку не идёт, либо его надо перенести под правильным именем. Переименование
   делается **человеком** в открытой папке: скилл содержимое и имена не меняет.
3. Переименование — повод проверить ссылки повторно: после смены имени все `query:`,
   `template:`, `rule:`, `процесс:`, `действие:` обязаны указывать на новое имя. Старое имя,
   оставшееся в ссылке, — ошибка раскладки.
4. Исключение по имени — `config/sources.json`: имя фиксированное, но в общую ветку этот
   файл не переносится вовсе (координаты живут в командной ветке).

Проверять имя до переноса, а не после: файл с префиксом, попавший в общую ветку, начинает
выглядеть как командный и путает уже саму рассортировку по уровням.

**Условие 2. Ссылки процесса ведут только на общее.**

1. Каждый шаг процесса вида «действие:» ссылается на действие, которое **есть в общей
   ветке** (`origin/<основная>`), а не только в открытой папке. Действие, добавленное в
   командной ветке, в общий процесс не годится: его там нет.
2. Данные действия (`query:`, `template:`, `rule:`) существуют в общей ветке по пути
   `actions/<действие>/<папка>/<имя>.md` и **не имеют префикса уровня**.
3. Обратного наклона быть не должно: ни процесс, ни действие в общем уровне не ссылаются на
   процесс, действие или данные, которых нет в общей ветке и которые лежат в командной или
   личной ветке.

Проверять именно по составу **общей ветки после обновления**, а не по открытой папке: в
открытой папке командные файлы видны, и ошибка маскируется — ровно так правка однажды
«доехала» до чужого уровня, а нужного не достигла.

**Что делать при находке:**

- ссылка на командное действие или данные → файл **не переносится целиком**; человеку
  называется строка и причина;
- упоминание команды в тексте → файл не переносится целиком, потому что переписывать
  содержимое этому скиллу запрещено: назвать место и предложить поправить в файле, а
  перенос повторить;
- ошибка найдена только в одном из нескольких переносимых файлов → остальные можно
  перенести, если человек выберет их; оставить молча не перенесённое нельзя.

Та же проверка применяется к файлам общей ветки, которые уже изменены в открытой папке:
правка общего процесса со ссылкой на командное действие ломает общий уровень для всех
команд.

## Шаг 7. Согласие и отправка

1. Показать итог: сколько файлов, что изменится для всех команд, ветка, куда уйдёт, что
   нашлось при проверке. Дождаться **явного «да» на отправку**: правка общего уровня видна
   всем, поэтому «да» на сборку не равно «да» на отправку.
2. Отправить: `git push -u origin <ветка>`. Отклонён пуш правилами репозитория — показать
   причину, не обходить.
3. Создать запрос на изменения в основную ветку тем же способом, что и в прошлый раз.
   Заголовок — сообщение из шага 5, тело — короткое описание: что перенесено, что проверено,
   что осталось за уровнем и почему.
4. Передать человеку адрес запроса и одну строку итога. Сказать, что правка начнёт
   действовать у других после того, как запрос на изменения примут.

## Чего не бывает

- переноса в командную ветку этим скиллом — для этого `pp-ai-promote-changes-team`;
- отправки без явного «да» на шаг;
- переноса координат подключений, названия команды и файлов уровней в общий состав;
- переписывания содержимого файлов и переименований;
- слияния запроса на изменения;
- работы с черновой веткой в открытой папке человека: у неё своё рабочее место вне
  открытой папки (шаг 4);
- работы через `--force`, `git reset --hard` и правок глобальных настроек git.
