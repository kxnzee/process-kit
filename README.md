# Process Kit

Повторяемые рабочие задачи через чат GigaCode. В поставке: отчёт о доле историй,
выполненных по SDD, и правка готового текста. Почтовой отправки нет — только черновик.

## Начало работы

1. Получите адрес корпоративного репозитория у владельца и клонируйте его в отдельную папку.
2. Откройте эту папку в GigaCode. Нужны Git и Node.js 18 или новее.
3. Напишите задачу словами. Для живых систем помощник проведёт настройку; для правки
   текста или демо внешние подключения не нужны.

Не вводите токены в чат. Если нужен доступ, помощник назовёт секрет и ключ для настроек
GigaCode; после добавления перезапустите клиент. Значения не записываются в репозиторий.
Пока секреты и живая работа не проверены в вашем клиенте, доступ не считается подтверждённым.

Результаты в outputs/<дата>_<задача>/; в чате полный путь к итог.md. Настройка сохраняет
что-сделано.md. Прошлые результаты и личная история не отправляются в общее хранилище.
«Перепиши короче» редактирует явно переданный текст либо однозначный последний результат.

## Обновление

Сначала убедитесь, что ваши изменения сохранены. Получите версии: git fetch origin --tags.
В личной копии примите согласованный владельцем стабильный тег vX.Y.Z: git merge vX.Y.Z;
для команды — также git merge origin/team-<код>. Конфликт не решается автоматически:
сохраните обе стороны и обратитесь к владельцу. Затем node tools/check-all.js.
Фраза «обнови Process Kit» пока не отдельный автоматический механизм.
Без стабильного тега новая установка без команды требует действий владельца поставки.

## Для разработчика

Архитектура — ARCHITECTURE.md, термины — CONTEXT.md, точные контракты — docs/reference/.
Правила для агента — GIGACODE.md, заготовки — docs/templates/.
После изменения контракта обновите код, шаблон и регрессионную проверку. Не копируйте
правило во все скиллы: скилл должен ссылаться на общий контракт.

```
node tools/check-all.js
node tools/validate.js --process edit-text
node tools/validate.js --process sdd-stories-report --demo
node tools/validate.js --process sdd-stories-report --params <json-файл>
node tools/check-report.js --process sdd-stories-report --run <папка-запуска>/.run
```

check-layout.js — совместимое прежнее имя validate.js. Код 0 — проверки пройдены,
1 — найдено нарушение, 2 — неверный вызов. Самотесты создают только временные папки;
check-prepush.js отправляет в локальные одноразовые bare-репозитории без сети.
Положительная сверка эталонов не означает, что GigaCode исполнил живой процесс.

Склонированная ветка master содержит только sources.template.json. Командный или
личный sources.json заполняется настройщиком, глобальные настройки не меняются.
Установить hook для этой копии: node tools/install-hooks.js. Прежний hook сохраняется
и продолжает проверять отправки. Повтор установки безопасен. Скрипт нужно запускать
в каждой клонированной копии; git не устанавливает hooks при clone сам.
Записи refs/notes/ai — локальные заметки GigaCode, они не отправляются в общий адрес.

## Для администратора Bitbucket

Общий репозиторий: master, командные ветки team-<код>, рабочие ветки master-* и
promote/*. На master и team-* запретите прямую запись, переписывание истории и удаление;
принятие только через запрос на изменения с владельцами соответствующей команды.
Новая команда может потребовать отдельного права первоначального создания ветки;
при отсутствии права помощник выдаёт заявку, не обходит ограничения.
Назначение ревьюеров и точный UI зависят от корпоративной версии Bitbucket.
Автоматическое создание PR требует реально доступного инструмента; без него запрос
создаёт человек. Серверные настройки не восстанавливаются из этой выгрузки.

Выпускайте стабильные теги vX.Y.Z только с master после проверок и корпоративной приёмки.
Описание тега: изменения формата, несовместимости, устаревшие процессы и замены.
Код команды [a-z0-9]+; my не имеет upstream и отправляется только в отдельный mine
при явной настройке. Локальный hook — дополнительная проверка, серверную не заменяет.

## Замена восстановленной версии

Сохраните резервную копию исходной рабочей папки. Переносите изменения платформы в
отдельную рабочую ветку корпоративного репозитория и проверьте diff до принятия.
Не заменяйте .git/, config/sources.json, TEAM.md, my-*/team-* материалы, outputs/,
.history/ и настройки секретов готовой общей копией. Изменение имён/состояния старого
прогона не означает его безопасное продолжение новой версией.
План приёмки — docs/acceptance.md; результаты ремонта — docs/architecture-review-2026-11-02.md.
