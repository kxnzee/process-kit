# Форма артефакта `methodology-check`

Одна форма для всех процессов: шаг отчёта читает именно эти ключи, поэтому переименовывать
их нельзя. Пустые списки остаются пустыми — раздел не удаляется.

```yaml
methodology-check:
  source:                    # на чём сверяли
    pageUrl: <адрес страницы методики>
    pageTitle: <название страницы>
    version: <номер версии страницы>
    updatedAt: <дата последнего изменения страницы>
    readAt: <когда прочитана>
    readToEnd: true | false  # дочитана ли страница целиком
    connection: <каким сервером чтения прочитана>  # в live — обязательно, в demo — пусто
  mode: live | demo          # demo — сверка не по странице, а по данным фикстуры
  total: <сколько разделов сверялось>
  matched: <сколько сопоставлено>
  mismatched: <сколько разошлось>
  unverified: <сколько не проверено>
  sections:                  # по записи на раздел, в порядке methodologyMap
    - section: <раздел методики>
      target: <где в процессе лежит значение, например params.lookBack>
      status: matched | mismatched | unverified
      process: <фактическое значение в процессе>
      method: <фактическое значение в методике>
      action: change | clarify | keep
      reason: <причина, если статус не matched>
  unverifiedSections:          # разделы и причины, по которым сверка не сложилась
    - section: <раздел>
      reason: <почему>
  notInProcess:              # значения методики, которых в процессе не заведено
    - value: <значение>
      section: <откуда>
  methodologyNews:           # изменения методики, которые задевают этот процесс
    - date: <дата изменения>
      change: <что изменилось>
  notes:
    - <сноски: решения владельца процесса, ручные значения, ограничения чтения>
```

Правила заполнения:

- `mismatched` + `matched` + `unverified` = `total`; иначе артефакт неполный;
- `process` и `method` — значения, а не пересказ; если список длинный, значения
  перечисляются через запятую, остаток сворачивается как «и ещё N»;
- границы окна пишутся как они есть у каждой стороны: формула методики остаётся формулой
  (`startOfDay(-3)..startOfDay(3)`), окно процесса — своими датами или длиной;
- `action: change` — значение в процессе надо поправить; `clarify` — сначала выяснить
  у автора сценария; `keep` — оставить как есть, причина в `reason`;
- `methodologyNews` — только записи, задевающие параметры этого процесса, и только когда
  прочитана предыдущая версия страницы; без сравнения версий список пуст;
- при `readToEnd: false` все разделы, до которых не дошли, идут в `unverified`, а в `notes`
  пишется, на какой порции чтение остановилось.

## Значения методики, которых нет на инстанции

- Значение методики, снятое по решению владельца уровня и подтверждённое ответом системы
  (Jira отклонила его с 400 «The value '…' does not exist for the field '…'»), — это
  `matched`, `action: keep`, а не `mismatched`. Причина пишется прямо: «значения нет
  на инстанции, снято по решению владельца процесса».
- Такие значения идут одним списком в `notes` — с датой проверки и дословной формулировкой
  отказа системы, чтобы через полгода было видно, на чём это решение держалось. В `sections`
  они не разворачиваются по одному значению и в `mismatched` не считаются.
- В `notInProcess` они не попадают: этот список — для значений, о которых человек ещё
  не решил. Разобранное туда не дублируется.
- Запись без подтверждения системы (значение не проверялось живым обращением) правилом
  не пользуется: раздел остаётся `mismatched` или `unverified`.
- В `notes` пишется и фактически прочитанный файл решений (`methodologyNotes`); его нет —
  сверка шла без них, и это не ошибка.
