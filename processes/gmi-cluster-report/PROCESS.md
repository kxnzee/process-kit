# Процесс: цифры кластера и план подъёма по GigaCode Maturity Index

Считает по сводной таблице оценок то, что просит сценарий «GigaCode Maturity Index»: целевой
показатель по трём блокам и итогу, сотрудников ниже цели, рекомендацию каждому и две таблицы
для отчёта.

Данных из систем нет: вся таблица приходит файлом, поэтому расчёт и обе формы локальны.
Единственное обращение наружу возможно до чтения таблицы — сверка методики с порталом, и только
если человек на неё согласился (`methodologyCheck`). Без согласия маршрут остаётся локальным
целиком.

## Что важно знать при исполнении

- **Периметр — все строки файла.** Отбора по КЭ, трайбу или списку людей в процессе нет;
  если нужен отбор — он делается до прогона, а результат прогона называется другим периметром
  в параметре `perimeter`, иначе число людей в отчёте будет врать.
- **Цель задаёт человек.** В методике целевого значения нет; `goal` (по умолчанию 6,0 из 10) и
  предупреждающий порог `warnBelow` (3,0) — решения владельца. Разложение цели по блокам
  берётся из весов методики: 30 %, 30 % и 40 % от цели.
- **Средние и «Общий балл» считаются по-разному.** Средний GMI и средние блоков — среднее на
  человека по строкам с заполненным «Общий итог»; «Общий балл» — сумма тех же итогов.
  Знаменатель печатается под таблицей: без него две цифры рядом читаются как одна.
- **Блоки пересчитываются, итог — из файла.** Пересчёт нужен рекомендациям: рычаг считается
  по шкале, а не по чужому итогу. Расхождение блока с баллом файла не прячется — оно попадает
  в раздел расхождений, а при массовом расхождении процесс задаёт вопрос.
- **Рекомендация — детерминированное правило**, не суждение модели: только шаги, видимые в
  колонках выгрузки (курсы, частота, режим, навыки, когорта, метрики продуктивности, Story),
  и прирост по следующей ступени той же шкалы. Балльные приросты складываются в потенциал,
  поэтому «этого хватает до цели» — проверяемое число.
- **Пустое значение — не ноль.** «В файле нет» остаётся неподтверждённой частью блока и
  попадает в строку «Не подтверждено»: занижать человеку балл из-за дырки в выгрузке нельзя.
  Так же и с незнакомой градацией: например «Резко чаще» в частоте использования не превращается
  ни в «ежедневно», ни в «не используют».
- **ФИО и название команды берутся из самой выгрузки** — колонки `ФИО сотрудника` и `Команда`
  (номер сотрудника при этом подписан то `Номер сотрудникА`, то `ТН` — читаются оба варианта).
  Поиск по табельному номеру в Jira и Bitbucket ничего не даёт, SberTrack и справочник
  сотрудников OneWork недоступны, поэтому имена из чужих систем не подставляются никогда: если
  колонок нет, процесс молча просит справочник (`nameFile`) для старого снимка, а без него
  подписывает людей табельными номерами и называет это в оговорках.
- **Название команды важнее кода**: в сводной таблице печатается `Команда`, код (`Код Команды`)
  остаётся запасным вариантом для снимков, где названия ещё не было.
- **Столбцы трайба в оценку человека не входят**: «TRIBE_AVG …», «Персентиль 25/50» и
  «Оценка в БП» (трайбовый бонус МУИ 0–0,2) относятся к трайбу. В файле они есть, процесс их
  читает и не использует — это видно в оговорках.
- **Балл «Рост Story на 1 сотрудника» трактован по сноске слайда 6**, потому что таблица того
  же слайда противоречит и сноске, и баллам файла: команда выше цели кластера — 1, ниже — 0.
  Расшифровка формулировок выгрузки лежит в `reference.md`.
- **Методика живёт на портале, процесс сверяет её по запросу.** Числа шкал правила получились из
  снимков владельца: на портале они лежат картинками слайдов (`Слайд2.JPG`, `Слайд3.JPG`,
  `Слайд5.JPG`, `Слайд7.JPG`…), а тела вложений подключение портала не отдаёт. Текстом на
  «Методологии расчета GigaCode Maturity Index» (MApp, страница 466404, v18 от 08.10.2026) заданы
  периоды анализа метрик и контакты владельцев методики; определения метрик читаются на странице
  «AI PDLC. Проникновение в целевую аудиторию.» (`https://mapp.sberbank.ru/ditrace/page/27914`,
  v142 от 09.11.2026) — её переписывают часто, и расхождение определений возможно именно здесь.
  Оба источника с версиями перечислены в `reference.md` и печатаются в отчёте параметром
  `methodologyVersion`. Шаги `check-scales` и `check-index` читают эти страницы ДО таблицы и
  только при согласии человека; каждое чтение — одна страница, своей картой разделов. Ни один шаг
  ничего не правит: расхождение шкал — вопрос владельцу методики, а не молчаливая правка правила.
  Принятые расхождения (цель, порог, сноска слайда 6, трайбовые колонки, контакты владельцев)
  записаны в `methodology-notes.md`, чтобы сверка показывала их отдельной строкой, а не как новую
  ошибку.
- **Обе формы создаются автоматически.** Главный результат — `отчёт-gmi.html`,
  текстовая форма `отчёт-gmi.md` сохраняется рядом через run publish. Отдельный вопрос
  о формате не нужен; обе формы локальны и строятся из одних данных.

- **Форма страницы не меняет содержимого**: шаг `render-html` собирает одностраничник из текста
  той же markdown-формы, поэтому способ выдачи — про оболочку, а не про новые выводы.
- **Ссылка «Письмо сотруднику» — это черновик, а не рассылка.** Право на ссылку даёт адрес из
  почтового справочника организации: он владелец почты, и адрес в нём уже принадлежит человеку.
  Карту «ФИО → адрес» собирает шаг lookup-mail этого прогона; peopleFile позволяет явно передать готовую карту. Адрес берётся по точному совпадению ФИО. Сверять
  номер учётной записи с каталогом пользователей задач перестали 11.11.2026 по решению владельца
  процесса — расхождение номеров чаще значило, что человека нашли в другой инсталляции задач,
  а не что адрес чужой.
  При двух-трёх неразличённых записях отчёт даёт выбор адреса человеку; угадывать адресата письма нельзя,
  поэтому человека, которого не удалось опознать в справочнике, в карту не вносят. Одинаковые ФИО
  внутри одного списка писем не получают никогда. В письмо попадают только формулировки
  «что сделать» из раздела персональных рекомендаций: баллов, степеней улучшения, оценок и
  расхождений в письме нет. Отправляет его человек сам, шага отправки в маршруте нет; сколько
  писем не создано и по каким причинам — процесс пишет в оговорках.

## Вход и завершение

Вход — файл таблицы. Действие чтения принимает пути только из рабочих папок процесса, поэтому
выгрузку кладут в `processes/gmi-cluster-report/data/` и передают процессу:
`node tools/kit.js check --process gmi-cluster-report --params <json>`, где в `<json>` —
`scoreFile` и `runDate`. Форма входа: xlsx первого листа в порядке вкладок книги либо JSON вида
`{"headers": […], "rows": [[…]]}` с теми же заголовками столбцов.

Аргументами запуска передают то, что меняется: `scoreFile`, `runDate`, `demo`, `nameFile`,
`peopleFile`, `goal`, `warnBelow`, `perimeter`, `methodologyCheck`. Демонстрационный прогон
оставляет `scoreFile` по умолчанию и ставит `demo: true` — тогда весь отчёт помечен «ДАННЫЕ ДЕМО»,
а внешних обращений нет. При `methodologyCheck: yes` в режиме demo используется явно
явно переданная синтетическая сверка контракта, не подтверждающая актуальность страниц;
при разработке её предоставляет приёмочный тест. Без такого входа демо-сверка останавливается.
Для чтения
настоящей методики нужен режим live; local допускает только `methodologyCheck: no`.

`scoreFile`, `nameFile` и `peopleFile` объявлены в `runtimeInputs`: передаются точными
путями к JSON/XLSX в data/ этого процесса, защищаются снимком конкретного Run и не
входят в допуск определения. Новая выгрузка не требует перепубликации процесса.

Содержание отчёта — артефакт `report-page`: тот же текст становится файлом для человека и
основой формы страницы. `итог.md` журнал пишет сам; finish побайтно копирует последний артефакт
под именем `resultName`. Штатный маршрут создаёт HTML и Markdown; остановка после
сверки сохраняет её JSON-сводки без расчёта отчёта.

Рабочий маршрут ведёт существующий журнал: start → next → отдельный choose на развилке,
затем execute или begin/save с текущим attemptId и finish. Для user-развилки достаточно
явного ответа человека из диалога в decision; доверенный хост не обязателен.

## Шаги

### methodology-gate

Сверка идёт до чтения таблицы и не обязательна: `methodologyCheck` = `ask` — помощник спрашивает
человека до начала прогона и продолжает с явным `yes` или `no`. В demo сверка
синтетическая, без чтения внешних страниц и без вывода об актуальности методики.

- decision: code
- branch:
  - когда: `params.methodologyCheck` = `yes` → goto: check-scales
  - иначе (default): goto: read

### check-scales

Чтение страницы определений метрик — её переписывают часто (на 12.11.2026 версия 142 от
09.11.2026), поэтому она читается первой. Здесь текстом заданы определения, а не баллы: расчётная
целевая аудитория, градации частоты через пороги отработанных дней, режим агента против режима
ассистента, когорты потребления токенов, шесть навыков и планка «5 из 6», метрики продуктивности.
Выполняет отдельный агент: страница десятками тысяч знаков, в контексте прогона нужны сводка и путь
артефакта. Если сервер портала или его инструмент чтения страницы в сессии не объявлены, действие
останавливается и называет причину; содержимое страницы по памяти или из прошлых прогонов не
восстанавливается — без источника сводка была бы выдумкой.

- действие: check-methodology
- параметры:
  - `methodologyUrl: {params.methodologyScalesUrl}`
  - `methodologyName: "определения метрик GigaCode (дашборд проникновения, страница 27914)"`
  - `methodologyAdapterFile: {params.methodologyAdapterFile}`
  - `parameters: {"methodologyMap":{params.methodologyScalesMap},"methodologyAliases":{params.methodologyAliases},"methodologyReadOnly":{params.methodologyReadOnly},"methodologyNotes":"{params.methodologyNotes}"}`
- артефакт: methodology-scales
- следующий: check-index

### check-index

Второе чтение — документ с составом индекса. Он меняется редко и нужен как проверка знаменателя:
три блока, их метрики и шесть навыков. Карта разделов своя, поэтому сверка не перепутывает
«состав не сошёлся» с «шкала другой версии».

- действие: check-methodology
- параметры:
  - `methodologyUrl: {params.methodologyIndexUrl}`
  - `methodologyName: "методология расчёта GigaCode Maturity Index"`
  - `methodologyAdapterFile: {params.methodologyAdapterFile}`
  - `parameters: {"methodologyMap":{params.methodologyIndexMap},"methodologyAliases":{params.methodologyAliases},"methodologyReadOnly":{params.methodologyReadOnly},"methodologyNotes":"{params.methodologyNotes}"}`
- артефакт: methodology-index
- следующий: methodology-review

### methodology-review

Развилку решает человек. Координатор показывает ему обе сводки целиком — по шкалам и по составу
индекса: сколько разделов сопоставлено, что разошлось и в какую сторону, что не проверено и почему
(в том числе разделы, которых на странице не нашлось), — полные пути артефактов
`methodology-scales` и `methodology-index` и список вопросов, где нужно решение владельца
методики. Ответ агента человеку не виден, поэтому пересказ обязателен. Молчание означает остановку
на сверке: finish сохранит её сводки, а не числа, которые ещё не на чем считать.

- decision: user
- branch:
  - когда: человек получил обе сводки и подтвердил продолжение → goto: read
  - иначе (default): goto: end

в отчёте и должен соответствовать файлу.

- действие: read-score-table
- параметры:

  - `nameFile: {params.nameFile}`

### mail-gate

Карта адресов дополняет отчёт: цифры и рекомендации без неё сохраняются.
Проверь доступные инструменты сессии и mailServer без внешнего чтения. При наличии
одного выбранного поиска контактов перейди в lookup-mail; при отсутствии — mail-off.
Несколько серверов требуют выбора человека. Параметр peopleFile позволяет передать
готовую карту; в demo lookup-mail использует только локальные данные.

Первое пробное чтение по probe-mail.js выполняется после begin шага lookup-mail.
При отказе доступа или таймлимите сообщи причину и получи решение: остановиться
либо сохранить карту с причинами отсутствия адресов. Молчание не разрешает опрос.

- decision: model
- branch:
  - когда: в сессии найден один выбранный инструмент поиска контактов на сервере со словом `email` в имени → goto: lookup-mail
  - иначе (default): goto: mail-off

### lookup-mail

Карта адресов собирается в прогоне, а не заводится человеком заранее. Опрашивают
не всю выгрузку, а адресатов рекомендаций: строки артефакта чтения, где «Общий итог» — число и оно
ниже `goal`. Это ровно те ФИО, под которыми отчёт печатает персональный блок со ссылкой, поэтому
карта не может разъехаться со списком писем и не тратит живые обращения на людей без письма.
Сколько строк попало в адресаты и сколько осталось за его краем, шаг называет счётчиками
(`адресатов` и `внеСпискаАдресатов`); индекс строки фильтр не меняет, поэтому прерванный опрос
продолжается с того же места. Строки без «Общего итога» адресатами не считаются: рекомендации им
процесс не даёт. Справочник читает отдельный агент, в папке прогона остаётся карта и её счётчики.

Сервер справочника ищется по `mailServer` или по `email` в имени настроенного MCP-сервера; живой
признак наличия берётся на развилке `mail-gate`, и без неё в этот шаг процесс не входит.
Несколько подходящих серверов — остановка шага со списком имён: выбирать должен человек. Если
подключение пропало уже в ходе опроса (отказ доступа или таймлимит на большинстве имён), шаг не
делает вид, что адресов просто нет: незакрытые люди получают причину своими словами, а следующий
прогон опрошивает только их — сырые выдачи остальных уже лежат файлами.

Адрес берётся только из незаблокированной записи справочника: одна такая запись отдаёт адрес,
несколько различаются столбцом выгрузки (`companyColumn`) и берутся, только когда
совпала ровно одна запись. Ни один признак не совпал — единственного адреса нет. Пригодных записей
две или три карта отдаёт все вместе (`"кандидаты"` с должностью и отделом каждой), и на странице под
блоком человека стоит по кнопке «Письмо сотруднику» на каждую запись: кому из однофамильцев писать,
решает человек, а не процесс. Записей четыре и более — остаётся текстовая причина, потому
что выбирать среди них — гадать. Подрядная учётка помечается `"подряд": true`, и право на письмо у
неё наравне со штатной (решение владельца процесса от 11.11.2026).

**Как передать шаг агенту.** Координатор делает `run begin`, пишет пакет шага в
`.run/inputs/lookup-mail.json` и кладёт в него готовую команду сохранения вместе с путём spec-файла,
который собирает разбор: `{output, step, attemptId, artifact, extension, content, next}` — карточка save содержит текущий attemptId. Форму сохранения словами не описывают: прогон 13.11.2026 потерял на переделке
сохранения больше часа там, где весь живой опрос занял четыре минуты. Порядок один: опрос кусками →
разбор → перепроверки правил 5 и 7 → разбор → одна команда `run save`. Сырые выдачи справочника в
контекст не читаются — из них берутся только счётчики разбора. Помощники шага живут в папке
действия и объявлены в его `requiresFiles`, то есть приходят вместе с процессом на любую копию:
`actions/find-mail-contacts/scripts/poll-ldap.js` (опрос кусками, уже отвеченные имена пропускает)
и `actions/find-mail-contacts/scripts/build-map.js` (разбор выдач, карта и spec сохранения);
описание — в разделе «Помощники шага» рецепта. Два куска опроса допустимо исполнять параллельно,
отказ по квоте отрабатывает встроенный повтор. Агенту называется потолок вызовов инструментов — 25:
близко к порогу он сохраняет карту как есть и называет незакрытых людей, а дополняет их следующий
прогон, где выдачи этих имён уже лежат файлами и справочник повторно не опрашивается.

- действие: find-mail-contacts
- параметры:
  - `inputs: {"scores":"{score-table}"}`
  - `scoreFile: {params.scoreFile}`
  - `mailServer: {params.mailServer}`
  - `companyColumn: {params.companyColumn}`
- артефакт: people-map
- следующий: assess

### mail-off

Штатный итог, когда почтового подключения нет: карта собирается без единого обращения к
справочнику — у каждого адресата рекомендации причина, названная на развилке. Форма отчёта не
меняется: под каждым персональным блоком страница печатает эту причину вместо ссылки, в текстовой форме
появляется строка примечания со счётчиком. Агент для шага не нужен и подключений он не требует —
координатор выполняет карточку run execute. Если нужен отдельный текст причины, после begin допустим помощник:

```bash
node actions/find-mail-contacts/scripts/build-map.js <выпуск> --без-подключения "<причина с развилки>"
node tools/kit.js run save outputs/<выпуск>/.run/inputs/save-mail-off.json
```

Разборщик пишет карту, счётчики и spec сохранения сам; форму spec править нельзя. Строку человеку
повторять не надо — она уже сказана при выборе перехода.

- действие: find-mail-contacts
- параметры:
  - `mailMode: off`
  - `inputs: {"scores":"{score-table}"}`
  - `scoreFile: {params.scoreFile}`
  - `companyColumn: {params.companyColumn}`
  - `mailServer: {params.mailServer}`
- артефакт: people-map
- следующий: assess

### assess

вход того же шага: она нужна только подписи писем и на баллы не влияет, поэтому пустая заготовка

### end

Терминальный узел. При report-page-html вызови finish с resultName=отчёт-gmi.html,
затем run publish с artifact=report-page и name=отчёт-gmi.md: обе формы лежат рядом.
При остановке после сверки сохрани последний JSON-артефакт как сверка-состав-индекса.json,
а methodology-scales отдай через run publish как сверка-шкалы.json; отчёт тогда не создан.
Ошибка чтения таблицы остаётся ошибкой входа с причиной, а не пустым отчётом.
