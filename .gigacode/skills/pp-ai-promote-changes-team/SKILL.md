# Перенос изменений в командную ветку

Вход — открытая папка и просьба человека перенести наработки в команду (все или выборочно).
Выход — ветка с перенесёнными файлами и запрос на изменения в командную ветку, либо честный
отказ с причиной. Модель и правила уровней — в `GIGACODE.md` проекта; здесь только порядок
действий.

**Что этот скилл не делает:** не правит содержимое файлов, не сливает запросы на изменения,
не отправляет в общую ветку (это `pp-ai-promote-changes-master`), не переносит координаты
подключений, не трогает чужие файлы — в том числе не «приводит их к уровню» переименованием.

**Как говорить.** По-русски, с первой фразы. Человеку — слова изменения, уровня, команды,
запроса на изменения. Не произносить: ветка, master, team-, префикс, скилл, конфиг,
sources.json, адаптер, MCP, PR, коммит, имена файлов, команды «/». Вместо «ветка
team-<команда>» — «командный уровень вашей команды», вместо «git push» — «отправлю в
хранилище», вместо «PR» — «запрос на изменения».

## Шаг 0. План и согласие

Показать короткую карточку и дождаться «да»:

> Я соберу наработки в вашей папке, разделю их по уровням и покажу список. Дальше вы
> скажете — переносить всё подходящее или только выбранное. В вашей папке я ничего не
> изменю; запрос на изменения отправлю только после отдельного «да».

## Шаг 1. Где мы и что менялось

1. Открытая папка — корень проекта. Уровень рабочей копии — по `git branch --show-current`:
   `my` — личный; ветка команды — командный; `master` и `master-*` — общий.
2. Имя команды: из `TEAM.md` (поле с названием команды) в открытой папке. Нет `TEAM.md` —
   остановиться и сказать, что команда не определена, перенос невозможен.
3. Список изменённого: `git status --porcelain` — новые и изменённые файлы в рабочей копии
   плюс те, коммиты которых есть в текущей ветке и ещё не попали в командную ветку
   (`git log --oneline origin/team-<команда>..HEAD`). Если не изменено ничего — сказать
   «переносить нечего» и закончить.
4. Выполнить `git fetch origin` — нужен свежий вид командной ветки. Сеть недоступна —
   остановиться и сказать об этом, не собирать перенос по устаревшим данным.

## Шаг 2. Отнести каждый файл к уровню

Уровень файла определяется **именем и местом**, а не намерением человека.

Порядок проверки, первый подошедший признак решает:

1. **Общий уровень** — файлы, которые правятся только в общей ветке: `GIGACODE.md`,
   `README.md`, `ARCHITECTURE.md`, `tools/*`, `config/sources.template.json`,
   `.gigacode/settings.json`, `.gigacode/hooks/*`, `.gigacode/skills/pp-ai-*/`, а также
   `processes/`, `actions/`, `adapters/`, `context/`, `tests/<имя>/` — **без префикса
   уровня**. Такие файлы в перенос **не берутся**: их место — общий уровень, и здесь
   человеку говорится об этом одной строкой.
2. **Командный уровень** — файл с префиксом `<команда>-` в `processes/`, `actions/`,
   `adapters/`, `context/`, `tests/<имя>/`; `config/sources.json`; `TEAM.md`.
3. **Личный уровень** — файл с префиксом `my-`. В командную ветку `my-*` **не переносится
   никогда**: это личные файлы человека, у команды их быть не должно.
4. **Нераспознанное** — имя без префикса в месте, где префикс ожидается, файл в
   неожиданном каталоге, служебные каталоги агента (`runs/`, `.gigacode/worktrees/`,
   локальные файлы редактора). В выбор не попадает; человеку — одной строкой, что и почему.

Файлы, подпавшие под пункты 1, 3 и 4, в список выбора не попадают вовсе: иначе перенос
упадёт на чужом файле, и человек не поймёт почему. Если изменений в командном уровне нет
вовсе — сказать, что переносить в команду нечего, и назвать, если что-то принадлежит
другому уровню.

## Шаг 3. Показать и спросить: всё или выбранное

Показать список простыми словами — что это и куда уйдёт:

```
Перенесу в командный уровень:
  1. отчёт по спецификациям — описание процесса
  2. отчёт по спецификациям — правила отбора
  3. отчёт по спецификациям — вид отчёта
  4. настройки подключений команды
Не перенесу (чужой уровень):
  - правка правил набора — это общий уровень
  - служебный скилл конструктора — это общий уровень
```

Спросить одним вопросом: «Перенести всё из списка или только часть? Назовите номера».
Всё — берётся весь список командного уровня; часть — только названные. Ничего не выбрано —
закончить без переноса.

## Шаг 4. Завести рабочую ветку

1. Имя ветки: `promote/team-<команда>/<краткая тема>`; сегмент `team-<команда>` задаёт
   уровень назначения и команду; тема — из сути изменений, две-четыре латинские части через
   дефис, например `promote/team-sws/weekly-report`. Ветка с таким именем уже есть —
   добавить номер или уточнить у человека.
2. Ветку завести **от командной ветки после обновления**, а не от текущей рабочей копии —
   иначе в перенос попадут чужие незавершённые изменения:
   - `git fetch origin`;
   - `git branch -f <ветка> origin/team-<команда>`;
   - работать с ней только через отдельный рабочий каталог (`git worktree`): открытая
     папка и её текущая ветка не переключаются ни при каком раскладе.
3. Рабочий каталог держать **вне открытой папки** — во временном каталоге машины:
   `git worktree add /tmp/<имя> <ветка>`. Клиентский файловый страж не пускает запись
   наружу — запасной путь внутри открытой папки: `.gigacode/worktrees/<имя>` (служебный
   каталог, в перенос не попадает). Черновая ветка живёт только пока идёт перенос.
4. После отправки убрать за собой: `git worktree remove /tmp/<имя>`, затем
   `git branch -d <ветка>` — ни временных каталогов, ни черновых веток после себя
   не остаётся. Перенос не отправлен — спросить человека, убирать рабочее место или
   оставить до следующего шага.
5. Несохранённые изменения открытой папки не переключать и не прятать (`stash`): перенос
   идёт через отдельный рабочий каталог, открытая папка остаётся как есть.

## Шаг 5. Перенести выбранные файлы

1. Скопировать в ветку только выбранные файлы — те же пути, то же содержимое. Содержимое
   не редактируется: скилл переносит, а не правит.
2. Проверить, что в ветке нет файлов чужого уровня: ни `my-*`, ни общих файлов из
   пункта 1 шага 2. Нашлись — убрать их из ветки и сказать человеку.
3. Сформировать сообщение об изменении одной строкой: что перенесено и зачем (по сути
   изменений, без перечисления путей).
4. Изменить только эту ветку: открытая папка и текущая ветка человека не переключаются.

## Шаг 6. Проверить

1. Прогнать `node tools/validate.js` **в ветке переноса** (прежнее имя `node tools/check-layout.js`
   принимает те же аргументы): уровень и команду она
   узнаёт из имени рабочего места (`promote/team-<команда>/…`). Ошибки раскладки —
   остановка: показать, что не так, и не отправлять. Предупреждения о префиксе уровня —
   перечислить человеку, они не блокируют.
2. Проверить, что ссылки перенесённых файлов разрешаются внутри ветки: имя, которого нет
   в ветке, — ошибка раскладки, а не повод дослать его «за компанию».

## Шаг 7. Согласие и отправка

1. Показать итог: сколько файлов, что за изменения, ветка, куда уйдёт, что нашлось при
   проверке. Дождаться **явного «да» на отправку**.
2. Отправить: `git push -u origin <ветка>`. Отклонён пуш правилами репозитория — показать
   причину, не обходить её.
3. Создать запрос на изменения в командную ветку тем же способом, что и в прошлый раз
   (инструмент хранилища из подключений). Заголовок — сообщение из шага 5, тело — короткое
   описание: что перенесено, что проверено, что осталось за уровнем.
4. Передать человеку адрес запроса и одну строку итога.

## Чего не бывает

- переноса в общую ветку этим скиллом — для этого `pp-ai-promote-changes-master`;
- отправки без явного «да» на шаг;
- переписывания содержимого файлов, переименований и «приведения уровня»;
- слияния запроса на изменения;
- работы с черновой веткой в открытой папке человека: у неё своё рабочее место вне
  открытой папки (шаг 4);
- переноса `my-*`, координат чужой команды и файлов общего уровня;
- работы через `--force`, `git reset --hard` и правок глобальных настроек git.
