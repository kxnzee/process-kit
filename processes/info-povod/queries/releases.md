# Запрос: отобрать релизы Release 2.0 периметра КЭ и прочитать их состав

Шаги `fetch-sigma` и `fetch-delta` процесса `info-povod`. Один текст под обе инсталляции:
чем отличается sigma от delta (адрес, коды полей, периметр КЭ) — решает выбранная запись
подключения, здесь кодов полей нет. Окна, тип задачи и исключаемые статусы приходят
параметрами шага из `params` процесса.

Механика системы (что отдаёт выдача, чем фильтруется поле, как читается состав) —
`adapters/jira/ADAPTER.md`; адреса, коды полей и периметр КЭ — выбранная запись подключения.
Правила отчёта — не здесь:
разделение технических и содержательных задач делает шаг классификации, группы по КЭ и форму
— шаг расчёта.

Выход — `task-records` по контракту `actions/run-query/contracts/result.json`: `meta`,
`records[]` (релизы, прошедшие отбор), `excluded[]` (вне отчёта с причиной), `unverified[]`
(прочитать не удалось), `selectionId`.

## Параметры

Приоритет: аргументы вызова → `параметры` шага → `params` процесса → настройки подключения.

| Параметр | Откуда | Что означает |
|---|---|---|
| `instanceLabel` | `параметры` шага | метка инсталляции для `meta` (`sigma`, `delta`); в отчёт не печатается |
| `releaseType` | `params` процесса | тип задачи релиза (`Release 2.0`) — обязателен в JQL |
| `statusesExclude` | `params` процесса | статусы, которые не попадают в отбор (`Cancelled`) |
| `runDate` | `params` процесса, аргумент вызова | дата прогона `ГГГГ-ММ-ДД`; из неё считаются оба окна |
| `lookBackDays`, `lookAheadDays` | `params` процесса | ширина окна назад и вперёд |
| `taskFields` | настройки: `taskStores[].taskFields` | коды полей этой инсталляции: `ke`, `startDate`, `itService` |
| `modules` | настройки: `taskStores[].modules` | периметр КЭ этой инсталляции: записи `{ code }` |
| `issueUrlTemplate` | настройки: `taskStores[].issueUrlTemplate` | сборка ссылки на задачу |

`runDate` пуст или не передан — остановиться и спросить дату прогона: окна без неё считаются
по часам машины и в выборке, и в расчёте по-разному.

## Окна прогона

Границы считаются **один раз** из `runDate` и одинаковы для этого запроса и для шага расчёта:

- текущие поводы: `[runDate − lookBackDays ; runDate]`, включительно;
- планы: `[runDate + 1 ; runDate + lookAheadDays]`, включительно.

Дата релиза — поле `taskFields.startDate` («Начало внедрения (план)»). Релиз вне обоих окон —
`excluded[]` с причиной «дата начала внедрения вне окон прогона» и самой датой.

## Периметр КЭ

1. Взять `taskStores[].modules`. Запись без `code` или с `code` не вида `CI0…` — остановка:
   периметр правит владелец настроек, а не прогон.
2. Из каждой `code` взять **цифровую часть без префикса `CI` и без ведущих нулей**
   (`CI03296913` → `3296913`): фильтр сравнивает значение поля, а не упоминание в тексте.
3. Итоговый список — `modulesInScope`, записать его в `meta` вместе с `instanceLabel` и
   эффективными границами окон.
4. `taskStores[].modules[].shared: true` — отметка, что код встречается в обеих инсталляциях.
   Она ничего не фильтрует: в этой инсталляции ищется весь список целиком.

## Правила отбора релиза

Релиз попадает в `records[]`, если подтверждены **все** пункты 1–4.

1. **Тип.** `issuetype = "<releaseType>"`. Проект не фильтруется: периметр задают коды КЭ,
   а релизы периметра лежат в разных проектах.
2. **КЭ.** Поле `taskFields.ke` содержит хотя бы один код из `modulesInScope`. Поле
   **фильтруется на стороне системы**: `cf[<номер>] in (<числа через запятую>)` — рабочий вид
   (подтверждён живым запросом 2026-11-07 в обеих инсталляциях). Оператор `~` и отображаемые
   имена КЭ не поддерживаются: запрос по названию даёт пусто, а запрос с несуществующим
   значением отбивает весь фильтр ответом 400. Номер поля — из `taskFields.ke` этой записи
   подключения (`customfield_18300` → `cf[18300]`); в текст запроса номер не выносится.
3. **Статус.** `status not in (<statusesExclude>)` — имена статусов существуют в этой
   инсталляции; новый список всегда подтверждать чтением (400 = имени нет в инстансе).
4. **Окно.** Дата в `taskFields.startDate` попадает в одно из окон: поле тоже фильтруется
   кодом — `cf[<номер>] >= "<ГГГГ-ММ-ДД>" AND cf[<номер>] <= "<ГГГГ-ММ-ДД>"` (подтверждено
   живым запросом 2026-11-07). В JQL идут обе границы сразу, `[runDate − lookBackDays ;
   runDate + lookAheadDays]`, а к какому окну относится релиз, определяет шаг расчёта по
   фактической дате.

Значения полей читать `get_issues` с `include_custom_fields: true`: без этого признака поле
«КЭ» и значение услуги в выдаче нет. Пакет — не больше `limits.getIssuesBatchMax`, пагинация
дочитывается до конца, счётчик прочитанного попадает в `meta`.

## Состав релиза

Состав — связи вида, а не перечисление в описании:

1. Для каждого релиза — `get_issue_links`; брать связи с именем типа `PartOf` (внутрь —
   «consists of»). Имя внутреннего id связи в инсталляциях разное, судить по имени.
   `relates`, «contains bugs», `Introduction Order` и прочие связи составом не считать.
2. Заголовки, типы, статусы и метки связанных задач добираются `get_issues` батчами
   (`get_issue_links` отдаёт только ключи).
3. Задача с типом `Bug` из состава исключается по требованию сценария — в `members[]` не
   попадает, а попадает в `excluded[]` родителя с причиной «тип задачи Bug».
4. Прочитать связи не удалось (сервер не отдал, нет прав) — у релиза `membersComplete: false`
   с причиной в `meta`-оговорке: пустой `members[]` при `membersComplete: false` — это
   непроверенность, а не «релиз пустой». Целостность всего релиза под сомнением — релиз в
   `unverified[]`.
5. Поле «КЭ» релиза — список `{ id, value }`; `value` — имя КЭ вида
   `SBP.IRBIS.Открытые данные(3296913)`. В `records[].keValues` сохраняются **все** значения
   поля, а в `records[].codes` — какие из них вошли в `modulesInScope`. Имя КЭ в отчёте
   печатается дословно из `keValues`.
6. Поле «ИТ-услуга» (`taskFields.itService`) — только в `meta` как справочное; строку отчёта
   определяет КЭ. Пустое поле — отметка в оговорках прогона, а не исключение релиза.
7. Поле «КЭ дистрибутива» с полем «КЭ» не смешивать: это другое поле
   (`customfield_21710` / `customfield_27011`), для отчёта оно не читается.

## Что вернуть

- `records[]` по каждому релизу: `key`, `summary`, `url`, `status`, `plannedAt`
  (`ГГГГ-ММ-ДД` из `taskFields.startDate`), `itService` (`value` или `null`), `keValues[]`
  (`{ id, name }`), `codes[]` (цифровые коды из `modulesInScope`), `members[]`
  (`{ key, issueType, summary, status, labels, url }`), `membersComplete`.
- `excluded[]`: `key`, `status`, `reason` (дата вне окон, тип задачи `Bug` в составе, КЭ вне
  периметра при повторной сверке).
- `unverified[]`: `key`, `summary`, `reason`.
- `meta`: `instanceLabel`, эффективные границы окон, `releaseType`, `statusesExclude`,
  `modulesInScope` (коды), прочитанный `queryFile`, число прочитанных релизов и батчей,
  оговорки (`plannedAtMissing`, `itServiceMissing`, `linksUnread`).
- `selectionId` сохраняет команда сохранения; после `save` объект не дополняется. Классы
  задач (`contained` / `technical`), группы по КЭ и строки отчёта сюда не писать — это шаги
  `classify-*` и `assess`.

Отсутствие данных не заменяется отрицательным выводом: не прочитано ≠ «в релизе ничего нет».

В demo сети нет: взять раздел задач из `dataFile` через `queryFixture(fixture, queryFile)`;
в демо оба шага чтения получают один и тот же набор релизов — это условие демо, оно остаётся
в оговорках прогона, а классификация из фикстуры не заимствуется.

## Чего в запросе не бывает

- правок настроек по ходу прогона: подтверждённые имена статусов и полей докладываются
  человеку, вносит их владелец уровня;
- классификации задач («техническая» или «содержательная») и группировки по КЭ;
- подмены кода поля из другой инсталляции: коды различаются, своя проверка — `get_fields`
  по имени поля.
