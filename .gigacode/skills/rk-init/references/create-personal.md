# Создать новую личную копию

Вход: результат setup-status с personal.state=missing,
исходная задача, personal-only/live и уже полученные ответы/согласия. Другое состояние
не разрешает создание новой личной копии: верни состояние агенту для продолжения исходной задачи. Существующую личную копию здесь
не пересоздавай. Чтение этого раздела само по себе не является согласием на изменения.

Общие ограничения — GIGACODE.md. Вопросы и изменения касаются только отсутствующих
значений; известные ответы не переспрашивай. Настройка не подбирает рабочий процесс.
Проверь выбранное подключение по config/team/README.md только когда оно нужно.

## Выполнение уже согласованной настройки

Если человек уже согласовал personal-only, команду/её отсутствие, хранение и профиль,
выполните настройку сейчас по разделам ниже с завершением по .gigacode/skills/rk-init/references/save-settings.md. Отсутствие my, профиля или hooks — задача
настройщика, а не причина blocked и не повод ещё раз спрашивать «начать?». Сначала
проверьте основание (fetch локального/согласованного origin, стабильный тег либо team),
затем создайте my, сохраните подтверждённый config, установите hooks, выполните check
и отчёт. Blocked требует фактической ошибки или отсутствующего обязательного ответа.
Не завершайте разрешённую настройку списком того, что вы ещё не сделали.

Не смешивайте идентификаторы: process — точное имя папки processes/<имя>, teamId —
код команды из team.id. Фраза «для команды a» не задаёт process=a. Если точное имя процесса
неизвестно, не угадывайте его: используйте общую проверку,
уточните process по исходной задаче или у человека и продолжайте разрешённую personal-only часть.
Не объявляйте нужный пользователю процесс отсутствующим по проверке кода команды.

Если при готовой my сообщён 401/403, но в config нет выбранного подключения,
НЕ советуйте наугад добавлять или заменять секрет. Сначала уточните, какой MCP/сервер
вернул ответ. Зафиксируйте личную готовность отдельно от недоступных подключений.
Если запрос не запрещает изменения, сохраните отчёт незавершённой настройки.

## План новой установки

Для новой установки без личной копии коротко объясни цель настройки и изменения:
в этой папке появятся личная копия и настройки; нужно выбрать команду и место хранения,
а для работы с системами — уточнить недостающий проект и проверить доступ.
Поясни, что сама настройка не меняет данные в этих системах. Называй только нужные
для текущей задачи системы и ещё не решённые вопросы. Формулируй естественно,
без дословного сценария и перечисления внутренних команд.

Если эта настройка ещё не согласована, получи согласие до изменения файлов и настроек;
до этого не задавай вопросы рабочей задачи.
Повторная уже готовая установка не требует этого плана.
Для personal-only покажи короткий соответствующий план: команда, личная копия,
способ хранения и защита отправки; явно скажи, что доступы к системам не проверяются.
Не обещай проверку Jira в режиме, в котором её не будет.

В вопросах настройки объясняй ближайший выбор и его последствия. Если человек не
знает команду, поясни возможность работать без команды, не создавая её автоматически.
При выборе хранения порекомендуй локальное, если работа с нескольких компьютеров
или личный удалённый репозиторий не требуются; дождись выбора. При остановке назови
конкретное необходимое действие и что проверишь после него. Например, при запрете
записи в папку объясни, что настройка не сохранена и нужен доступ на запись в эту
папку; не предлагай менять токен или подключение без связи с причиной. Не заставляй
человека повторять уже согласованные команду, хранение и подпись.

## 2. Проверить копию

Корень — из GIGACODE.md. Прочитай git status --porcelain=v1, текущую ветку и
настройки командного/личного слоя. Для уже выполненной проверки используй сохранённые
факты, перечитывая только то, что могло измениться перед записью; не повторяй вопросы
о подтверждённых значениях. Несохранённые общие/командные изменения — остановка
с объяснением; не stash, не reset. Личные незавершённые изменения не включай в настройку.
Единственное исключение — `.gigacode/settings.json`, если свежий setup-status
подтвердил, что изменились только локальные разрешения клиента и файл не подготовлен
к коммиту. Оставь файл как есть. Исключение не распространяется на другие изменения
или на подготовленную к коммиту версию.
Если my уже существует, не создавай её заново и не перезаписывай config.
Зафиксируй исходную ветку/HEAD и список staged/unstaged до записи. Существующие
изменения человека не присваивай настройке. Изменённый config не является автоматическим
поводом всё заблокировать: отдельно покажи diff и выясни, можно ли продолжить его настройку.
Не включай этот diff в коммит молча и не обходи общие несохранённые изменения.
Коммиту нужны имя и email: используй существующие; иначе спроси и задай --local.
До первого коммита (включая создание команды) установи node tools/kit.js hooks-install.
Ошибка установки блокирует коммит; прежние hooks не затирать, тесты не запускать.

## 3. Команда

Скачай сведения: git fetch origin --tags. Нет сети — не заявляй актуальность команд;
существующую my можно использовать, новую установку с неизвестным основанием останови.

Кандидатами считаются ветки origin/team-<код>, где код — строчные латинские буквы и цифры
без дефисов ([модель владения](../../../../docs/ownership.md)). Код и название бери из этой же
ветки: git show origin/team-<код>:config/team/config.json, поля team.id и team.name. Ветка
без такого файла или с незаполненным team.id командой не считается и не предлагается, даже
если название похоже; ветки с дефисом в коде (team-irbis-cleanup) правилу кода не следуют
и относятся к подготовке изменений, а не к командам.

Выбор команды — два шага: сначала название, потом подходящий список.

1. Спроси название свободным ответом, а не списком веток: «Как называется ваша команда?
   Если команды нет — так и скажи.» Ответ об отсутствии («нет команды», «без команды»,
   «я ни в одной») означает teamId=null: переходи к шагу 4 от стабильного тега и создание
   команды не предлагай.
2. По названию отбери кандидатов без учёта регистра — по team.name, team.id и коду ветки:
   сначала точное совпадение, затем похожие (часть названия или кода, общий префикс, другое
   написание того же слова). Предложи весь список как «<название> (код)», точное совпадение
   поставь первым и назови предполагаемым выбором, добавь вариант «Моей команды нет в списке».
   Даже при единственном точном совпадении выбор подтверждает человек: названия разных команд
   могут различаться одной буквой, а молча связать личную копию с чужой командой нельзя —
   смена команды позже требует отдельной миграции. Больше четырёх подходящих — назови их
   число, покажи не больше четырёх (точное совпадение первым) и попроси уточнить название.
   Совпадений нет — не выбирай «похожую» и не оставляй человека с пустым выбором: скажи, что
   команды с таким названием не найдено, и предложи уточнить (код, другое написание или часть
   названия) либо «Моей команды нет в списке».
3. «Моей команды нет в списке» означает команду, которой ещё нет среди опубликованных: сразу
   переходи к созданию (абзац ниже). Работу без команды не предлагай повторно — отказаться от
   команды человек мог ответом на первом шаге; продолжение без команды возможно только по его
   новому явному ответу после отказа в создании.

Существующий подтверждённый выбор (setup-status: known.team=selected или without-team)
не переспрашивай. В config/my записывай team.id команды, которую назвал человек, а не
название из чата.

Создание: название уже названо на первом шаге — спроси остальное: «Каким кодом из строчных
латинских букв и цифр без дефисов обозначить команду и кто её владельцы?». Если команда уже
есть, используй её, не перезаписывай.
До создания и отправки: «Сейчас создам команду <название> в общем репозитории, чтобы ею
могли пользоваться коллеги. Создать?» Отказ — без изменений.
После «да»: git switch -c team-<код> --no-track origin/master; создай config/team/config.json из config/team/EXAMPLE.json, заполни team.id/name/owners и только подтверждённые командные подключения.
Неиспользуемые примеры taskStores/codeStores удали, defaults очисти от ссылок на них.
Уже известные из окружения сведения не спрашивай повторно. Недостающие значения
уточни в чате; не придумывай. До коммита вызови setup-status и проверь все поля
configuration.missing: хотя бы один TODO или неизвестное состояние означает, что
настройка не завершена. Назови оставшиеся поля отдельной строкой отчёта; до их
заполнения или согласованного удаления не объявляй успех и не отправляй команду.
При configuration.state=ready выполни check --level team; затем коммит только
командного конфига и git push -u origin team-<код>.
Проверь удалённую ветку и привязку. Успех: «Команда создана. Попросите администратора
добавить владельцев команды проверяющими.»
Подтверждённый отказ в правах: сохрани заявку в новой outputs-папке, вернись на
зафиксированную исходную ветку/HEAD. Удалять можно только созданную этим вызовом
локальную team-ветку с ровно ожидаемым коммитом, если её содержимое сохранено в заявке
и человек согласовал продолжение без команды. Иначе оставь её и объясни причину.
Объясни отказ в создании команды, дай ссылку на заявку и назови согласованное
продолжение без команды. Не выдавай его за уже полученное согласие.
Сбой сети после push: сначала проверь, появилась ли ветка; неопределённый результат
не повторять и не удалять вслепую.

## Поля личного конфига

EXAMPLE.json в config/my показывает все возможные заполняемые поля и содержит TODO.
Не сохраняй его как готовый config.json без материализации:

- profile.name/email — подтверждённая локальная Git-идентичность. Для новой настройки
  прочитай только `git config --get user.name` и `git config --get user.email`; предложи
  найденные значения человеку и разреши поправить имя/ФИО и почту. Не считай Git-значения
  подтверждёнными автоматически. Недостающее спроси один раз, запиши только --local;
  глобальный Git-конфиг не меняй. Уже подтверждённый профиль повторно не спрашивай.
- teamId — выбранный код либо null без команды; имя/владельцы команды находятся в team.
- storage.mode — local или repository; storage.repositoryUrl только для repository,
  это подтверждённый адрес mine, отличный от origin. Для local поле удалить.
- taskStores/codeStores — только нужные собственные подключения; учебные записи удалить.
- defaults — только подтверждённые выбранные id/ресурсы; неиспользуемые TODO-ключи удалить.
- preferences.addressAs — форма обращения в чате, отдельно от Git-подписи.
  Сохрани точный вариант человека, например «Алексей Викторович»; «без имени» — null.
  Если создаёшь новый профиль и человек не выбрал обращение, запиши подтверждённое
  `profile.name` целиком как обращение по умолчанию. Пример `addressAs: null` в
  EXAMPLE.json не является выбором пользователя. Не выводи обращение из email
  или неподтверждённых значений Git. При восстановлении существующего профиля
  сохрани прежние предпочтения. Смена обращения не меняет profile или Git.
- preferences.addressMode — formal («вы») или informal («ты»); без поля — на «вы».
- preferences.responseDetail — brief (кратко), detailed (с объяснениями) или auto
  (по задаче, также используется при отсутствии поля).
- Остальные preferences — только отдельно согласованные пожелания; {} допустим.

Дополнительного вопроса о стиле при подтверждении профиля не задавай. Остальные
предпочтения оставь по умолчанию, если человек сам не попросил их изменить.

Составь полный личный конфиг из подтверждённых ответов, а не подставляй весь шаблон.
Personal-only сохраняет profile/teamId/storage, оставляя подключения=[] и defaults={}.
С командными подключениями также не нужны копии записей: достаточно выбранных id.
Проверь совпадение profile с локальной Git-идентичностью и storage с branch.my.pushRemote/
remote mine. При расхождении не перенастраивай молча — уточни конкретный выбор.

## 4. Личная копия и защита

Основание — origin/team-<код>; без команды — последний стабильный vX.Y.Z, достижимый
из origin/master. Тег выбирать по версии, не по алфавиту и не среди чужих веток.
Нет стабильного тега — остановка обычной настройки и сообщение владельцу поставки.
Исключение: явно согласованный пилот без команды с полным SHA и источником.
Только в этом случае прочитай [процедуру пилота](../../../../docs/pilot-install.md)
и выполни её в новой папке; не подменяй SHA текущим master и не создавай стабильный тег.
Создай git switch -c my --no-track <основание>, либо используй существующую my.
Существующую команду my не меняй переключением на другую основу без отдельной миграции.
Создай config/my/config.json из config/my/EXAMPLE.json: teamId=<код> либо null без команды. Существующий файл не перезаписывай; противоречие с выбранной командой — остановка. Источник выбора — my.teamId и team.id.
«Ваши процессы хранить только на этом компьютере или ещё в вашем репозитории?
Если не уверены — только на этом компьютере.»
Локально: убрать upstream my, git config --local branch.my.pushRemote no_push.
Свой репозиторий: mine с подтверждённым адресом, отличным от origin;
существующий mine не менять без согласия; git config --local branch.my.pushRemote mine.
Установи node tools/kit.js hooks-install: защита индекса перед коммитом и защита отправки.
При ошибке не считать защиту установленной. Тесты эта защита не запускает.
Скрипт идемпотентен, сохраняет существующий hook; не редактируй .git/hooks вручную.
После проверки сообщи фактический способ хранения по [итогу настройки](save-settings.md#проверка-сохранение-и-возврат).

## 5. Настройки и доступ

При personal-only команда уже сохранена в config/my/config.json. Перейди к проверке
и сохранению итога. Настройка подключений ниже нужна, только если она входит в поручение.

Прочитай настройки: node tools/kit.js config --json. В my не изменяй унаследованный team-конфиг.
Заполняй только собственные записи my и личные defaults. Недостающие общие сведения
команды требуют отдельной правки владельцем в team-ветке; не создавай личную запись
с тем же id, чтобы скрыть незаполненное командное подключение. Если человек выбирает
собственный ресурс, создай новый уникальный id. Не запрашивай неиспользуемые системы.
Секреты человек вводит в GigaCode, не в чат и не в файл. Не меняй глобальные настройки
Git и файлы ~/.gigacode/. Для штатного подтверждения проектных MCP после явного согласия
есть узкое исключение по [процедуре подключения](connect-existing.md): подтверждения
сохраняет сам клиент, вручную его файлы не редактируются. В проектных settings только ссылки $secret:.
Проверь нужный MCP безопасным чтением. Есть объявление без ответа — доступ не проверен.
Различай причины: отсутствие секрета, HTTP401 (не принята авторизация), HTTP403
(отказ в доступе/политике) и сетевой сбой. Выбранный сервер и имя секрета должны быть
подтверждены конфигом/ответом, не догадкой по settings. Если неизвестно, какой MCP
вернул ошибку, уточни это. Для 403 не советуй безусловно менять токен: проверь права.
Сообщение не должно объявлять токен устаревшим без подтверждения.
Пока нужного доступа нет, живую задачу не запускать. Перед ожиданием перезапуска
сохрани согласованные настройки по .gigacode/skills/rk-init/references/save-settings.md и отчёт с незавершённым доступом;
верни blocked. Если настройка уже начата и личная копия существует, при ожидании
доступа сохрани что-сделано.md с personalReady=true, connectionsReady=false и точным
препятствием; отсутствие доступа не отменяет готовую личную копию. При явном запросе
«ничего не менять» ограничься ответом и не создавай отчёт.
После добавления секрета нужен перезапуск клиента. Повторный вызов
проверяет доступ и продолжает, не пересоздаёт личную копию и не теряет ответы.

## Завершение

Для сохранения, проверки и возврата результата прочитай .gigacode/skills/rk-init/references/save-settings.md
в этой же папке скилла и выполни его. Не запускай исходную задачу самостоятельно:
затем агент продолжает её по профильной инструкции с сохранённой целью и возвращёнными personalReady/connectionsReady.
