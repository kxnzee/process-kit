# Адаптер: Почтовый справочник организации (kind = `mail-contacts`)

Мой адаптер личного уровня: чтение контактов из корпоративной адресной книги через почтовое
MCP-подключение. Нужен одному шагу — найти рабочий адрес человека по ФИО из сводной таблицы
оценок. Только чтение: отправку письма этот адаптер не описывает и не выполняет.

## Подключение

MCP-сервер: имя сервера передаёт вызывающий шаг параметром `mailServer`. Если параметр пуст,
шаг берёт единственный настроенный сервер, в имени которого встречается `email`; серверов нет
или их больше одного — остановка с причиной. Первый попавшийся сервер не подставляется.

Почтовое подключение не входит в записи `taskStores`/`codeStores` файла настроек, поэтому имя
сервера машинно не проверяется: подтверждение доступа — одно живое чтение (раздел «Пробный
прогон»). Секретов в адаптере нет; токен лежит в хранилище секретов клиента.

## Операции

| Capability | Инструмент | Тип | Вход | Результат |
|---|---|---|---|---|
| findContacts | `search_ldap` почтового сервера | read | `query` — ФИО целиком (или фамилия, или адрес); `limit` — 20 по умолчанию, максимум 100 | Список записей тем же текстовым форматом (ниже) |
| listSameName | `search_ldap` того же сервера | read | `query` — ФИО целиком, `limit` = 100 | Все однофамильцы: нужна каждая запись, чтобы различить тёзок и сослать причину честно |
| narrowSearch | `search_ldap` того же сервера | read | `query` — одна фамилия; `baseDN` — сузленное дерево (`OU={Omega},OU=GAL,…`, `OU={ЦА},OU=GAL,…`); `scope` (`sub` по умолчанию) | Записи служебных деревьев, которые общий запрос по общему основанию не отдаёт |

Сам инструмент сначала делает индексный (префиксный) запрос и только если он ничего не дал —
подстрочный; если сервер не уложился в лимит времени, это сообщается отдельной оговоркой, и пустой
ответ при этом не означает, что человека в книге нет. `baseDN` принимают только базу внутри
настроенного корня: произвольное дерево сервером отклоняется.

Структурированного тела у ответа нет — это текст построчно. Формат подтверждён живым чтением
2026-11-12 (несколько контрольных ФИО):

- блок записи начинается строкой `👤 <ФИО>` с пометками: `[B]` — подрядная учётка, `[ДЗО]` —
  дочернее общество, `{ЦА}` или `{Omega}` — служебная запись соответствующего дерева;
- дальше идут строки признаков, любого из них может не быть: `📧` — адрес почты, `📞` — внутренний
  номер, `💼` — должность, `🏢` — организация или подразделение, и обязательная `DN:`;
- у `🏢` два разных смысла: у штатной учётки там подразделение банка («Сектор экспертной поддержки
  КИБ»), у подрядной — юридическое лицо подрядчика (`ООО "Сбер2В"`, `ООО "ИЦ Философия.ИТ"`,
  `ООО "Зазекс"`). Этим признаком запись и отличается от тёзок;
- отключённые учётки выдаются вместе с активными и отличаются путем внутри DN: у отключённых он
  идёт через `OU=Disabled Objects`; адрес в такой записи может быть, но писать на него нельзя.

## Пагинация и полнота

Пагинации у `search_ldap` нет: есть `limit` (максимум 100), который обрезает список сверху.
Операция `listSameName` обязана вернуть записей меньше `limit`, иначе список усечён и считать имя
однозначным нельзя — это «не проверено», а не «запись одна». Усечение реально: 12.11.2026 на
ФИО с десятком тёзок ответ при `limit` = 10 вернулся ровно десятью записями, а полный список дал
только `limit` = 100. Число тёзок в причину ставят только по полному ответу: усечённый список —
это «не проверено», а не «записей N».

Отдельно отличается пустая выдача от непроверенной. У сервера есть известный режим, когда
фильтр по подстроке по всему дереву не успевает в серверный лимит времени и ответ приходит пустым
или с кодом `Code: 0x3` (`TIMELIMIT_EXCEEDED`). Пустой ответ без ошибки при длинном фильтре
трактуется как «не проверено»: нужен повтор более коротким фильтром (фамилия с инициалами),
и только потом — «записей нет».

## Поля и нормализация ответа

| Поле выдачи | Как читается | В результат действия |
|---|---|---|
| `DN:` | путь записи дерева | признак отключённой учётки (`OU=Disabled Objects`) и дерево (`{ЦА}`, `{Omega}`, `OU=VDR` у подрядных) |
| строка `👤 <ФИО>` | отображаемое имя и пометки `[B]`, `[ДЗО]`, `{ЦА}`, `{Omega}` | ФИО сверяется с выгрузкой нормализацией: регистр, лишние пробелы, `ё`→`е`, дефис («Иванов-Иванов» — другое ФИО) |
| `📧` | рабочий адрес | значение `email` карты |
| `💼` | должность | различие записей в причине: «аудитор ИТ и подрядчик» |
| `🏢` | у штатных — подразделение банка, у подрядных — юридическое лицо | признак различения тёзок: сверяется со столбцом выгрузки |

Сверки по табельному номеру нет — она невозможна. Живая проверка 2026-11-12 на двух контрольных
ФИО: в выгрузке `ТН` 1993789 и 2188728 (они же с ведущим нулём — 01993789 и 02188728), а в
справочнике у однофамильцев `CN=20326223`, `CN=20999137`, `CN=22028321`, `CN=23323986`; совпадений
нет ни в одном виде. Встречаются и нечисловые `CN` (`CN=Trofimov-IV`, `CN=OUT-Bykov-AM`). Различать
записи остаётся только по `🏢`, `💼` и пометкам.

Вычисленные бизнес-признаки в данные чтения не добавляются: адаптер отдаёт записи, правомерность
выбора адреса решает вызывающее действие.

## Ограничения и ошибки

- Служебные записи дерева `{ЦА}` общий запрос отдаёт — они видны по пометке `{ЦА}` в заголовке
  (проверено 12.11.2026). Записи `{Omega}` общим запросом не находятся: на контрольном ФИО
  подрядчика справочник вернул единственную отключённую запись без адреса, тогда как рабочая
  почта этого человека лежит в домене `omega.sbrf.ru` — её достают `narrowSearch` с базой этого
  дерева и запросом по одной фамилии.
- Адрес может выглядеть как номер учётной записи (`<номер>@sberbank.ru`) — это настоящий рабочий
  ящик, а не ошибка справочника.
- Ошибки доступа (`401`, `403`) и отказа сервера (`5xx`) не подменяются пустой выдачей; таймаут
  сервера — отдельный исход, он не означает «человека нет».
- Ответы содержат персональные данные: карта адресов не попадает в git и остаётся в папке прогона.

## Пробный прогон

В demo внешних вызовов нет: шаг с этим адаптером в demo не выполняется, карта адресов берётся
файлом `peopleFile`, если человек её передал.

Живое подтверждение подключения (2026-11-12, пять контрольных ФИО из рабочей выгрузки):

- подрядчик с одной живой учёткой: ответ — одна активная запись `[B]` с адресом на
  `sberbank.ru` и `🏢` = юридическое лицо из выгрузки;
- три живых адреса на одно ФИО: записи различаются `🏢` (подразделение банка, `ООО "Зазекс"`) и
  `💼`, одна из них отключена — признак различения совпал со столбцом выгрузки ровно с одной
  записью;
- десять тёзок: при `limit` = 10 ответ усечён, полный список дал только `limit` = 100;
- человек без живой учётки: обе записи прошли через `OU=Disabled Objects`, адрес в них есть, а
  писать некому;
- служебное дерево `{ЦА}`: отдельная запись с пометкой `{ЦА}` и адресом в домене `mail.ca.sbrf.ru`
  вернулась общим запросом.
