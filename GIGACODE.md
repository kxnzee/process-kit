# Process Kit — сборка сценариев из независимых действий

Process Kit — папка проекта: человек открывает её клиентом GigaCode (CLI, VS Code,
приложение) и пишет задачу словами. Ассистент находит подходящий процесс и выполняет
его шагами: **процесс → действия → адаптеры → системы**. Расширения и установки нет:
клиент видит обычный репозиторий, `GIGACODE.md` и `.gigacode/skills/`.

## Язык

- Любая твоя реплика человеку только на русском языке. Это касается и самой первой
  фразы, и фраз перед вызовом скилла или команды.
- Не объявляй, что вызываешь скилл. Не пиши «вызываю помощника», «I'll invoke».
  Сразу вызывай pp-ai-mentor.

## Структура

Одна и та же во всех ветках; уровни отличаются только набором файлов.

| Путь | Что лежит | Кто добавляет |
|---|---|---|
| `GIGACODE.md`, `README.md`, `ARCHITECTURE.md` | правила и документация | master |
| `processes/<имя>.md` | процесс: шапка-манифест и шаги-ссылки на действия | все уровни, со своим префиксом |
| `actions/<имя>/ACTION.md` + `queries/`, `templates/`, `rules/` | атомарный шаг и его данные | все уровни |
| `adapters/<система>.md` | механика обращения к системе | master; команда — только новую систему, `team-<команда>-<система>.md` |
| `context/*.md` | термины, командные и личные правила | все уровни |
| `config/sources.template.json` | шаблон координат с `TODO` | master |
| `config/sources.json` | координаты систем (id, адаптер, `mcpServer`, проект, доска, defaults) | командная ветка; в master его нет |
| `tests/<имя>/*.json` | вымышленные данные для демонстрационного прогона и эталоны сверки | все уровни |
| `.gigacode/settings.json` | MCP-серверы; на месте токена — ссылка на секрет `$secret:<имя>/<ключ>` | master |
| `.gigacode/hooks/pre-push` | защита общего репозитория: личная ветка, заметки, перезапись, удаление веток | master |
| `.gigacode/skills/pp-ai-*/SKILL.md` | служебные скиллы: помощник, настройка, исполнитель, конструктор, перенос изменений в команду и в общий уровень | master |
| `tools/` | скрипты проверки раскладки и установленного hook (`validate.js`, `check-report.js`, `check-prepush.js`) | master |
| `TEAM.md` | название команды | командная ветка |

## Основная ветка

Основная ветка — `master`. В текстах скиллов и правил её имя руками не пишется: агент
берёт основную ветку так:

1. ветка, на которой человек оказался сразу после клонирования (`origin/HEAD`);
2. иначе `master`.

## Уровни — ветки

| Уровень | Ветка | Кто правит | Что видит |
|---|---|---|---|
| общий | `master` | разработчик набора, через PR из `master-*` | только общие файлы |
| командный | `team-<команда>`, ответвление от `master` | команда, через PR | свои файлы + общие |
| личный | `my`, ответвление от командной ветки или от `master` | сам человек | личные + командные + общие |

**Ссылки идут только вверх по этой таблице:** личная ветка → командная → `master`.
Личный процесс ссылается на командное и общее действие; командный — на общее. Обратного
направления нет: ни общие, ни командные файлы не ссылаются на имена, которые есть только
в личной или командной ветке, и агент эти имена им не подставляет. Общий файл со ссылкой
на имя, которого нет в его ветке, — ошибка раскладки.

Клиент про уровни ничего не знает. Агент определяет уровень по текущей ветке:
`git branch --show-current`. Ветка `master` — только общие файлы, файлов уровней здесь
нет вовсе. Ветка `team-*` — общие файлы плюс файлы с префиксом команды. Ветка `my` —
плюс личные файлы с префиксом `my-`. Единственные рабочие ветки — `master-<имя>` (правки
общего уровня, только через PR) и ветка команды, ответвлённая от `team-<команда>`; уровень
у них — по имени: `master-*` — общий, ветка команды — командный. Рабочее место переноса —
служебная ветка `promote/master/<тема>` (перенос в общий) или `promote/team-<команда>/<тема>`
(перенос в команду); уровень проверка распознаёт по имени, при нестандартном случае его можно
задать явно: `node tools/validate.js --level …` (прежнее имя `tools/check-layout.js`
принимает те же аргументы; `--root` и `--process` — не уровень). Ветка с другим именем —
остановиться и спросить, какого она уровня.

## Правило имён

| Уровень | Префикс файла | Пример |
|---|---|---|
| общий (`master`) | без префикса; служебные скиллы — `pp-ai-` | `processes/sdd-stories-report.md` |
| командный (`team-<команда>`) | `team-<команда>-` — имя ветки целиком | `processes/team-sws-weekly-report.md`, `context/team-sws-team.md` |
| личный (`my`) | `my-` | `processes/my-standup.md`, `context/my-preferences.md` |

- Папок по уровням нет: командные и личные файлы лежат в тех же папках, что и общие, и
  отличаются только префиксом. Подпапки внутри `processes/`, `adapters/`, `context/` не
  создаются.
- Отчётный процесс — маршрут заканчивается текстовым отчётом (последний шаг — действие
  `compose-report`) — получает постфикс `-report`: `processes/sdd-stories-report.md`;
  командный и личный варианты наследуют его (`team-sws-<имя>-report`, `my-<имя>-report`).
  Набор эталонов `tests/<имя>/` называется по имени процесса, вместе с этим постфиксом,
  и префикса уровня не имеет.
- Данные действия (`queries/`, `templates/`, `rules/`) называют по имени процесса, который
  их использует, — вместе с его постфиксом: запрос шага `fetch` лежит как
  `queries/sdd-stories-report.md`. Это имя не проверяется механически: оно задаётся в шаге
  значением параметра (`query: sdd-stories-report`), а не ссылкой на файл, поэтому
  расхождение ловится только при исполнении шага. Второму процессу те же данные не
  подставить: он заводит свой файл под своим именем.
- **Исключение — `tests/`:** там подпапки нужны, по одной на проверяемый набор
  (`tests/<имя>/`), и префикса уровня у них нет: файлы набора проверяют общий или командный
  процесс, а не принадлежат человеку. Вымышленные данные прогона (`fixture.json`) лежат в
  папке своего набора, рядом с эталонами; отдельного каталога `config/fixtures/` нет.
- Свой вариант чужого файла — новый файл под своим префиксом, а не правка чужого. Общий
  процесс `processes/sdd-stories-report.md` в ветке `team-sws` становится
  `processes/team-sws-sdd-stories-report.md`, в личной ветке —
  `processes/my-sdd-stories-report.md`; действие `actions/run-query/` —
  `actions/team-sws-run-query/ACTION.md` (префикс получает и папка действия — у всех трёх
  префикс стоит в начале имени). Это касается и копии «один в один»: даже если меняется
  одна строка, файл — свой.
- Имя со своим префиксом ничуть не сильнее общего: одноимённых файлов нет, они сосуществуют
  под разными именами, и процесс, который должен взять свой вариант, обязан ссылаться на
  него явно — шагом `действие: team-sws-run-query`. Ссылка на имя без префикса возьмёт
  общий файл. Молчаливой подмены («взять свой, если есть») нет: какой файл взят, видно в
  выводе прогона по `processFile`/`actionFiles`.
- Ссылаться можно только вверх по уровням: личный файл — на командные и общие, командный —
  на общие. Общий или командный файл со ссылкой на имя из более близкого уровня — ошибка
  раскладки, а не повод подставить файл из другой ветки.
- Чужие файлы не правятся, а дополняются своими: нужно другое поведение — свой файл
  с префиксом своего уровня.
- Если чужой файл всё же поправлен, конфликт при обновлении решает тот, кто правил, —
  общая ветка о правке не знает и продолжает меняться сама.
- Исключение по номенклатуре — `config/sources.json`: имя фиксированное, потому что его
  читает исполнитель; командная ветка создаёт его у себя, в `master` его нет.

## Где что ищет агент

Ищется **в рабочей копии открытой ветки**, без обращения к другим ветвям и без
`git show` чужих деревьев:

- процесс — `processes/<имя>.md`;
- действие — `actions/<имя>/ACTION.md`, его данные — в его папке (`queries/`, `templates/`, `rules/`);
- адаптер — `adapters/<система>.md`; имя берётся из записи конфига (`adapter`/`kind`);
- конфиг — `config/sources.json`; файла нет → сообщить, что нужна настройка (её делает
  скилл `pp-ai-init`), и не подставлять другой инстанс;
- контекст — **все** файлы `context/*.md`.

## Контекст

Перед работой прочитать все файлы `context/*.md` и подать их в каждый шаг. При
противоречии командный файл (`team-<команда>-*.md`) и личный (`my-*.md`) важнее общего, а
личный важнее командного. Файлы контекста — факты и пожелания, а не рецепты: рецепт
исполнения всегда берётся из `ACTION.md`.

## Три понятия модели

1. **Действие** (`actions/<имя>/ACTION.md`) — атомарный шаг-пакет. Контракт в заголовке
   файла (`kind`, `adapter`, `consumes`, `produces`), ниже — рецепт исполнения; собственные
   данные лежат рядом в той же папке. Виды:
   - `source` — обращение к внешней системе через адаптер (пример: «выполнить запрос»);
   - `transform` — чистая переработка артефактов предыдущих шагов без сети (пример: «составить отчёт»);
   - `act` — действие по результатам, имеющее внешний эффект (пример: «отправить письмо»);
     выполняется только после явного подтверждения пользователя; может быть и последним
     звеном маршрута после трансформаций.
   Действие — не скилл GigaCode: клиент его не регистрирует, файл читает исполнитель по
   имени из процесса. Поэтому ограничение на вложенность скиллов к действиям не относится.
2. **Процесс** (`processes/<имя>.md`) — маршрут из шагов. Шаг **ссылается** на файл
   действия или другой процесс — текст действия в процесс не копируется никогда.
   Шаги образуют маршрут: `entry` → `следующий:`, развилки — шагом `branch`.
3. **Адаптер** (`adapters/<система>.md`) — механика обращения к системе: инструменты MCP,
   пагинация, известные ограничения.

## Скиллы и действия

`.gigacode/skills/` — только «движок»: четыре служебных скилла `pp-ai-*`. GigaCode
регистрирует их сам, поэтому они лежат плоско: `.gigacode/skills/<имя>/SKILL.md`.
Атомарные шаги сюда **не** кладутся, новый процесс или шаг **не** создаёт новый скилл.

Командный (`team-<команда>-*`) или личный (`my-*`) скилл — исключение: только когда человеку
нужна отдельная команда «/», которую нельзя выразить процессом. Ожидаемое число скиллов
в ветке — единицы, а не десятки. Скиллы тоже лежат плоско и называются по тому же правилу
префиксов.

## config/sources.json

Координаты и дефолты, без критериев отбора. В поставке рабочего конфига **нет**: в
`master` лежит только `config/sources.template.json` — формы полей и `TODO` без значений.
Командная ветка создаёт у себя `config/sources.json` из шаблона (это делает скилл
`pp-ai-init` вместе с командой) и заполняет; поля без подтверждённого значения остаются
`TODO`. Личная ветка при необходимости правит копию в своей ветке — общая от этого не
меняется.

Нет `config/sources.json` — живой прогон останавливается: назвать отсутствующий файл и
сказать, что нужна настройка. Не подставлять координаты из шаблона, примеров или другой
ветки.

## MCP-серверы и токены

`.gigacode/settings.json` из `master` описывает MCP-серверы; на месте токена стоит ссылка
на секрет вида `$secret:<имя>/<ключ>` (например, `$secret:pp-ai-jira/x-jira-token`).
Доступами заведует сам клиент GigaCode (CLI, VS Code, десктопное приложение): человек
добавляет секрет штатным способом, клиент подставляет значение по ссылке, и после
перезапуска сессии сервер работает. Отдельного файла доступов в проекте нет и не создаётся.
Значения токенов не выводятся ни в чат, ни в отчёты.
Командная и личная ветки `settings.json` не меняют; свои личные серверы человек добавляет
в глобальные настройки GigaCode.

## Приоритет значений при прогоне

Аргументы вызова → `параметры` шага → `params` процесса → `defaults` из
`config/sources.json` → значения, зашитые в действии.

## Как исполняется шаг

Изоляция шагов — часть модели, а не рекомендация: у каждого шага свой пакет входа
(рецепт действия, нужный адаптер, данные действия, артефакты по `consumes`, значения
параметров), и наружу шаг отдаёт только свой `produces` — файлом в каталоге прогона
`outputs/<имя>/.run/` в корне папки (см. раздел «Где лежат результаты»).
Сырые ответы систем, диффы и содержимое шаблонов в общий контекст прогона не переносятся.
Артефакт передаётся следующему шагу **путём к файлу**, поэтому каждый шаг можно проверить
отдельно по его файлу. `outputs/` в `.gitignore`.

## Где лежат результаты

Все пути считаются от корня папки: ROOT=$(git rev-parse --show-toplevel).
Каждый запуск — одна папка: $ROOT/outputs/<имя>/.
- Процесс по задаче человека: файлы для человека и итог.md — в $ROOT/outputs/<имя>/;
  служебные файлы прогона (run.md, trace.jsonl, артефакты шагов) — в
  $ROOT/outputs/<имя>/.run/.
- Настройка: $ROOT/outputs/<имя>/что-сделано.md.
- Заявка: $ROOT/outputs/<имя>/заявка.md.
- Личная история запусков: $ROOT/.history/runs.jsonl.
Имя папки: <ГГГГ-ММ-ДД>_<1–4 слова через дефис>, без пробелов, до 40 символов после
даты; если такая папка есть — добавь -2, -3. Существующую папку не перезаписывай.
Результаты и служебные файлы прогона создавай только в outputs/<имя>/: не в корне
папки и не прямо в outputs/.
Какой файл куда (проверяемо, без толкований):
- артефакт КАЖДОГО шага — в outputs/<имя>/.run/<NN>-<имя шага>.<расширение>;
- результат ПОСЛЕДНЕГО шага процесса — тем же шагом вторым файлом в outputs/<имя>/ под
  именем по смыслу («отчёт.md», «письмо.md», «таблица.md»); это файл для человека;
- переносить, копировать и переименовывать файл из .run/ нельзя: папка запуска получает
  свою запись от самого шага;
- артефакты промежуточных шагов в корне папки запуска не появляются никогда;
- в итог.md строка «Файлы в этой папке» перечисляет только файлы, реально лежащие рядом
  с итог.md; служебная подпапка в ней не упоминается.

Зарезервированные имена папок (часть <коротко>), чтобы каждый вид работы сразу ложился
по правилу:

| <коротко> | Кто создаёт |
|---|---|
| настройка | pp-ai-init |
| заявка-команда-<код> | заявка на команду |
| заявка-подключение-<система> | заявка на подключение |
| проба-<задача> | пробный прогон на тестовых данных |
| обновление | будущее «обнови Process Kit» |
| поделиться-<процесс> | будущее «Поделись с командой» |
| сборка-<процесс> | будущая сборка процесса в экстеншен |

- **Пробный прогон** идёт в папку `<дата>_проба-<задача>`; в `итог.md` строка «Чем
  закончилось» начинается со слов «Пробный прогон, ничего не отправлено».
- **Служебные файлы шагов** в `.run/` называются `<NN>-<имя шага>.<расширение>`
  (например, `01-jira-search.json`), где NN — номер шага. После каждого завершённого шага
  исполнитель пишет `.run/state.json`: номер и имя последнего завершённого шага и
  параметры прогона.
- **Строка истории** в `.history/runs.jsonl` содержит поле `output` — имя папки запуска.
- **Два вида данных в `.history/`**: `runs.jsonl` и пожелания человека — память
  помощника, не чистится; `.history/cache/` — то, что можно собрать заново, её можно
  удалить в любой момент. Пересобираемое пишется только в `.history/cache/`.
- **Данные человека не версионируются**: `outputs/` и `.history/` не попадают в git;
  их нет в `requires` манифестов, в «Поделись с командой» и в сборке процесса.
- **Во время прогона** скиллы и действия пишут только в `outputs/` и `.history/`.
  В `processes/`, `actions/`, `adapters/`, `context/`, `.gigacode/` пишется только то,
  что человек сохраняет коммитом (`my-*` файлы, `config/sources.json` при настройке,
  новый процесс из конструктора).
- **Ссылки внутри действия** на его собственные файлы — относительно папки действия:
  `actions/<имя>/templates/x.md` пишется как `templates/x.md`.
- **Старые прогоны** (`runs_keep_days`) удаляются только как подпапки `.run/` в папках
  `outputs/<имя>/` старше срока; сами папки, `итог.md` и файлы для человека не удаляются
  никогда.

## Защита и запреты

- Правки `master` — только через ветку `master-*` и PR; в Bitbucket прямой push
  в `master` и `team-*` запрещён правилами веток. Хука GigaCode нет:
  защита — правила веток, `.gitignore` и запрет отправки личной ветки средствами git.
- Чужие файлы (команды, `master`) не правятся: своё добавляется своим файлом с префиксом.
  Единственное исключение — исправление ошибки раскладки по прямой просьбе владельца
  уровня; об этом говорится отдельной строкой.
- Личная ветка `my` не отправляется в общий репозиторий. Для страховки:
  `git branch --unset-upstream`, `git config branch.my.pushRemote no_push` и `pre-push`
  из `.gigacode/hooks/pre-push`, установленный в `.git/hooks/pre-push` (файл hook в
  репозиторий не попадает). Скрипт сверяет **адрес отправки**: в общий адрес (`origin`)
  личная ветка не уходит, в собственный репозиторий (`mine`) уходит; служебные заметки
  `refs/notes/*` в общий адрес тоже не уходят. Отправляется только конкретная ветка.
- Порядок работы с git, обязательный для всех шагов и скиллов:
  - **сначала посмотреть**, что в папке: `git status --porcelain` и
    `git branch --show-current`;
  - **в набор добавлять только свои файлы поимённо**: `git add <файл> <файл>`.
    Широкие `git add -A`, `git add .`, `git commit -a`, `git add -u` запрещены — рядом
    может лежать чужая работа;
  - **своё — в отдельной ветке**: `git switch -c <имя> --no-track`, без `--no-track`
    ветку не создавать;
  - **отправка — только одна ветка поимённо**: `git push origin <ветка>`; общая отправка
    всех веток и зеркал, принудительная перезапись истории и отправка заметок в общий
    репозиторий запрещены;
  - **удаляющие команды — только по прямой просьбе человека, с объяснением последствий**:
    `git reset --hard`, `git clean -fd`, `git checkout -- .`, `git restore .`,
    `git stash drop`/`git stash clear`, `git branch -D`, `git rebase -i`,
    `git update-index --assume-unchanged`. Если человек просит такую команду — сначала
    сказать, что именно она уничтожит, и спросить отдельно;
  - **сбой или непонятное состояние** — остановиться и назвать, что не сработало. Не
    исправлять наугад и не удалять чужое;
  - глобальные настройки git (`--global`, `--system`, `~/.gitconfig`, `core.hooksPath`)
    не меняются: всё пишется в `.git/config` этой папки.
- Доступами заведует клиент GigaCode: токенов, файлов с ними и их подстановок в проекте
  нет и не создаётся. Глобальная `~/.gigacode/` только читается: ничего туда не пишем.
- Зацикливание (повтор пары «процесс, шаг») — ошибка процесса: остановиться и сообщить,
  в каком процессе маршрут замкнулся.

## Как запускать

Человек склонировал репозиторий, открыл папку и написал задачу словами — больше ничего.
Помощник на первой задаче сам вызывает настройку: команда, ваша личная копия, где брать
данные, доступы, проверка раскладки. Настройка (`pp-ai-init`) показывает
план и ждёт «да», вносит изменения только в открытую папку, системы не опрашивает (кроме
одного проверочного чтения) и процессы не запускает; повторный запуск ничего настроенного
не перезаписывает. После настройки помощник возвращается к задаче человека.

- Помощник `pp-ai-mentor`: `/pp-ai-mentor <задача словами>` — проверяет готовность,
  подбирает процесс по описанию и передаёт его исполнителю.
- Исполнитель `pp-ai-run-process`: `/pp-ai-run-process [process=<имя>] [param=<значение> …]`.
  Демонстрационный прогон без обращения к системам:
  `/pp-ai-run-process dataFile=tests/<имя>/fixture.json` — действия-источники берут
  выборку из указанного файла и помечают прогон как демо.
- Конструктор `pp-ai-create-process`: `/pp-ai-create-process` + описание сценария словами.
  Файлы кладутся по уровню владельца значения: общее — в ветку `master` (только через PR),
  настройка команды — в файл с префиксом команды, личное — в файл с префиксом `my-`.
- Перенос изменений: `pp-ai-promote-changes-team` — из открытой папки в командную ветку;
  `pp-ai-promote-changes-master` — в общую. Оба собирают изменённые файлы, относят каждый к
  уровню, показывают список и спрашивают «всё подходящее или выбранное»; файлы чужого
  уровня в выбор не попадают. Отправка и запрос на изменения — только после отдельного «да».
  Содержимое файлов перенос не меняет.
- Проверка раскладки: `node tools/validate.js` (прежнее имя `tools/check-layout.js` тоже
  работает). Раскладку ветки она берёт из имени: `master` и `master-*` — общий уровень,
  `team-<команда>` и `promote/team-<команда>/<тема>` — командный, `my` — личный;
  `promote/master/<тема>` — общий, при нестандартном имени уровень задаётся флагом
  `--level` с кодом команды. Сверка прогона с эталоном —
  `node tools/check-report.js` по набору `tests/<имя>/`.

## Правила поведения агента

- Каждый шаг исполняется по рецепту своего файла действия; текст действия агент
  не выдумывает и не дублирует в диалоге.
- Ссылки разрешаются только внутри открытой ветки и только вверх по уровням. Имя, которого
  нет в ветке, — остановка с указанием файла и ссылки.
- Каждое условие отбора подтверждается полем ответа системы. Не подтверждено → раздел
  «Проверить не удалось», а не «не найдено».
- Система определяется полем `mcpServer` в `config/sources.json`. Сервер или инструмент
  недоступен в сессии → остановиться и сказать какой; не подменять другим сервером.
- Действия вида `act` выполняются только после явного «да» пользователя на показанный
  черновик эффекта.
- Ветвление: предикаты шага `branch` оцениваются строго по артефактам выполненных шагов;
  заходить в шаг, на который нет маршрута, запрещено.
- Факты, которые агент узнал о системах (реальные имена типов, статусы, проекты), он
  докладывает человеку, а не вписывает в `master`: их место — в файлах своего уровня.

## Как агент говорит с человеком

- **Первое действие на любое сообщение человека с рабочей задачей** и на вопрос
  «что ты умеешь», «какие процессы есть» — вызвать скилл `pp-ai-mentor` со словами
  человека: «сделай сводку…», «покажи отчёт…». Сам агент процессы не ищет, шаги не
  подбирает, настройку не проводит и исполнителя не вызывает.
- **Язык ответа — язык человека, с первой фразы.** Человек пишет по-русски — весь ответ
  по-русски, включая первую фразу; служебные пересказы шагов внутри тоже по-русски.
- **Пиши по правилам `context/writing-style.md`**: и в чате, и во всех текстах для
  человека (сводки, письма, отчёты о настройке). Если правило противоречит пожеланию
  человека из его личного контекста, выполняй пожелание.
- **Запрещённые слова в разговоре с человеком:** ветка, master, team-, префикс, скилл,
  конфиг, sources.json, адаптер, фикстура, MCP, PR, слияние, коммит, а также смержить,
  смерженный, мерж, слить, координаты, координаты подключений, рабочее пространство,
  workspace, имена файлов и команды «/». Вместо них: процесс, действие, подключение,
  контекст, команда, принять, принятые изменения, адрес проекта в Jira, где брать данные,
  ваша папка, ваши настройки.
  Запрет касается разговора; в файлах подхода термины остаются как есть.
- **Замены для неудобных слов:**

  | Нельзя | Говори |
  |---|---|
  | смержить, смерженный, мерж, слить | принять, принятые изменения |
  | координаты, координаты подключений | адрес проекта в Jira, где брать данные |
  | рабочее пространство, workspace | ваша папка, ваши настройки |
  | Story, Bug, Task без пояснения | истории (Story), ошибки (Bug), задачи (Task) |

  Тип задачи можно оставить в скобках так, как он называется в Jira, но сначала скажи его по-русски.
- **Не предлагать человеку вызвать** `pp-ai-init`, `pp-ai-run-process`,
  `pp-ai-create-process`: их вызывает помощник (`pp-ai-mentor`), а человек просто пишет
  задачу словами. Помощник сначала убеждается, что установка готова, и сам проводит
  настройку — человеку для этого ничего вызывать не нужно.

## Прозрачность работы

Человек работает в Process Kit в своей роли — аналитик, менеджер, тестировщик, разработчик.
Команды, скрипты и файлы набора он не читает: о работе узнаёт из ответа и видит последствия.
Поэтому:

- **Перед любой работой — план простыми словами:** что прочитаешь, что сделаешь, что
  изменишь на его компьютере или в системах. Две-четыре строки, без служебных терминов.
- **Перед каждым обращением к человеку за действием или подтверждением** — одна строка
  простыми словами, что произойдёт и зачем. Это относится и к случаю, когда GigaCode сам
  спрашивает разрешение на команду: сначала объяснение, потом команда. Например: «Сейчас
  скачаю обновления Process Kit, ваши файлы это не изменит».
- **После каждого шага настройки** — одна строка: что сделано.
- **Что сделал** — отчёт простыми словами: «outputs/<дата>_настройка/что-сделано.md»
  (шаги, что запускалось, что изменено). В чат — полный путь к файлу.
- **Где лежат результаты** — в папке `outputs/` в корне папки и в `.history/`; служебный
  журнал прогона — в подпапке `.run/` внутри папки запуска, не в корне папки. Точные
  пути — в разделе «Где лежат результаты».
- Списков разрешённых команд не заводится и в настройки клиента ничего для этого не
  добавляется: разрешения спрашивает сам GigaCode, а агент объясняет, что делает.

## Только локальные изменения

Ни одна команда Process Kit не меняет глобальные настройки компьютера:

- `git config` — только без `--global` и `--system` (запись в `.git/config` этой папки);
  команды с `--global`/`--system` запрещены;
- нет `user.name`/`user.email` для коммита — не задавать их глобально: спросить человека и
  задать только для этой папки, либо сказать, что их нужно задать;
- не трогать `~/.gitconfig`, `~/.gigacode/`, глобальные git hooks (`core.hooksPath`),
  credential helper и переменные окружения профиля оболочки;
- `pre-push` ставится только в `.git/hooks` этой папки;
- `tools/validate.js` проверяет, что в текстах скиллов нет `--global`, `--system`,
  `~/.gitconfig`, `~/.gigacode`, `core.hooksPath`.

Создатель сущностей (`pp-ai-create-process`) следует тем же ограничениям: он не выдумывает
значения координат, не правит конфиг по ходу сборки и пишет в общие файлы только по решению
владельца набора через PR, отдельно предупредив, что это правка общей ветки.

Для разработчика Process Kit: эталоны структуры, файлов и реплик лежат в
docs/reference/ (как должно быть), заготовки для копирования — в docs/templates/ (что
копируют, заменяя `<…>`). Собирая новый процесс, действие или подключение, бери заготовку
и правь её; эталон читай, когда нужно понять устройство. Читай их только при правке
Process Kit (или сборке нового процесса), не при работе с задачей человека.
