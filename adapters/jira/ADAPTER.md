# Адаптер: Jira (kind = `jira`)

Как говорить с системой задач этого типа. Инструменты и ограничения — здесь; критерии
отбора задач — в описании запроса вызывающего процесса `processes/<имя>/queries/<запрос>.md` (командные
и личные варианты лежат рядом, в папках вызывающих процессов соответствующего уровня). Здесь их не менять.

Исторические наблюдения ниже не заменяют проверку схемы объявленных инструментов
в текущей сессии. Не конструируй неподдерживаемые параметры по одному примеру.

## Операции

MCP-сервер берётся из `taskStores[].mcpServer` в разрешённых настройках `tools/lib/config/config.js`: имя сервера,
объявленного в настройках, вписывает команда при настройке. В настройках этого набора
объявлен `pp-ai-jira` (рядом — `pp-ai-jira-delta`, если доступы к Jira разделены).
Имена инструментов строятся от этого имени: `mcp__<mcpServer>__<имя>`, для `pp-ai-jira` —
`mcp__pp-ai-jira__<имя>`.

| Capability из конфига | Инструмент | Зачем |
|---|---|---|
| `searchIssues` | `search_issues` | первичная выборка по JQL |
| `getIssues` | `get_issues` | батч по списку ключей: статус, метки, тип, исполнитель; с флагами `changelog` и `include_custom_fields` — ещё история изменений и значения кастомных полей каждой задачи |
| `getIssue` | `get_issue` | подробности по одной задаче |
| `getIssueLinks` | `get_issue_links` | связи задачи (`consists of` / «состоит из» и прочие) с ключами и статусами узлов |
| `addComment` | `add_comment` | публикация комментария в задаче — только для действий класса `act` |

`add_comment` принимает ключ задачи и текст комментария; возвращает id комментария — это
и есть подтверждение публикации. Других способов писать в задачу адаптер не даёт: правка
полей и статусов — не его дело.

Если нужного инструмента нет в объявленных — сначала загрузить его `tool_search` с запросом
`select:mcp__pp-ai-jira__search_issues,mcp__pp-ai-jira__get_issues` (имя сервера — из
конфига). Если и после загрузки инструментов нет — сервер не поднят в этой сессии:
остановить работу и сообщить человеку (лечится перезапуском MCP/сессии), не подменять
выборку догадками и не искать задачи по локальным файлам.

Операции `searchIssues`, `getIssues`, `getIssue`, `getIssueLinks` — чтение (`read`); `addComment` — запись
(`write`) и только для действий класса `act` после явного подтверждения человека.

## Пробный прогон

В demo экшен использует только явно переданный dataFile и не обращается к Jira.
Для run-query поле fixture.query совпадает с точным queryFile, а входные задачи
читаются из fixture.result. Файл процесса может содержать разделы нескольких шагов;
каждый экшен читает свой раздел по собственному контракту. Форма демоданных не
определяется одним названием адаптера. Демо не подтверждает доступ к живой системе.

## Правила JQL (экономят прогоны)

- **Фильтр по `issuetype` указывать всегда.** Запросы без него на части инсталляций падают
  с внутренней ошибкой сервера. Рабочий пример формы (подставьте свои значения):
  `project = <КЛЮЧ> AND issuetype = <ТИП> AND labels in (<МЕТКА>) AND status not in (<СТАТУСЫ>) ORDER BY updated DESC`.
- Поле окна задаёт запрос. Для окна по истории переходов нельзя подменять его created/updated:
  такое сужение поиска потеряет подходящие задачи.
- `status not in (...)` — именно исключение: в выборку попадают все статусы, кроме перечисленных.
- Пагинацию читать до конца (`isLastPage`/`nextPageStart`), счётчик «сколько прочитано»
  выносить в отчёт.

## Ограничения выдачи

- `get_issue`/`get_issues` **не отдают** Epic Link/parent — связь с эпиком так не получить;
  если отчёт требует эпика, это отдельный инструмент и его доступность надо проверять.
- `get_issue_links` отдаёт связи задачи с ключами и статусами связанных узлов; тип связи
  приходит в `type.name` («consists of» / «Состоит из»), направление — в `inwardIssue`/
  `outwardIssue`. Тип связи фильтруется по ответу, а не отдельным запросом на каждый тип.
  Подтверждено 2026-11-07: на пяти стори возвращённые связи совпали с записями `consists of`
  в истории изменений.
- Те же связи видны в истории изменений: запись поля `Link` содержит тип связи и ключ узла
  (текст вида «This issue Состоит из SBAR-6656»), снятая связь помечена как удалённая. Когда
  историю задачи всё равно читают, ключи дерева берут оттуда, а `get_issue_links` остаётся
  способом подтвердить направление связи или найти узлы, если записей `Link` нет. Отдельный
  вызов ради дерева нужен только когда историю не читают вовсе: раньше именно это и стоило
  дороже всего.
- `get_issues` принимает те же флаги, что и одиночное чтение: `changelog: true` отдаёт полную
  историю изменений каждой задачи пакета без усечения, `include_custom_fields: true` — её
  кастомные поля. **Без второго флага `custom_fields` приходит пустым**: не видно ни значения
  поля «КЭ», ни привязки PR, и задача ложно выглядит пустой. Подтверждено 2026-11-07: на 20
  ключах история и поля каждой задачи совпали с одиночным чтением тех же задач.
- Пакет с историей велик: порядка 30 КБ на задачу, около 0,6 МБ на 20 ключей. Ответ сохраняется
  в файл и разбирается скриптом с выбором нужных полей; переносить такую выдачу целиком в
  контекст или в артефакт нельзя.
- Поле справочника («КЭ» — `customfield_18300`) приходит в `custom_fields` списком
  `[{ id, value }]`, где `id` — число справочника без префикса (`3296913`). Сверять его с кодом
  КЭ из настроек нужно после нормализации: префикс `CI` и ведущие нули в настройках есть,
  в выдаче их нет.
- `get_issues` брать батчами ≤ `limits.getIssuesBatchMax` (по умолчанию 20) ключей за вызов.
- Метки (`labels`) приходят в выдаче `get_issues` — финальную проверку по метке делать
  именно по ним: JQL и фактическая выдача могут разойтись из-за регистра или алиаса.

## Проверка имён типов задач и статусов (при первом прогоне на новой инсталляции)

Имена типов и статусов в разрешённых настройках `tools/lib/config/config.js` — предположение. Подтвердить одним из:

1. справочнику метаданных, если инструмент объявлен и доступен;
2. по известной задаче нужного типа через get_issue прочитать фактические тип и статус.
Пустая поисковая выдача сама по себе не доказывает правильность имени типа.

Подтверждённые значения фиксируются в разрешённых настройках `tools/lib/config/config.js` **командной ветки** (или в
личной копии, если инсталляция личная). Этот файл про механику, не про значения. По ходу
прогона агент только докладывает фактические значения и место, куда их стоит внести.

## Статус проверок этого адаптера

| Факт | Статус |
|---|---|
| JQL без `issuetype` падает; батчи `get_issues`; эпик-связь недоступна | подтверждено при первом внедрении настольной инсталляции |
| пакет `get_issues` с `changelog` и `include_custom_fields` заменяет одиночные чтения: та же полная история и те же поля | подтверждено 2026-11-07 на 20 ключах |
| MCP-сервер `pp-ai-jira` (имя из `taskStores[].mcpServer`) доступен в текущей сессии | проверяется `pp-ai-init` и первым шагом прогона |
| имена типов задач и написание статусов | у каждой команды свои — подтверждаются при первом прогоне |
| инструмент `add_comment` существует и возвращает id комментария | не проверено |

## Привязка PR: поле «Development»

`get_issue` или пакетный `get_issues` с `include_custom_fields: true` отдают поле «Development»
(`customfield_23400`). В `value` лежит текст со встроенным `devSummaryJson` — сводка панели
разработки. Из неё берут
`pullrequest.overall` (`count`, `state`, `stateCount`, `details.openCount`/`mergedCount`/
`declinedCount`, `lastUpdated`), `pullrequest.byInstanceType` (какая система кода) и
`repository.overall.count` (число коммитов). Идентификаторов, ссылок и веток PR в сводке **нет** —
она годится для «привязан ли принятый PR и сколько», а какие это запросы, решается чтением в
системе кода (`adapters/bitbucket/ADAPTER.md`).

| Наблюдение | Статус |
|---|---|
| поле отдаёт сводку только при `include_custom_fields: true`; без него поля нет | подтверждено 2026-11-06 |
| пакет отдаёт сводку по каждой задаче вызова — на узлы дерева отдельных чтений не нужно | подтверждено 2026-11-07 на 20 ключах |
| часть узлов отвечает ошибкой сервиса вместо сводки | подтверждено 2026-11-06 — это «не проверено», не «PR нет» |
| сводка засчитывает и релизные PR, где ключ только перечислен в заголовке (`merged = 1`, `commits = 0`) | подтверждено 2026-11-06 |
| `text ~` и `comment ~`, имена типов и полей | см. разделы выше |
