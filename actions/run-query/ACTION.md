name: run-query
description: Делает выборку в системе задач или в репозитории по правилам запроса
kind: source
adapter: по системе — имя из config/sources.json: taskStores[].adapter / codeStores[].adapter (например, jira)
consumes:
  artifacts: [report-data (только в режиме «чтение текста»)]
  params: [query, window, taskStore, dataFile(опционально)]
produces:
  report-data: выборка задач и PR, собранная по правилам запроса, вместе со счётчиками и списком непроверенного
  records-text: текстовые поля объектов выборки, нужные для проверки по правилам (только в режиме «чтение текста»)
---

# Действие: выполнить запрос через адаптер

Один шаг процесса. Обращается к нужному источнику через его адаптер и отдаёт
выборку следующему шагу. О критериях отбора здесь ничего не решается — их читает
исполнитель из файла запроса.

## Рецепт исполнения

0. Определить режим запроса по заголовку файла `queries/<query>.md`:
   - `поиск выборки` (по умолчанию) — шаг ищет объекты по критериям запроса;
   - `чтение текста` — шаг получает готовую выборку артефактом `report-data` и
     дочитывает у её объектов поля, перечисленные в запросе (`fields`). Поиск не
     повторяется: критерии отбора уже применены, второй проход фильтрации даст
     расхождение между шагами.
   В режиме чтения текста `produces` — только `records-text`; `report-data`
   остаётся артефактом первого шага и в отчёт о прогоне попадает как есть.
1. Взять файл запроса `queries/<query>.md` из папки этого действия в открытой ветке; если
   имя в параметре задано с префиксом уровня (`team-<команда>-…`, `my-…`) — файл с этим
   префиксом. Зафиксировать фактически использованный файл (`queryFile`).
   Если файла с именем `<query>` нет, а шаг-источник в процессе один — взять единственный
   файл в `queries/` и назвать его в `queryFile`: так прогон не ломается на имени, которое
   осталось от процесса-предшественника. Двух и более посторонних файлов — не угадывать,
   остановиться и назвать, какого файла не хватает.
2. Если задан `dataFile` — читать выборку из указанного файла, сеть не трогать,
   пометить весь прогон как **ДЕМО** (данные фикстуры ничего о реальных задачах не говорят).
   Фикстура описывает один шаг: файл, у которого в поле `query` стоит имя другого
   запроса, для этого шага не годится — искать фикстуру своего запроса рядом
   (`<имя запроса>.json`) и сказать, если её нет. Исключение — процессы с одним общим
   файлом запроса: у них форма артефакта одна, поэтому годится фикстура, взятая
   по единственному файлу из `queries/` по правилу пункта 1; использованный файл назвать
   в шапке отчёта. В демо фикстура — **вход** шага: критерии пункта 1 к ней уже применены,
   повторно по `prs[]` и `labels` они не пересчитываются, иначе демо разойдётся
   с живым прогоном.
3. Иначе взять системы из `config/sources.json` по id `taskStore` и `codeStore`, открыть
   их адаптеры `adapters/<система>.md` и исполнять по ним: инструменты MCP, пагинация до
   конца, батчи, ограничения.
4. MCP-сервер из поля `mcpServer` недоступен в сессии → остановиться и сообщить
   какой именно; не подменять другим сервером, не искать данные в локальных файлах.
5. Порядок поиска — из текста запроса (например, сначала код, потом задачи): он выбран не
   случайно, а под ограничения конкретной инсталляции; отступления перечислить в результате.
6. Каждое условие отбора подтвердить полем ответа хранилища; всё, что проверить
   не удалось, уйти в `unverified[]` с причиной — «не подтверждено» не равно «нет».
7. Вернуть `report-data`: выборка + счётчики (сколько прочитано страниц/батчей) +
   непроверенное с причинами. Форму артефакта подсказывает словарь переменных
   шаблона, который использует следующий шаг.
8. В режиме чтения текста вернуть `records-text`: по объекту — ключ и запрошенные
   текстовые поля без сокращений; объект, у которого поле пустое или недоступно,
   остаётся в артефакте с пометкой причины, а не выбрасывается из выборки.

## Что в этом действии НЕ делается

- не выбирается шаблон отчёта и его вёрстка — это следующий шаг;
- не выполняются внешние эффекты (письма, комментарии) — это действия `act`;
- не проверяется текст объектов по правилам — это `transform`-действие;
- не редактируются конфиг и адаптеры, даже если вывод выдал неожиданные значения
  имён типов или статусов — факты докладываются человеку с указанием файла и уровня.
