# Сохранение рабочего прогона

Это служебные операции, не тесты и не движок исполнения. GigaCode читает рецепт,
выполняет действие и решает branch. run-journal.js сохраняет факты выполнения,
не вызывает MCP, не пишет текст за модель и не запускает тесты.

## Что читать

1. Выбранный процесс, его ACTION.md, точные query/rule/template, нужный контекст.
2. Из docs/templates — только примеры формы создаваемых файлов.
3. В demo — только dataFile, указанный пользователем. Не читай весь tests/<процесс>,
   fetch.json, report.md, expected*, check.js; не используй glob tests/* и не открывай
   файл «посмотреть формат». Формат уже есть в docs/templates и контракте артефакта.
4. Не угадывай имена инструментов/скриптов. Расчёт SDD — assessSdd из sdd-data.js;
   отдельного tools/assess-sdd.js нет. Проверяющие команды при обычном запуске не нужны.

## Команды и порядок

Из корня: node tools/run-journal.js <операция> <путь-к-spec.json>.
Spec — JSON-файл в системной временной папке, не JSON-строка в аргументе. Создавай
его штатным JSON.stringify/json.dump, не сложным printf с ручным экранированием.
Можно использовать экспортированные start(cwd,spec), operation(cwd,command,spec)
из небольшого Node-скрипта; порядок тот же. Не создавай новый исполнитель процессов.

1. start — до исполнения первого шага. Сохраняет identity, начальные state/trace/run/итог.
2. begin — непосредственно перед каждым действием; пишет step_started и pending.
3. Агент выполняет действие, используя эффективные параметры и фактические входы.
   Текст отчёта составляется моделью по структуре шаблона. Не пиши собственный
   универсальный рендерер и не исполняй {{each/if}} как программу.
4. save — сразу после получения результата: артефакт → событие → атомарное state.
5. Следующий begin только после save. Ни trace, ни timestamps не переписываются в конце.
6. finish — после окончания маршрута: файл для человека, итог, событие и одна строка
   истории на output. Повтор finish обновляет ту же запись, не дублирует её.
   fail — при остановке из-за недоступного входа/системы, отмены или неустранимой
   ошибки: сохраняет pending, причину, итог и неуспешную историю. Локальную ошибку
   оформления до save исправь в черновике того же pending-шагa; источники не перечитывай
   и не создавай новый прогон автоматически. Перед save текст уже должен быть готов.

### Start: текст

```json
{"process":"edit-text","mode":"local","date":"2026-11-03","slug":"сократить-текст","title":"Сократить текст для руководителя","inputText":"Текст текущего пользователя","params":{"режим":"коротко","кому":"руководителю"}}
```

Date — местный день человека, а не дата из примера. InputText — фактический вход.
Команда возвращает output, state.params и readFiles. Params.input уже указывает на
сохранённую копию входа относительно корня. Используй эти параметры, не создавай
второй свой словарь с другими датами/путями.

### Start: demo SDD

```json
{"process":"sdd-stories-report","mode":"demo","date":"2026-11-03","slug":"отчёт-sdd","params":{"dataFile":"tests/sdd-stories-report/fixture.json"}}
```

Query/rule/template, контекст, схемы выходов, вложенные процессы и используемые
адаптеры собираются автоматически по определениям и эффективным параметрам.
Ручной files не нужен; он оставлен только для явно дополнительных входов. ReadFiles
в ответе — список снимка, не команда прочитать весь список в контекст. Читай только
рецепт текущего шага и нужные ему данные. Не добавляй тестовые эталоны.

В demo период берётся из meta.window указанной исторической фикстуры. Если пользователь
явно попросил другой период, передай его в explicitParams — несовпадение блокирует
запуск вместо выдумывания другой выборки. В state.params, identity.params, report-data
и отчёте один и тот же период. Date папки — день запуска, generatedAt данных может
быть историческим: это разные поля. Today разрешается один раз до исполнения.

### Один шаг

```json
{"output":"<возвращённый output>","step":"edit"}
```

Это spec для begin. После редактирования передай save:

```json
{"output":"<тот же output>","step":"edit","artifact":"report-text","extension":"md","content":"Фактический результат действия","next":"end"}
```

SDD: fetch/task-records/json → read-code; read-code/code-evidence/json → assess;
assess/report-data/json → compose; compose/report-text/md → gate.
Для JSON content — объект; для текста — строка. Не записывай служебный артефакт сам
до save. Его физическое имя выдаёт сохранённое state.artifacts.

### Завершение

```json
{"output":"<тот же output>","resultName":"текст.md","summary":"Что реально изменено"}
```

Для SDD без письма: resultName=отчёт.md, decision=«Пользователь не просил письмо».
GigaCode сам проверяет gate; decision фиксирует его решение. Если письмо запрошено,
begin notify с decision=«Пользователь попросил черновик и есть истории без SDD», затем
save mail-draft/…/end и finish с resultName=письмо.md. Внешней отправки нет.
Не называй выбор branch выполнением API. Неизвестный стек старого прогона нельзя продолжать по одному last_step;
новые вызовы сохраняются командами enter/leave.

Fail spec: output, reason (краткая безопасная причина). При ошибке записи истории
результат/состояние сохраняются, ошибка сообщается отдельно; lock не удаляется вручную.
Если save прервался, существующий файл можно принять только повторным save с тем же
content; иной content блокируется. Действие не повторяется ради записи файла.

## Откуда берутся значения

| Поле | Источник |
|---|---|
| output/date | Новое имя и местный день запуска, вычисляет start |
| params | Возвращённые start эффективные значения, не данные из примера |
| identity/files | Хеши реальных выбранных файлов, автоматически |
| artifacts/artifactHashes | Фактически сохранённые результаты save |
| trace.ts/state.updated | Реальное время операции, автоматически |
| report counters | assessSdd по task-records/code-evidence |
| report window | Эффективный период state.params, совпадающий с входом |
| history | finish/fail через штатный updateHistory, не ручное дописывание |

Файл с примером не является доказательством завершённого шага. Не копируй его числа,
даты, selectionId или хеши. Проверяй содержание действия по контракту и пользовательской
задаче; это не запуск тестового набора. Исправление формата не даёт права менять факты.

### Технический идентификатор отбора

При save task-records selectionId фиксирует сам run-journal по окончательному
содержимому. После save не добавляй поля в объект и не меняй сохранённый файл.
Следующий source читает именно сохранённый task-records. Для demo используй
evidenceFromFixture(fixture, savedTasks), а не новый независимый splitFixture().code.
Идентификатор — служебное поле, его нельзя брать из примера или обслуживать вручную.

## Вызов подпроцесса

Если текущий узел имеет процесс:, используй enter, а не begin:

```json
{"output":"<output>","step":"<узел вызова в родителе>"}
```

Enter сохраняет продолжение родителя в stack и возвращает cursorProcess/next_step
вложенного процесса. Агент выполняет его action-узлы через begin/save. Даже если
next_step=end, это ещё не конец всего запуска: сначала leave с одним output.
Leave возвращает к сохранённому следующему шагу родителя и восстанавливает его
параметры. Finish при незакрытом stack запрещён. Повторные вызовы того же процесса
получают отдельные номера физических файлов. Если у узла вызова указан артефакт:,
он становится именем результата подпроцесса у родителя; иначе сохраняется имя
последнего выхода ребёнка. Для ребёнка с разными финальными выходами задай явное имя.

Выбор branch остаётся за агентом; decision у enter/begin/leave/finish только фиксирует
основание уже выбранного перехода. Нельзя вызвать произвольный process через begin.
Все JSON-выходы проверяются по contracts действия до сохранения файла и события
успешного шага. Текстовый контракт требует непустого текста; факты проверяет агент.
