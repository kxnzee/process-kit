Здесь происхождение каждой шкалы, порога и трактовки, а также то, что в методике расходится.
Числа правила (`rules/gmi.js`) берутся отсюда; когда сверка с порталом покажет другую версию,
менять нужно правило, а эту страницу — только дополнять датой снимка.

Снимок шкал: 2026-11-08. Актуальность методики проверяют шаги сверки в начале прогона
(`check-scales` и `check-index`, общее действие `actions/check-methodology` с чтением страницы
по `adapters/wiki-page/ADAPTER.md`, если человек согласился на сверку); сверка ничего не меняет —
она показывает расхождение, а решение по нему принимает владелец.

## Шкалы блоков

### Обучение и применение — вес 30 %, максимум 3

| Метрика | Шкала |
|---|---|
| Курсы, завершённые в срок (5 курсов) | 0 → 0; 1 → 0; 2 → 0,3; 3 → 0,5; 4 → 0,8; 5 → 1 |
| Частота использования | не используют → 0; ежемесячно → 0,2; еженедельно → 0,5; ежедневно → 1 |
| Режим работы | ассистент → 0,5; агент → 1 (не используют → 0) |

Сноска слайда: сотрудник **не** состоит в целевой аудитории курсов SDD и «Управление контекстом
AI-агентов» — этим курсам засчитывается максимальный балл. В выгрузке это столбцы
«ЦА Обучение SDD» и «ЦА Обучение контекст» со значениями `0` / `1`: правило добавляет credit=1
за каждый курс с флагом `0`, если только курс уже не завершён в срок.

### Навыки — вес 30 %, максимум 3

| Метрика | Шкала |
|---|---|
| Достиг планового значения по навыкам (флаг) | да → 1; нет → 0 |
| Количество навыков, достигших планового значения | 0 → 0; 1 → 0,1; 2 → 0,2; 3 → 0,4; 4 → 0,6; 5 → 0,8; 6 → 1 |
| Когорта потребления токенов | минимальное использование → 0; низкое → 0,3; базовый уровень → 0,5; продвинутый уровень → 0,8; power users → 1 |

Навыков ровно шесть: Prompting, Prompt engineering, Context management, Creating tools,
Creating skills, Agent team. У каждого в выгрузке две колонки: текущий уровень (1…5) и
`DONE` — достигнута ли планка (1/0). Именно `DONE` участвует в шкале количества, текущий
уровень показывает, до чего человек уже дотянул (его показывает формулировка рекомендации).

### Продуктивность — вес 40 %, максимум 4

Шесть метрик по 0,5 балла: трудоемкость, PR, строки кода, коммиты, количество строк кода на
1 коммит, коммитов в статусе Jira «Установлен на ПРОМ». Седьмая — «Рост Story на 1 сотрудника»,
максимум 1 балл.

Коэффициент эффективности: `индивидуальный показатель ÷ медиана целевой аудитории × 100 %`.
Градация: bot — менее 25 %; mid — от 25 % до 75 %; top — 75 % и выше. Баллы: bot → 0,
«соответствуют ожиданиям» (mid) → 0,3, top → 0,5. В выгрузке за градацию отвечает столбец
`<метрика> top bot` со значениями `bot` / `mid` / `top`.

## Противоречия методики и решения

1. **«Рост Story на 1 сотрудника».** Таблица слайда 6: «Команда выше цели кластера» → 0,
   «Команда ниже цели кластера» → 1. Сноска того же слайда: выполнение цели по кластеру
   (выше или равно 70 % цели) → 1 балл, ниже 70 % → 0; для сотрудников вне команд оценивалось
   исполнение цели по кластеру. Баллы файла соответствуют сноске (формулировка «Команда выше
   цели кластера» отдаёт 1). Правило держится сноски, а расхождение с баллом файла показывает
   в разделе сверки. Вопрос владельцу методики назван в оговорках прогона.
2. **Целевое значение.** В методике цели по GMI нет: есть веса, шкалы и трайбовые перцентили.
   Цель `goal = 6,0` из 10 и предупреждающий порог `warnBelow = 3,0` — решение владельца
   процесса от 08.11.2026, они приходят параметром процесса, а не являются константой методики.
3. **«Персентиль 50 Обучение/Навыки/Продуктивность» = 2,3 / 0,9 / 2,4** одинаковы у всех строк
   файла: это перцентили трайба (совпадают с примером слайда 7: трайб 5,9 против кластера 4,5),
   а не распределение людей. Поэтому они не участвуют ни в оценке, ни в отборе ниже цели.
4. **Трайбовый бонус МУИ 0–0,2** («Оценка в БП») относится к трайбу и в оценку человека
   не входит.

## Откуда адреса для ссылок «Письмо сотруднику»

В сводной таблице адресов нет. Карту готовит тот, кто запускает прогон, — сам процесс сеть не
касается и ни из одной системы адрес не читает. Карта плоская, «ФИО → адрес»:

```json
{ "Примеров Пётр Петрович": "<адрес из почтового справочника>" }
```

- ключ — ФИО ровно как в колонке `ФИО сотрудника` выгрузки: правило сравнивает строго, разница в
  лишних пробелах не в счёт, частичное совпадение или «фамилия + инициалы» не считаются;
- значение — адрес из почтового справочника организации (поиск контактов по подключению почты).
  Запись с пояснениями (`{"email": "…", …}`) тоже читается — адрес берётся из поля `email`,
  остальное правилам не нужно. Пометка внешнего исполнителя (`{"email": "…", "подряд": true}`) —
  решение владельца процесса от 11.11.2026: подрядная учётка `[B]` из справочника даёт письмо наравне
  со штатной, а пометка нужна тому, кто потом читает файл карты.

- запись без адреса может нести `"причина"` — например `{"причина": "в почтовом справочнике три
  разных человека с этим ФИО"}`. Текст печатается под блоком человека ровно как написан и попадает
  в оговорку группы: «нет в карте адресов» значит, что карту никто не заполнял, а не то, что
  справочник молчал. Правил выбора между однофамильцами в процессе нет намеренно.

Право на ссылку даёт сам адрес, найденный в справочнике по точному ФИО: справочник — владелец
почты, и адрес в нём уже принадлежит человеку. Сверку `account_id` из каталога пользователей задач
владелец процесса снял 11.11.2026: она стояла по два обращения на человека, а разошедшиеся номера
чаще означали, что человека нашли в другой инсталляции задач, чем что адрес чужой. Ответственность
за выбор адресата остаётся собирающему карту: если справочник под одним ФИО даёт нескольких разных
людей и их не удалось различить по должностям и подразделениям, адрес в карту не кладут — угадать
адресата значит отправить письмо не тому человеку. Одинаковое ФИО внутри одного списка писем не
получает ссылку никогда, это проверяет правило.

Справочник выбран источником адреса ещё и потому, что выдача поиска пользователей задач приносит
копию, которая отстаёт и не показывает отключённые и подрядные учётки. На снимке 11.11.2026 по
задачам адреса не нашлись у 22 человек ниже цели из 54, справочник закрыл 17 из них — 14 оказались
внешними исполнителями с одной подрядной учёткой, писать ли им, решает владелец процесса. Карту
собирают вручную и обычно раньше, чем меняется список отчёта, поэтому часть людей остаётся без
ссылки — отчёт показывает это под каждым таким блоком, а не молча.

Под одним ФИО в справочнике живут несколько записей: рабочая, отключённая, подрядная (пометка
`[B]`, в организации — подрядчик) и служебные в чужих деревьях (`{Omega}`, `{ЦА}`) с другим
доменом. Первая строка выдачи — не ответ: брать можно только ту запись, в которой человек
опознан однозначно. Адрес может выглядеть как номер учётной записи (`<номер>@sberbank.ru`) — это
настоящий рабочий ящик, а не ошибка справочника, брать его можно.

Служебные записи деревьев `{Omega}` и `{ЦА}` полным ФИО по общей базе не находятся: у них заполнено
только отображаемое имя, а запрос строится по фамилии, имени и отчеству. Их достают сузением базы
поиска до этого дерева (`OU={Omega},OU=GAL,…`), где ФИО ищут уже по одной фамилии. Такой адрес
считается пригодным, если живая запись с почтой на человека одна и другой просто нет, — решение
владельца процесса от 11.11.2026; в карте адрес тогда лежат с пометкой, откуда он взят.

Прежняя редакция этого раздела запрещала брать адрес из почтовой книги: поиск по полному ФИО
отвечал `Code: 0x3` — `LDAP_TIMELIMIT_EXCEEDED` (подстрочный фильтр по всему дереву `dc=Sigma` не
успевал за отведённые сервером 30 секунд, база и область поиска наружу не выводились). 11.11.2026
сервер починен: первым идёт индексный (префиксный) запрос, лимит времени сообщается оговоркой, а
не молчаливым пустым списком, и полный ФИО находится. Запрет был следствием поломки, а не
правилом, и его больше нет.

Сам процесс сеть не касается: карта адресов — локальный файл рядом с таблицей оценок, в git он
не оказывается (в нём персональные данные), а пустая заготовка `data/people.example.json` нужна
только чтобы шаг расчёта всегда получал второй вход.
