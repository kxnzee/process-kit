# Архитектура Process Kit

Один репозиторий, уровни разделены ветками: `master` — общий уровень, `team-<команда>` —
командный, `my` — личный. Клиент GigaCode открывает репозиторий как обычную папку
проекта; про уровни он не знает. В исходной реализации на стенде использовалась схема: расширения GigaCode
работают только в CLI и перезаписывают `~/.gigacode/`, поэтому расширения нет —
есть файлы в папке проекта.

```
process-kit/                       ← ветка master (общий уровень)
├── GIGACODE.md                    ПРАВИЛА модели: уровни, структура, имена, контекст
├── README.md                      для человека + раздел «Для разработчика»
├── docs/ARCHITECTURE.md           устройство системы (этот файл)
├── .gitignore                     outputs/, .history/, всё, что клиент пишет сам
├── .gigacode/
│   ├── settings.json              MCP-серверы; токен — ссылка $secret:<имя>/<ключ>
│   ├── hooks/pre-push             запрет отправки личной ветки в origin
│   └── skills/                    ПЛОСКО: pp-ai-mentor, pp-ai-init, pp-ai-run-process,
│                                  pp-ai-create-process, pp-ai-create-action, pp-ai-create-adapter, pp-ai-promote-changes-team,
│                                  pp-ai-promote-changes-master
├── processes/<имя>/PROCESS.md      шапка-манифест и маршрут; данные внутри папки
├── actions/<имя>/                 действия: ACTION.md + queries/, templates/, rules/
├── adapters/<имя>/ADAPTER.md                      механика систем: jira/, bitbucket/
├── context/<master|team|my>/<тема>/CONTEXT.md        термины и общие правила
├── config/
│   ├── master/                    общие безопасные defaults
│   ├── team/                      командные настройки и EXAMPLE.json
│   └── my/                        личные настройки и EXAMPLE.json
├── tools/
│   ├── kit.js                     единый CLI и каталог команд
│   └── lib/                       внутренние модули по назначению
├── tests/                         тестовый код и run.js, запуск через kit.js test
├── outputs/                       результаты запусков (не версионируется):
│                                   ОДНА папка на запуск, имя без пробелов
│   ├── <ГГГГ-ММ-ДД>_настройка/    что-сделано.md
│   ├── <ГГГГ-ММ-ДД>_<задача>/     итог.md + файлы для человека
│   │   └── .run/                  run.md, trace.jsonl, <NN>-<шаг>.*, state.json
│   └── <ГГГГ-ММ-ДД>_заявка-<что>/ заявка.md (нет прав создать ветку или систему)
└── .history/                      runs.jsonl — журнал прогонов; cache/ (не версионируется)
```

Командная ветка `team-<команда>` и личная `my` повторяют структуру и добавляют файлы
со своим префиксом в те же папки. Командная ветка хранит `config/team/config.json`. Личная добавляет `config/my/config.json`; master поставляет общие настройки и примеры сущностей.

## Что чем не является

| Каталог | Что это | Кто читает |
|---|---|---|
| `.gigacode/skills/pp-ai-*` | служебные скиллы, команды «/» | GigaCode — регистрирует сам |
| `actions/` | вызываемые функции с аргументами и результатом | исполнитель по имени из процесса |
| `processes/` | маршруты шагов | помощник (подбор), исполнитель |
| `adapters/`, `config/` | подключения к системам | исполнитель |
| `context/` | факты и пожелания | исполнитель — только при явном подключении |

Действие не регистрируется клиентом, поэтому вложенность `actions/<имя>/queries/`
ограничением GigaCode не задевается. Скиллы, наоборот, лежат строго плоско.

## Уровни

| Уровень | Ветка | Кто правит | Префикс файлов | Видит |
|---|---|---|---|---|
| общий | `master` | разработчик набора через PR из `master-*` | нет | только свои файлы |
| командный | `team-<команда>` от `master` | команда через PR | `team-<команда>-` | свои + общие |
| личный | `my` от команды или от `master` | сам человек, обычно локально | `my-` | свои + командные + общие |

**Ссылки только вверх:** `my` → `team-*` → `master`. Вниз — никогда: общий или командный
файл, ссылающийся на имя, которого нет в его собственной ветке, — ошибка раскладки;
исполнитель останавливается и называет файл и ссылку.

Уровень определяется по текущей ветке (`git branch --show-current`), файлы ищутся в
рабочей копии. Рабочие ветки — `master-<имя>` (общий уровень, правки через PR) и ветка
команды от `team-<команда>`; имя рабочей ветки команду не называет — её берут из
настроек master/team/my через tools/lib/config/config.js или из `--team <код>`. Ветка, которая не называет
команду и не определена в настройках master/team/my, — предупреждение проверки: префиксы файлов
уровня в ней не проверены.

Клиент про уровни не знает: все клиенты читают одну и ту же папку и один и тот же
`GIGACODE.md`. Процессы, экшены и адаптеры различаются префиксами папок. Конфиг и контекст разделены папками master/team/my; содержимое настроек зависит от окружения.

## Четыре уровня модели

| Уровень модели | Вопрос | Где живёт | Правило изменения |
|---|---|---|---|
| Процесс | в каком порядке и когда что выполнять | `processes/` | меняются шаги и ветвления; действия не трогаются |
| Действие | что делает один шаг | `actions/<имя>/ACTION.md` | контракт (`consumes`/`produces`) стабилен; общие материалы — у экшена, специфические запросы/правила/шаблоны — у вызывающего процесса |
| Адаптер | как говорить с системой | `adapters/` | новая система = новый адаптер; процессы не правятся |
| Координаты | где именно лежит | `config/master/`, `config/team/`, `config/my/` | меняются хосты, проекты, лимиты, дефолты |

Верхний уровень знает нижний **только по ссылке**: имя файла или `id` системы.
Контекст — отдельная сущность фактов и договорённостей; адаптер и координаты вместе
описывают подключение. Уровни модели в таблице — границы ответственности файлов.

## Принцип декомпозиции

1. **source / transform / act** — три класса действий; сеть есть только у `source`
   и `act`, поэтому отчёт логику можно проверять на фикстурах без систем.
2. Сценарий раскладывается в цепочку независимых блоков. Для отчёта SDD:
   `run-query` (задачи) → `read-code-evidence` (код) → `evaluate-data` с правилом процесса (расчёт) →
   `compose-report` (отчёт) → `branch` → `evaluate-data` (данные письма) →
   `compose-report` (тело письма) → `prepare-mail-draft` (черновик по просьбе).
   Почтового подключения в поставке нет: черновик не отправляется.
3. В процессе хранятся только ссылки и параметры шага — текст действия не дублируется.
4. Действие — одна законченная операция, фиксированные входы и один именованный
   результат. Пагинация/батчи остаются внутри чтения; границы операций определяются контрактами функций, а не количеством инструментальных вызовов. Контракты SDD — processes/sdd-stories-report/reference.md.

## Форма процесса

Процесс — Markdown: шапка (`name`, `version`, `area`, `status`, `description`,
`examples` или `example`, `requires`, `entry`, `params`; `title` — заголовок для человека) и раздел «Шаги», где у шага есть `действие:` / `процесс:` /
`branch:`, `параметры:`, `артефакт:`, `следующий:`. Маршрут читается из этих полей, а не
из порядка подразделов. Шаги разбираются общим tools/lib/entities/process-model.js. Исполнитель — модель;
`tools/lib/validation/validate.js` проверяет механические свойства: шапки, ссылки, маршрут, циклы,
доступность входных артефактов и зависимости. Смысл рецепта подтверждает владелец;
зелёная структурная проверка не заменяет пробный прогон в GigaCode.

## Маршрут

- Шаги — именованные узлы; старт в `entry`, дальше по `следующий:`.
- Развилка — узел `branch`: упорядоченные правила `когда:` по артефактам выполненных шагов
  плюс `default`.
- Шаг может указывать на другой процесс (`процесс:`) — подпроцесс, глубина ограничена master.execution.maxProcessDepth, циклы
  запрещены.
- Каждый шаг кладёт результат в артефакт с именем `артефакт:` и пишет его файлом в
  каталог прогона.

## Изоляция шага

Пакет входа (рецепт действия, адаптер, данные действия, артефакты по `consumes`, значения
параметров) собирается для шага отдельно; наружу отдаётся только `produces` файлом
`outputs/<запуск>/.run/<NN>-<шаг>.<ext>`; соответствие логического имени файлу
записывается в state.artifacts. Сырые ответы систем, диффы и шаблоны в общий контекст
прогона не переносятся: в диалоге остаётся сводка шага не длиннее пяти строк.
Реальная изоляция контекста зависит от клиента; если отдельный контекст не
поддерживается, исполнитель фиксирует ограничение и не заявляет техническую изоляцию.

Папка запуска одна на прогон: `outputs/<ГГГГ-ММ-ДД>_<коротко>/` в корне папки, служебные
файлы — в её `.run/` (`run.md` с маршрутом и причинами остановок, `trace.jsonl`,
`<NN>-<шаг>.*`, `state.json`). Артефакт каждого шага пишется в `.run/`, включая последний:
полный след прогона нужен, чтобы любой шаг можно было проверить отдельно. Результат
последнего шага команда finish сохраняет побайтно вторым файлом в корень папки запуска.
Исходный артефакт остаётся в .run/, повторное выполнение действия не требуется. `итог.md` пишется всегда, даже если прогон остановился, и
перечисляет только файлы, лежащие рядом с ним.

Правило про два файла последнего шага записано явно (`GIGACODE.md`, «Где лежат
результаты», и шаг вывода исполнителя) и проверяется механически: `tools/lib/validation/validate.js`
сообщает об артефакте шага в корне папки запуска, об отсутствии файла для человека и об
упоминании служебной подпапки в итоге. Причина — опыт первого прогона: без явного имени
файла правило «результат в папку запуска» исполнитель понял по-своему.

## Конфиг и контекст

Настройки master/team/my читаются tools/lib/config/config.js. В master — общие defaults,
в team — метаданные команды и общие подключения/ресурсы, в my — выбор teamId,
собственные подключения и личные defaults. Массивы не перезаписываются: id уникальны.
Приоритет выбора: явный аргумент → my → team → master. teamId=null исключает team.
Механика и поля — config/team/README.md.

## Токены

`.gigacode/settings.json` описывает MCP-серверы; на месте токена в поставке стоит ссылка
на секрет вида `$secret:<имя>/<ключ>` (`$secret:pp-ai-jira/x-jira-token`). Значение подставляет
сам клиент GigaCode: человек заводит секрет штатным способом в CLI, VS Code или десктопном
приложении, клиент использует ссылку при подключении; после изменения настроек может потребоваться перезапуск сессии.
Отдельного файла доступов в проекте нет; в репозитории токенов нет.
Командная и личная ветки `settings.json` не меняют, свои личные серверы человек добавляет
в глобальные настройки GigaCode, а глобальную `~/.gigacode/` агент только читает.
Готовность подключения определяется по факту: сервер объявлен в сессии и ответил на одно
проверочное чтение.

## Защита

Хука GigaCode нет. Защита — правила веток Bitbucket (прямой push в `master` и `team-*`
запрещён, слияние через PR, запрет force push и удаления), `.gitignore` для `outputs/`
и `.history/`, запрет отправки личной ветки средствами git:
`git branch --unset-upstream`, `git config branch.my.pushRemote no_push`, pre-push hook
в `.git/hooks/`, устанавливаемый tools/lib/git/install-hooks.js с сохранением прежнего hook.
Локальный hook — дополнительная защита: серверные ограничения настраивает владелец,
наличие файла hook не доказывает, что ограничения Bitbucket включены. `tools/lib/validation/validate.js` дополнительно проверяет, что `outputs/` и
`.history/` не попали в git (`git ls-files`): данные человека версии не подлежат.

## Как устроен прогон

1. Помощник `/pp-ai-mentor <задача>` подбирает процесс по `description` в `processes/`.
2. Исполнитель `/pp-ai-run-process process=<имя>` читает шаги, для каждого берёт
   `actions/<имя>/ACTION.md`, данные, систему из `config/`, адаптер и
   нужный context по манифесту.
3. Результат шага — файл, он идёт входом в следующий шаг, и так до конца маршрута.

Демонстрационный прогон без систем:
`/pp-ai-run-process process=<имя> dataFile=processes/<имя>/fixture.json` — источники читают выборку из
фикстуры и помечают прогон как демо.

## Обновление

Общий уровень приезжает тегом `vX.Y.Z` на `master`: `git fetch --tags origin`,
`git merge vX.Y.Z`. Командный — `git merge origin/team-<команда>`. Свои файлы имеют свои
имена, что уменьшает число конфликтов, но не исключает изменения общих зависимостей.
Перед слиянием — просмотр изменений и согласие пользователя; конфликты разрешаются
явно, без автоматического reset. После слияния — node tools/kit.js test.

Экшен — функция с аргументами, результатом и ошибками; процесс связывает вызовы.
Запросы run-query и read-code-evidence передаются как queryFile из папки вызывающего процесса; parameters содержит аргументы запроса.

## Разрешение сущностей

Requires описывает целые сущности: actions/processes именами, context/config уровнями
master/team/my. Шаги используют объявленные экшены и подпроцессы. Внутренние ресурсы
экшена принадлежат его папке, ресурсы сценария — папке процесса. tools/lib/entities/entities.js
возвращает entities (точки входа и темы контекста), connections (выбранные записи и
адаптеры), files (снимок) и missing. Агент читает нужные сущности, не весь снимок.
Конфиги выбираются кодом только из объявленных уровней; execution master всегда
используется механизмом запуска. Конфликты контекста требуют решения человека.

Одиночные локальные transform вызываются через kit.js action без постоянного процесса.
Агент процесса остаётся координатором: run next сообщает следующий шаг, run execute
вызывает только локальные функции runtime. Сетевые инструменты и решения ветвления
за агентом. Структурированный текст может формироваться и проверяться rendererFile
процесса; успешный save тогда подтверждает перенос проверяемых фактов из данных.
