  Создатель сущностей Process Kit: служебный скилл, вызывается помощником (pp-ai-mentor)
  и никогда не предлагается человеку напрямую. Превращает описание сценария («получить X,
  проверить по правилу Y, отправить Z») в файлы подхода — процесс, действия, данные
  действий, адаптеры — и кладёт их по уровню владельца значения: общее в ветку master
  (только через PR), настройку команды в файл с префиксом команды, личное в файл с
  префиксом my-. Сначала сверяет с существующими действиями и расширяет их; новое
  действие создаёт, только когда расширение действительно не подходит. Применяй, когда
  помощник определил, что такого процесса пока нет.

# Создание процесса и его сущностей

**Условие запуска.** Запускайся только после того, как настройка закончена и человек
ответил «да» на предложение собрать процесс. Нет настройки или нет «да» — не собирать:
вернуть управление помощнику.

Вход — описание сценария словами (часто приблизительными: «получаем CR из системы задач,
смотрим по инструкции, пишем тому, кто должен править») и то, что уже лежит в ветке.
Выход — файлы подхода плюс отчёт: что создано, что расширено, что оставлено как есть и
почему именно так разложено по уровням.

Модель, классы действий и приоритет значений — в `GIGACODE.md` проекта; здесь — порядок
работы конструктора. Рецепт исполнения всегда берётся из `ACTION.md`, а не пересказывается.

## Шаг 0. Прочитать текущее решение

1. Корень проекта — открытая папка (`GIGACODE.md`, `processes/`). Уровень ветки:
   `git branch --show-current`; `master-<имя>` — общий (правки только через PR), ветка
   команды — командный; другое имя — спросить, какого она уровня.
2. Составить карту существующего в этой ветке: `processes/*.md`, `actions/*/ACTION.md`
   и данные внутри папок действий (`queries/`, `templates/`, `rules/`), `adapters/*.md`,
   `context/*.md`, наличие `config/sources.json`.
3. Для каждого действия прочитать шапку контракта (`kind`, `adapter`, `consumes`,
   `produces`) и раздел «Что в этом действии НЕ делается». Именно он решает, расширяется
   действие или нет.

Карту показывать человеку **до** вопросов: по ней видно, что уже есть и чего не хватает.

## Шаг 1. Спросить, не догадываться

Вопросы задавать **всегда**, а не только когда текст неполон; в каждом вопросе показывать
известное значение как вариант по умолчанию. Максимум четыре вопроса за вызов и только те,
которые меняют файлы.

Обязательный минимум:

1. **Объект источника** — что именно читаем: задача одного типа, PR, файл, страница.
   Для системы задач: точное имя типа, проект, окно, какие статусы исключать. Без точного
   имени типа шаг выборки неисправен — придумывать имя нельзя.
2. **Правило** — по чему судить о результате: файл-правило, критерии в тексте процесса,
   ссылка на внешнюю страницу. Если правило живёт вне подхода — в какой уровень его класть.
3. **Эффект** — что происходит по результату: комментарий в объекте, письмо, смена
   статуса, ничего; и куда именно направлен эффект.
4. **Граница прогона** — окно/лимит, что считается «ничего не найдено», нужен ли
   демонстрационный прогон на фикстуре.

Чего **не** спрашивать: названия действий, имена артефактов, форму шапки — это вывод из
шагов 2–4 и решается без человека.

## Шаг 2. Разложить сценарий на шаги

1. Минимальные шаги, у каждого ровно один класс: обращение к системе → `source`,
   переработка артефактов без сети → `transform`, внешний эффект → `act`.
2. Проверить границы: артефакт предыдущего шага — вход следующего. Если шаг потребляет
   «данные из головы», разбиение неверное.
3. Условие («если есть нарушения — писать») вынести в `branch`, а не в текст действия:
   предикат оценивается по артефакту.
4. Один `act` — один вид эффекта: комментарий в системе и письмо — разные действия, даже
   если текст одинаковый.

## Шаг 3. Сверить с существующим — расширить, а не создать

По каждому шагу, от общего к частному:

1. **Подходит существующее действие** — расширять его контракт и рецепт, сохраняя обратную
   совместимость (старые процессы продолжают работать).
2. **Действие почти подходит, но тянет чужой эффект** — создаётся своё действие того же
   класса (например, комментарий в системе против письма), `adapter` указывает на систему.
3. **Действие подходит, данных не хватает** — создаётся файл данных рядом с ним
   (`queries/`, `templates/`, `rules/`), `ACTION.md` не меняется. Самый дешёвый способ.
4. **Шаг не покрыт вовсе** — новое действие.

Решение по каждому шагу в отчёте одной строкой: «шаг → действие (расширено / новый файл
данных / создано / без изменений)» и причина, по которой расширение отвергнуто.

## Шаг 4. Выбрать уровень

Раскладывать **по владельцу значения**, а не по удобству:

| Признак | Уровень и префикс |
|---|---|
| Работает у любого, кто открыл набор; адреса проектов — только через `config/sources.json` | общий, без префикса (ветка `master`, только через PR) |
| Настройка команды: адреса её проектов, типы задач, критерии, проекты | командный, `team-<команда>-` — имя ветки целиком |
| Личный вариант: другой проект, другие критерии, своя ссылка на инструкцию | личный, `my-` |
| Настройка конкретной копии: адреса | `config/sources.json`, не файл уровня; токенов в проекте нет — доступом заведует клиент |

Правила раскладки:

- новое **действие** — в общий набор, если не содержит значений команды; если содержит —
  файлом уровня `team-<команда>-<имя>/` или `my-<имя>/` (папка действия тоже получает префикс);
- **данные действия** (запрос, шаблон, правило) кладутся в уровень владельца значений;
- **процесс** — общий, если он общий для всех; иначе `team-<команда>-<имя>.md` или
  `my-<имя>.md`;
- отчётный процесс — маршрут заканчивается текстовым отчётом (последний шаг — действие
  `compose-report`) — получает постфикс `-report` (`sdd-stories-report`;
  `team-<команда>-<имя>-report`, `my-<имя>-report`); данные действия (`query:`, `template:`)
  и набор эталонов `tests/<имя>/` называют по имени процесса;
- общие и командные файлы **не могут** ссылаться на имена, которых нет в их ветке: имя
  из личной ветки — ошибка раскладки, а не повод подставить файл;
- перекрытия по имени нет: файл другого уровня не заменяет одноимённый, а сосуществует под
  своим именем; ссылаться на него процесс должен явно.

## Шаг 5. Записать файлы

0. **Имя нового процесса:** `processes/<имя>.md` по уровню из шага 4 — `my-<имя>.md`
   в личной ветке, `team-<команда>-<имя>.md` в командной, без префикса в общей. Имя нового
   действия — так же, с префиксом уровня. Файлы пишутся не с нуля: заготовка лежит в
   `docs/templates/` (процесс — `process.md`, действие — `action/ACTION.md`,
   подключение — `adapter.md`), форма у неё та же, что у файлов в `processes/` и
   `actions/`. Заготовку скопировать, заменить `<…>`, убрать подсказки «#» — и дописать
   содержание сценария. Общий файл — только через ветку `master-<имя>` и PR.

**Главное правило записи: значение не дублируется там, где оно уже есть.** Два источника:

- **уже есть в `config/sources.json`** (проект, репозиторий, сервер подключения,
  `mcpServer`, адреса, базовая ветка, дефолты) — в процессе и действиях его **не повторять
  ни текстом, ни новым полем**: только ссылка на путь (`defaults.taskStore`,
  `repositories[].defaultBranch`). Новая копия того же значения в конфиг не заводится —
  иначе конфиг начинает противоречить себе;
- **нет в конфиге** (окно отбора, метка, папка артефактов, имена статусов, пороги) — остаётся
  **явно** в процессе, действии или его данных. Переносить такое в конфиг по своей
  инициативе нельзя: конфиг правит владелец уровня, а не конструктор.

Приоритет разрешения значений (из `GIGACODE.md`): аргументы вызова → `параметры` шага →
`params` процесса → `defaults` конфига → значение в действии.

Как проверить себя перед сохранением: пройти файл и для каждого значения спросить «оно уже
есть в конфиге?». Если да — на этом месте ссылка, если нет — значение пишется явно.

| Что это | Где живёт |
|---|---|
| проект, репозиторий, сервер подключения, `mcpServer`, адреса, базовая ветка | только `config/sources.json`; в файлах уровня — ссылка |
| имя типа задачи, статусы, метка, папка артефактов, шаблон ключа, окно отбора | явно в файле, если в конфиге их нет; если есть — ссылка |
| дефолты выбора записи | `defaults.taskStore` / `defaults.codeStore`, ссылкой |
| правило, что считать результатом | данные действия (`queries/`, `rules/`) |
| текст отчёта и названия колонок | шаблон действия (`templates/`) |

1. **Процесс** — `processes/<имя>.md` с префиксом уровня: шапка `name`, `title`,
   `description`, при необходимости `example`, `entry`, `params`, `requires`; раздел «Шаги» — на шаг
   `действие:` / `процесс:` / `branch:`, `параметры:`, `артефакт:`, `следующий:`. Форма та
   же, что у существующих процессов в `processes/`; новую не изобретать. `description` —
   то, по чему `pp-ai-mentor` подбирает процесс: одно предложение о результате и источнике.
   В `params` — значения отбора и настройки (окно, метка, папка артефактов); то, что уже
   есть в конфиге, не копируется: на него ссылаются `defaults.taskStore` и подобные пути.
2. **Действие** — `actions/<имя>/ACTION.md` с префиксом уровня: контракт в шапке `kind`, `adapter`,
   `consumes`, `produces`; ниже рецепт по шагам; в конце — «Что в этом действии НЕ делается».
   В рецепте — имена инструментов и последовательность вызовов; адреса и подключения —
   ссылкой, критерии отбора — по значению.
3. **Данные действия** — рядом, в его папке. Каждый файл самодостаточный: шаблон
   начинается со словаря переменных, правило — с идентификатора и серьёзности критерия,
   запрос — с таблицы «параметр → значение», где то, что есть в конфиге, стоит путём
   (`defaults.taskStore`), а свои критерии (метка, статусы, папка артефактов) — явно.
4. **Адаптер** — только когда меняется механика системы; критерии отбора в адаптер не
   писать, их место — в данных действия. Новая система — `adapters/team-<команда>-<система>.md`
   в командной ветке, `adapters/my-<система>.md` в личной. Адаптер описывает **как
   вызывать**, без значений координат.
5. **Скилл** — не создавать. Новый процесс или действие не является скиллом: файл
   `.gigacode/skills/<имя>/SKILL.md` появляется только когда человеку нужна отдельная
   команда «/», которую нельзя выразить процессом, и тогда имя получает префикс уровня
   (`team-<команда>-` или `my-`).
6. **Ссылки** — только по имени; текст действия в процесс не копировать, рецепт не
   дублировать в двух файлах. Ссылки действия на свои данные — относительно папки
   действия: `templates/x.md`, а не `actions/my-<имя>/templates/x.md`.
7. **Данные человека в сборку не попадают**: `$ROOT/outputs/` и `$ROOT/.history/` —
   личные данные, их нет в `requires` манифеста, в «Поделись с командой» и в будущей
   сборке процесса. Пути к результатам в манифест не писать.
8. **Чего нет в конфиге — не отправлять в конфиг.** Значение, подтверждённое живым вызовом
   (точное имя типа задачи, имя статуса), пишется явно в файл уровня и отдельной строкой
   отчёта называется человеку; заполнять им конфиг конструктор не вправе. Если такое
   значение уже есть в конфиге — наоборот, в файле остаётся только ссылка.

Если для процесса нужна система, которой нет в подключениях, — не выдумывать адрес, а
подготовить заявку `$ROOT/outputs/<ГГГГ-ММ-ДД>_заявка-подключение-<система>/заявка.md`:
какая система, для какого процесса, какие данные из неё нужны, кто владелец. В чат —
«Заявка: <полный путь к заявка.md>».

Записывать по одной сущности за шаг и показывать результат (путь + содержимое) до перехода
к следующей.

### Если нужен общий файл (`master`)

Правка общей ветки — решение владельца набора, а не побочный эффект сборки:

1. Сначала записать и показать всё, что уровнем ниже (командное и личное) — без них общее
   действие нечем проверить. Эта часть идёт по шагу 5: ветка `my`, префикс `my-`.
2. Общий файл пишется в ветке `master-<короткое-имя>`, ответвлённой от основной ветки
   (`git switch -c master-<короткое-имя> --no-track origin/HEAD`): файлы без префикса,
   `my-`-варианты из пункта 1 остаются в ветке `my` и в этот коммит не попадают. Затем
   закоммитить свои файлы поимённо, показать `git diff` и отдельной строкой сказать, что
   это правка общей ветки: она уйдёт всем, кто обновится на следующий тег.
3. Прямой push в `master` запрещён и обходиться не должен: дальше — PR и ревью владельцев
   кода. Если человек просит отправить, он подтверждает это отдельно.

## Шаг 6. Самопроверка до отчёта

Проверить механически, по файлам:

- каждая ссылка шага разрешается в этой ветке — назвать найденный файл;
- `entry` существует; из каждого узла путь доходит до конца или другого процесса; повторов
  узлов нет (цикл — ошибка);
- `consumes` каждого шага покрыт `produces` предыдущего;
- у каждого `act` в рецепте есть черновик и требование явного «да»;
- у каждого `transform` в рецепте нет обращения к сети;
- имена артефактов в шаге и в `produces` совпадают дословно;
- общие и командные файлы не ссылаются на имена только из личной ветки;
- `node tools/validate.js` не даёт ошибок.

Ошибку исправлять до отчёта, а не описывать в нём.

## Шаг 7. Отчёт

1. Таблица шагов: шаг → действие и уровень → что сделано → почему так.
2. Созданные и изменённые пути — списком, с уровнем и префиксом.
3. Открытые значения (имена типов, статусы, ссылки на инструкции) — каждое отдельной
   строкой, с файлом, где оно живёт.
4. Как проверить: `/pp-ai-run-process process=<имя>` и `dataFile=` для демо.
5. Чего конструктор **не** делает: не придумывает адреса проектов, не правит конфиг по ходу
   сборки, не создаёт скиллы вместо действий, не отправляет общие правки в `master` без PR.
