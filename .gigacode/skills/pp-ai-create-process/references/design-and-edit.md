# Проектирование и изменение Process

Читай до создания или изменения определения, выбора Actions и размещения ресурсов.

## Изменение существующего процесса

При адаптации сначала прочитай PROCESS.md и выясни затронутые шаги и контракты.
Сохраняй существующие действия и маршруты, не создавай копии без необходимости.
Читай только нужные файлы: для маршрута — соответствующие действия и их контракты;
для правила — правило и его вход/выход; код скрипта — когда меняется его поведение,
нужно установить контракт или разобраться в ошибке. Готовые скрипты запускай через
документированный интерфейс. Снимок files нужен проверке целостности и не является
списком файлов для чтения агентом. Не перечитывай неизменённые материалы без нужды.
Проверяй затронутый процесс и изменённые маршруты; полный набор проверок нужен при
изменении общих контрактов, инфраструктуры или по явной просьбе человека.
Следующий раздел относится к созданию нового процесса; при адаптации не копируй example.

Для чтения страницы используй подходящее существующее подключение либо read-page с
доступным инструментом среды. Не создавай адаптер для каждой страницы. Если инструмент
недоступен, предложи передать текст; не называй его автоматически полученной страницей.

## Создание процесса

1. Начинай по поручению на создание либо уже полученному согласию на предложение сборки.
   Уточни результат, входы, критерии
   и внешние изменения. Не больше трёх вопросов за раз; готовые ответы не повторяй.
2. Проверь необходимость процесса: назови самостоятельный пользовательский сценарий,
   его результат и решения, которые связывают операции. Прочитай `node tools/kit.js processes`,
   сравни доступные определения и степень их готовности: подходящее можно переиспользовать
   или адаптировать вместо дубликата. Неполный каталог не доказывает отсутствия. Явно
   заказанный отдельный вариант не подменяй молча чужим определением.
   Обёртка экшена только ради
   выбора входа, чтения прошлого результата или сохранения файла не требует процесса:
   это общие обязанности запуска. Число шагов само по себе не критерий: один Action
   допустим в Process при явном требовании управляемого запуска, регламенте или восстановлении.
   Только при отсутствии явного требования формального Process, регламента или нужды
   в восстановлении, если достаточно существующего экшена, предложи его как более
   простую альтернативу. Не подменяй явно порученное создание Process исполнением Action.
   Для локального transform поддержан kit.js action <spec.json>; не обещай ему
   start/finish без process. Исполняй одиночный экшен только если это входит в поручение.
   Иначе перескажи маршрут простыми словами и подбери действия по контрактам.
   Наличие имени в каталоге не доказывает пригодность контракта.
3. Выбери имя и владельца определения по [модели владения](../../../../docs/ownership.md).
   Командную копию в личной ветке не создавай: проверка уровня отвергнет её. Подготовка командной/общей версии — отдельная
   задача владельца в соответствующей рабочей ветке с согласованными именами и ссылками;
   это не скрытый режим обычной сборки. Исходные личные определения сохраняются.
4. Копируй определение и ресурсы processes/example/ по его README.md, исключая
   publication.json: допуск исходного процесса новой копии не принадлежит. Если уже
   скопировал его, удали только перенесённое свидетельство в новой созданной тобой
   папке; свидетельства исходного или существующего изменяемого процесса не удаляй.
   Если готового экшена недостаточно,
   сохрани needs-action: исходную задачу, нужный результат, входы, уровень и уже
   согласованные границы вместе с continuation. Примени pp-ai-create-action по его
   инструкции; проверь результат и продолжи с сохранённого этапа. Не дублируй процедуру
   конструктора действия и не объявляй сборку завершённой после его успеха.
   Согласие на процесс не заменяет согласование новых границ экшена, но уже
   утверждённую карточку повторно не согласовывай. Не дели процесс по вызовам инструментов:
   чтение и расчёт могут входить в одну работу с законченным результатом.
   Процесс содержит маршрут и параметры, а рецепт законченной работы — экшен.
Для локального JSON и расчёта сначала подходит evaluate-data, а затем compose-report.
Evaluate-data сам читает файлы из аргумента inputs: отдельный экшен «прочитать файл»
не требуется. Полученный от пользователя JSON положи в data/ создаваемого процесса,
передай его путь в inputs, создай локальное правило evaluate(inputs, parameters) и
resultContract. Для фиксированного отчёта добавь rendererFile с render/validate.
Это штатная композиция существующих функций, а не новая граница source-экшена.
Не блокируй такую сборку утверждением, что экшены не умеют читать локальный JSON.

5. Заполни name/version/area/status/description/examples/entry/params/requires.
   Поставь publication: required. У нового черновика publication.json отсутствует;
   для готового определения допуск создают штатные команды. Legacy не используй.
   requires содержит только целые сущности: actions и processes — списки имён,
   context и config — списки уровней master/team/my. Вызванные экшены и подпроцессы
   должны быть объявлены. Внутренние файлы не перечисляй; конфиг не описывай resolver,
   files, bindings или required — пути и выбор подключения определяет загрузчик.
   У процесса нет kind: source/transform/act принадлежит экшену. При переиспользовании
   не меняй класс и контракт экшена ради сценария; иной контракт согласуется через
   конструктор экшена. Действие подготовки черновика письма/контента без внешнего эффекта
   имеет kind=transform. Черновик определения с будущим внешним эффектом сохраняет act:
   степень готовности определения не разрешает переклассифицировать операцию.
6. Ресурсы конкретного сценария храни рядом с PROCESS.md в processes/<имя>/:
   queries/ — запросы и отбор, rules/ — предметные вычисления, templates/ — оформление,
   contracts/ — схемы результатов этих вычислений, fixture.json — вымышленные демоданные.
   Передавай точные пути экшенам явно. В actions/<имя>/ остаются только собственные
   универсальные правила и контракты экшена; не переноси туда ресурсы одного процесса.
   Объяви уровни контекста с учётом владельца; если экшену нужен styleFile, передай
   точную тему внутри объявленного уровня. Example не используется. Список тем
   возвращает загрузчик; контексты не объединяются по приоритету.
   Дополнительные требования сетевой выборки к настройкам опиши в configFields
   шапки её queries/<имя>.md. BaseUrl, adapter и mcpServer проверяются кодом.
   Не создавай общие папки tests/ или fixtures/ для рабочих данных.
   Адреса сервисов и секреты не помещай в процесс. Настройки подключений берутся по id
   taskStore/codeStore. Адрес страницы для read-page передаётся аргументом url запуска
   без секретов и не требует отдельного подключения. Критерии отбора — query/rules,
   форма результата — template, факты — context.
   Для структурированного отчёта с обязательными фактами создай внутри процесса
   rendererFile — локальный JS с render(data, params) и validate(text, data, params).
   Render обращается к точным путям JSON, validate отклоняет потерю/подмену фактов.
   Передай rendererFile в compose-report. Не переносись к схеме SDD в общем экшене.
   Для свободного текста без такого модуля исполнитель пишет текст по ACTION.md.
   Нужной системы нет: инструкция подключения существующего MCP либо заявка разработчику
   в отдельной папке outputs; не изобретай инструменты и не создавай подключение по догадке.
7. Проверь consumes/produces и доступность каждого входа на всех ведущих к шагу путях.
   Артефакт шага — псевдоним единственного выхода экшена; последующие ссылки используют
   этот псевдоним. Аргументы каждого вызова задавай явно через {params.имя} и {артефакт}.
   Исходный текст передаётся в start.inputText; журнал сохраняет копию и возвращает
   params.input, который передаётся в text экшена. Не создавай входной файл вручную
   и не выдумывай предыдущий артефакт. Прочие аргументы передаются в start.params;
   отсутствующие обязательные значения уточни, TODO из примера не оставляй.
   Задай entry, переходы, default каждой развилки и конечный результат каждого маршрута.
   Для вычислимых условий задай branchRule: rules/<имя>.js в шапке процесса. Модуль
   экспортирует чистую choose({step, params, artifacts}) → {target, reason}, без сети
   и записи файлов. Target должен быть объявленной целью. Семантическую развилку
   оставь decision: model; для решения после просмотра человеком результата —
   decision: user. Вычислимый узел пометь decision: code. Свободный текст условия
   не исполняется как код; в code-модуле можно экспортировать validateInput(params)
   для обязательных ответов, которые должны быть известны до start.
   Сохранение результата: save фиксирует выход шага, finish после конца маршрута
   копирует последний артефакт в файл для человека; экшен не пишет этот файл отдельно.
