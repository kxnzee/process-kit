name: pp-ai-run-process
description: >
  Исполнитель процессов Process Kit: служебный скилл, вызывается помощником (pp-ai-mentor)
  и никогда не предлагается человеку напрямую. Читает процесс из папки открытого проекта
  (processes/<имя>.md), собирает пакет входа каждого шага — действие из
  actions/<имя>/ACTION.md с его данными, адаптер из adapters/, адреса систем из
  config/sources.json, все файлы context/*.md — ведёт шаги по маршруту
  (entry / следующий / branch / подпроцессы), исполняет каждый шаг в изолированном
  контексте и отчитывается, какие файлы реально использованы. Применяй, когда помощник
  передал задачу человека на исполнение: process=<имя>, window=7d, dataFile=<путь>.

# Запуск процесса

Вызов: `/pp-ai-run-process [process=<имя>] [param=<значение> …]`. Без `process=` берётся
`defaults.process` из `config/sources.json`. Правила модели — в `GIGACODE.md` проекта;
агент читает их каждый раз, а не держит в памяти прошлых прогонов.

## Шаг 0. Корень проекта, уровень и каталог прогона

0. Корень проекта — текущая открытая папка (там же `GIGACODE.md` и каталог `processes/`).
   Ничего искать по соседним каталогам и другим ветвям не нужно: Process Kit — это папка,
   которую открыл человек, а уровни уже сведены в ней текущей веткой.
0a. Уровень ветки: `git branch --show-current`. `master` — общие файлы; `team-<команда>` —
   плюс файлы с префиксом `team-<команда>-` (имя ветки целиком: в ветке `team-sws` это
   `team-sws-`); `my` — плюс файлы с префиксом `my-`; `master-<имя>` — общий, ветка
   команды — командный. Другое имя — спросить, какого она уровня, а не угадывать.
0b. Прочитать **все** файлы `context/*.md` и держать их как общий контекст прогона. При
   противоречии ближний уровень важнее: `my-*` → `team-<команда>-*` → общий файл.
0c. Папка запуска — одна на прогон. Имя: `<ГГГГ-ММ-ДД>_<1–4 слова через дефис>`, без
   пробелов, до 40 символов после даты, по смыслу задачи (`сводка-просрочки`,
   `отчёт-sdd`). Для прогона с `dataFile=` имя начинается с `проба-`
   (`<дата>_проба-<задача>`). Если такая папка уже есть — добавить `-2`, `-3`;
   существующую папку не перезаписывать. Создать папку запуска и её `.run/`:
   ```
   mkdir -p "$ROOT/outputs/<имя>/.run"
   ```
   Запомнить `$ROOT/outputs/<имя>` как `<outDir>`, а `<outDir>/.run` как `<runDir>`.
   Пути — по разделу «Где лежат результаты» в `GIGACODE.md`. В корне папки и прямо
   в `outputs/` ничего не создавать.

## Шаг 1. Прочитать маршрут процесса

1. Процесс: `processes/<имя>.md`. Нет файла → остановиться и назвать имя, которого нет
   в ветке; другой процесс самовольно не подставлять.
2. Файл процесса — Markdown: шапка `name`, `title`, `entry`, `params` и раздел «Шаги», где
   на каждый шаг есть `действие:` / `процесс:` / `branch:`, `параметры:`, `артефакт:`,
   `следующий:`. Маршрут задаётся полями маршрута, а не порядком подразделов.
3. Для каждого шага с `действие:` разрешить файл действия: `actions/<имя>/ACTION.md`.
   Данные действия лежат в его папке и указываются в `параметры` шага:
   `actions/<действие>/queries/<имя>.md`, `.../templates/<имя>.md`, `.../rules/<имя>.md`.
   Нет файла действия или данных → остановиться и назвать имя.

Текст действия в диалог не копируется.

## Шаг 2. Собрать значения

1. Прочитать `config/sources.json`. Файла нет → остановиться и сказать, что нужна настройка
   (`/pp-ai-init` создаёт его из `config/sources.template.json` в командной ветке); не
   подставлять адреса систем из шаблона, примеров или другой ветки.
2. **Предпусковая проверка значений.** До первого шага и до создания папки запуска
   выполнить `node tools/validate.js --process <имя>` (`--json` — если нужен разбор
   полей). Скрипт проверяет только значения конфига, на которые ссылаются шаги этого
   процесса, их действия и данные действий; поля, к которым процесс не обращается, он
   не проверяет — незаполненное чужое подключение прогон не блокирует. Как ответить
   на находку, зависит от самого значения, по возрастанию тяжести:
   - **можно назвать в разговоре** (проект, доска, ветка приёмки, имя типа задачи или
     статуса) — спросить одной фразой и применить названное как аргумент **этого**
     прогона; приоритет «аргументы → конфиг» это уже разрешает. Сказать, что значение
     задано только для этого прогона;
   - **назвать нельзя** (сервер подключения, адрес системы, путь в чужом репозитории) —
     остановиться и сказать словами задачи, чего не хватает: «для отчёта SDD нужен
     адрес проекта», а не путь поля в файле;
   - **человек хочет заполнить насовсем** — передать в настройку (`pp-ai-init`) и после
     неё вернуться к его задаче; настройка сама перепроверит раскладку.
   Конфиг исполнитель не правит: заполнять его насовсем может только настройка. Скрипт
   только находит (код 1 — есть находки, код 2 — ошибка вызова: имени процесса нет
   или режим передан не с тем аргументом); как реагировать — решает исполнитель, а
   способ действия выбирает человек.
3. Приоритет значений: аргументы вызова → `параметры` шага → `params` процесса →
   `defaults` конфига → значения по умолчанию из файла действия. Все перекрытия
   перечислить в выводе одной строкой на параметр.

## Шаг 3. Исполнить шаг в изолированном контексте

Цель — чтобы в контексте прогона шли только **артефакты**, а не то, из чего они сделаны.
Для каждого шага:

1. **Собрать пакет входа** для этого шага, и только для него:
   - текст `actions/<имя>/ACTION.md` и его `consumes`;
   - файл-адаптер `adapters/<система>.md`, где система — из записи конфига (`adapter`
     или `kind`), если действие вида `source`/`act`;
   - данные действия (`queries/<имя>.md`, `templates/<имя>.md`, `rules/<имя>.md`) — по
     ссылкам в `параметры`;
   - артефакты предыдущих шагов, перечисленные в `consumes` (файлами из `<runDir>`,
     не пересказом из диалога);
   - все файлы `context/*.md`;
   - собранные значения параметров (шаг 2).
2. **Работать внутри шага**: читать системы, диффы, страницы пагинации, файлы шаблона —
   всё это остаётся в контексте шага. Сырые ответы MCP, полные диффы, содержимое
   запроса/шаблона в итоговый ответ шага не переносить; ссылаться на них («PR-335, дифф
   прочитан целиком») разрешено, цитировать — нет.
3. **Вернуть наружу только артефакт** `produces`: записать его в
   `<runDir>/<артефакт>.json` (данные) или `<runDir>/<артефакт>.md` (текст) и передать
   дальше **файл**, а не текст. Форму артефакта задаёт `produces` действия и словарь
   переменных шаблона следующего шага.
4. **Сводка шага в диалоге** — не больше пяти строк: узел → действие → артефакт и путь к
   нему → следующий узел. Отклонения от рецепта — строкой здесь же.

Если шаг не удалось завершить (MCP-сервер недоступен, файл не найден) — остановиться на
этом шаге, записать в `<runDir>/run.md` причину и не запускать следующие. `итог.md` в
`<outDir>/` пишется и в этом случае: «Чем закончилось» — причина простыми словами,
файлы, которые успели появиться, — в строке «Файлы в этой папке».

## Шаг 4. Вести маршрут

- Старт — `entry`; далее идти по `следующий:` / `goto`, а не по порядку подразделов.
- `{имя}` в параметрах заменяется **путём к файлу** артефакта шага с этим `артефакт:`;
  содержимое артефакта шаг читает сам из пакета входа. Значение параметра подставляется
  как `{params.<имя>}` (например `{params.window}`), а не просто `{имя}`: имя без
  `params.` — всегда артефакт.
- Шаг `branch`: правила `когда:` проверять по порядку строго по артефактам выполненных
  шагов; первое истинное — его `goto`. Ни одно не истинно и `default` нет — ошибка
  маршрута: остановиться и показать правило, которое не сработало.
- Ключ `процесс:` — подпроцесс: рекурсивно по этому же алгоритму в том же `<runDir>`,
  глубина ≤ 5. Повтор пары «процесс, шаг» — цикл: остановиться и показать замкнувшийся
  маршрут.
- Действие класса `act` показывает черновик эффекта и ждёт явного «да»; без него шаг не
  завершается отправкой, только статусом «черновик показан».

## Шаг 5. Направление ссылок и правка файлов

- Личная ветка может ссылаться на командные и общие файлы, командная — на общие. Общий
  или командный файл, ссылающийся на имя, которого нет в его собственной ветке, — **ошибка
  раскладки**: остановиться, назвать файл и ссылку, не «чинить» подстановкой и не искать
  файл в другой ветке.
- Чужие файлы (общие и командные, если работа идёт в личной ветке) во время прогона не
  правятся. Неожиданные значения, замеченные в системах, докладываются человеку с
  указанием, в какой файл и какого уровня их стоит внести.
- Своё человек добавляет своим файлом с префиксом уровня; имя файла — часть контракта,
  поэтому переименование чужого файла равносильно его правке.

## Шаг 6. Честность результата

- Каждое условие отбора подтверждать полем ответа системы; не подтверждено — раздел
  «Проверить не удалось», а не «не найдено».
- Система — поле `mcpServer` в `config/sources.json`. Сервер или инструмент недоступен
  в сессии → остановиться и сообщить какой; не подменять другим сервером и не добывать
  данные обходными путями.
- Доступы (токены) в проекте не читаются, не печатаются и не сравниваются: нужен лишь
  факт, что сервер подключения объявлен в сессии и ответил на проверочное чтение.
- Прогон с `dataFile=` — демо: такие данные ничего о реальных задачах не говорят.
  Пометку «ДАННЫЕ ДЕМО» ставит тот шаг, у которого в рецепте действия она есть (у
  `compose-report` — в шапке отчёта); форма артефакта задаётся действием, поэтому в
  чужие артефакты пометку не добавлять. В итоговой сводке и в `итог.md` режим «демо»
  называть всегда: он есть в шапке вывода и в строке «Откуда данные».

## Шаг 7. Вывод

1. Заголовок: имя процесса, уровень ветки, режим (живой/демо), каталог прогона,
   фактически использованные файлы (`processFile`, `actionFiles`, `adapterFiles`,
   `contextFiles`).
2. Маршрут: цепочка узлов с артефактами и путями к файлам; для развилок — какое правило
   `когда:` сработало.
3. Артефакты пользовательского формата (`report-text`, `mail-draft`) показать целиком —
   это и есть результат прогона; для этого их читают из `<runDir>`, а не восстанавливают
   из памяти хода.
4. Отклонения от текстов действий/процессов — отдельным разделом с причиной; молча
   «улучшать» рецепты запрещено.
5. Дописать `<runDir>/run.md`: процесс, уровень, режим, значения параметров, маршрут,
   артефакты, остановки и их причины.
6. После каждого завершённого шага — запись в `<runDir>/state.json`: номер и имя
   последнего завершённого шага и параметры прогона. **Все** артефакты шагов — в
   `<runDir>/` файлами `<NN>-<имя шага>.<расширение>`, где NN — номер шага
   (`01-jira-search.json`, `02-compose-report.md`). Даже артефакт последнего шага сначала
   пишется сюда: в `<runDir>` лежит полный след прогона, по нему видно каждый шаг.
7. Результат **последнего** шага процесса (отчёт, письмо, таблица) — файл для человека
   в `<outDir>/`: тот же шаг пишет его **вторым файлом** сразу в `<outDir>/`, под именем
   по смыслу результата (`отчёт.md`, `письмо.md`, `таблица.md`). Копировать,
   переименовывать и переносить файл из `.run/` нельзя: `<outDir>` получает свою запись
   от самого шага. Итог:

   ```
   <outDir>/письмо.md          ← результат последнего шага, файл для человека
   <outDir>/.run/03-send-mail.md  ← тот же артефакт, служебный след шага
   <outDir>/.run/02-compose-report.md  ← артефакт предыдущего шага, в корне его нет
   <outDir>/итог.md
   ```

   Артефакты промежуточных шагов в `<outDir>/` не попадают никогда — только в `.run/`.
8. История прогонов — одна строка на прогон в `$ROOT/.history/runs.jsonl`: время, процесс,
   уровень, режим, `output` (имя папки запуска), `итог` (дословно строка «Чем закончилось»
   из `итог.md`). Файл только дописывается.
9. `итог.md` в `<outDir>/` — писать **всегда**, в том числе если прогон не дошёл до
   конца. Шаблон (строки без данных не писать):

   ```
   # <задача словами человека>
   Дата: <ГГГГ-ММ-ДД ЧЧ:ММ>
   Чем закончилось: готово | не получилось: <причина простыми словами>
   Что сделано: <1–3 предложения>
   Период: <если был>
   Откуда данные: <система и проект, например «Jira, проект SWS»; для демо — «тестовые данные»>
   Сколько записей: <число>
   Что отправлено и кому: <или «ничего не отправлено»>
   Файлы в этой папке: <список с одной фразой о каждом, без .run/>
   ```

   В `итог.md` не бывает токенов, адресов серверов и текста системных ошибок. Для
   пробного прогона строка «Чем закончилось» начинается со слов «Пробный прогон, ничего
   не отправлено».

   Строка «Файлы в этой папке» — **только имена файлов, которые лежат в `<outDir>/`
   рядом с `итог.md`**: перечисли их (`ls`/`readdir` папки запуска), для каждого одна
   фраза. Служебную подпапку прогона в этой строке не упоминать — ни именем, ни словом
   «служебные», ни в скобках. Человек видит только свои файлы.
10. В чате — полный путь к главному файлу: «Результат: $ROOT/outputs/<имя>/итог.md».
    Путь относительный не писать.
11. Самопроверка перед ответом человеку: в `<outDir>/` нет файлов из `.run/`
   (`02-*`, `03-*` и подобных), результат последнего шага лежит в `<outDir>/`, `итог.md`
   перечисляет ровно эти файлы. Затем — `node tools/validate.js`: проверки группы
   `outputs` смотрят раскладку папки запуска, а не только файлы подхода.

## Шаг 8. Где лежат результаты

Пути задаются разделом «Где лежат результаты» в `GIGACODE.md`; здесь — только
напоминание, где что лежит в запуске:

- файлы для человека: `<outDir>` = `$ROOT/outputs/<имя>/`;
- служебные файлы прогона: `<runDir>` = `<outDir>/.run/` (`run.md`, `trace.jsonl`,
  `<NN>-<шаг>.*`, `state.json`);
- история: `$ROOT/.history/runs.jsonl`;
- прямо в `outputs/` файлов нет — только папки запусков; в корне папки ничего не
  создаётся. Путь вне `outputs/` в прогоне — ошибка.
