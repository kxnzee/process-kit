# Архитектура Process Kit

## Назначение и границы

Process Kit — библиотека повторяемых рабочих процессов для агента GigaCode.
Это проектная папка, не расширение и не отдельный автономный движок. Модель читает
Markdown-рецепты; Node.js-инструменты проверяют формальные контракты. Поэтому зелёные
тесты не доказывают корректность живого ответа агента и не заменяют приёмку клиента.
Исторические результаты внедрения не считаются проверкой текущей восстановленной копии.

## Источники истины

| Документ | Ответственность |
|---|---|
| CONTEXT.md | значения доменных терминов |
| GIGACODE.md | обязательные правила и маршрутизация агента |
| docs/reference/structure.md | формат, владение и подключения |
| docs/reference/outputs.md | файлы запуска, состояние и история |
| docs/reference/artifacts.md | данные SDD между источником и отчётом |
| docs/reference/dialogs.md | последовательность разговора и закреплённые реплики |
| docs/reference/promotion.md | перенос подготовленных изменений |
| docs/templates/ | заготовки тех же контрактов |
| tools/ | исполняемые проверки контрактов |

Архитектура объясняет связи, не дублирует все детали контрактов. Изменение правила
производится в ответственном документе, затем в коде, примерах и тестах. Старый отчёт
проверки — историческое свидетельство, не источник новых правил.

## Компоненты и ход работы

```
задача → mentor → [init при необходимости] → run-process → ACTION.md
                   ↘ create-process               ↘ выбранные данные и адаптер
файлы своего уровня → promote-changes-* → отдельный worktree → проверки → PR
```

Шесть служебных скиллов лежат плоско в .gigacode/skills/. Пользовательский вход один.
Действие не скилл GigaCode: оно выбирается шагом процесса. Источник данных не знает
шаблон следующего шага: источник и трансформация зависят от общего контракта артефакта.

| Компонент | Делает | Не делает |
|---|---|---|
| mentor | подбор, вопросы, маршрутизация | выполнение шагов и угадывание параметров по истории |
| init | личная копия, настройки, доступ, локальный hook | рабочая задача и глобальные настройки |
| create-process | композиция/создание материалов своего уровня | автоматическая отправка и изменение чужого |
| run-process | маршрут, пакеты шагов, артефакты, итог | ремонт платформы по ходу задачи |
| promote-changes-* | перенос согласованного снимка в целевой уровень | скрытая адаптация личного и автослияние |
| validate.js | структура, ссылки, маршрут, выбранные поля конфига | истина текстовых условий и доступ MCP |
| check-report.js | сверка фактов с ожидаемыми артефактами | выполнение процесса и обучение на эталоне |
| prepush.js | проверка реального изменения Git-ссылок | защита сервера и всех копий личных данных |

## Владение

Один репозиторий; master → team-<код> → my. Уровень распространяется на процессы,
действия, данные, контекст и тесты. Имена различны; автоматической подмены общего
файла личным нет. Ссылки явные, только к своему и более общему уровню своей команды.
Это осознанное уточнение старой модели system/team/user с резолюцией «первый найденный».
Близость уровня влияет на выбор подходящего процесса и приоритет фактов контекста,
не на замену имени действия. Настройки целиком принадлежат текущей ветке, overlay нет.

Общие материалы правятся через PR, командные — через ревью владельцев команды.
Личные my-* не отправляются в общий адрес. Публикация личного процесса требует отдельно
согласованной командной/общей копии с адаптацией имён, ссылок и личных сведений;
перенос изменений лишь доставляет подготовленное. Сохраняются исходные файлы человека.

## Данные и выполнение

Процесс задаёт маршрут и зависимости. Действие задаёт consumes/produces и рецепт.
Подключение внутри разделено на адаптер (механика системы) и sources.json (конкретные
адреса/идентификаторы). Человек видит одно подключение. Параметры не дублируют адреса.
Контекст — отдельные факты; ядро common.md и выбранные requires.context вместо
обязательного чтения всей растущей библиотеки. Каталог и автоматический сборщик процессов
пока не реализованы; при росте библиотеки они добавляются отдельной задачей.

Перед запуском проверяется структура и только зависимости выбранного процесса.
Transform и демо работают без источников; live проверяет выбранные id и поля из
requires.taskFields/codeFields. TODO посторонней системы не блокирует этот процесс.
Вложенный TODO нужного репозитория блокирует. Нет точного файла — отказ без подмены.
Параметры приоритезируются единообразно; today фиксируется один раз на местный день.

Шаг читает ограниченный пакет и пишет один служебный артефакт. Техническая изоляция
зависит от клиента: отдельного контекста нельзя обещать по одному Markdown-правилу.
state.json хранит отображение логических имён на реальные NN-файлы. Нумерация единая
для подпроцессов. Сначала запись артефакта, затем атомарное обновление состояния.
Последний результат также записывается файлом для человека, без повторного внешнего вызова.

Ошибки останавливают маршрут; итог создаётся даже при сбое начатого прогона.
Повтор внешнего эффекта не делается по одному last_step: нужен ответ/id предыдущего
вызова и известный исход. Без достаточного состояния продолжение вручную или новый прогон.
История — локальный индекс, не второй журнал событий шага и не источник бизнес-фактов.

## SDD и письма

SDD-процесс сохраняет исходный критерий: начало работы в окне, текущий статус от
тестирования и далее, нужная КЭ; метка SDD или принятый PR с изменениями спецификаций.
Точная логика в query, поля — artifacts.md. Окно старта не является окном слияния PR.
Неполная проверка отрицательного признака не становится «без SDD».
Фикстура и ожидаемый результат независимы: подставлять expected в результат запрещено.

Почтового адаптера нет. prepare-mail-draft — transform, формирует только черновик. Отправка
должна появиться отдельным act с подключением и явным согласием. Это устраняет ложное
обещание текущего имени. Класс действия заполняет конструктор, не пользователь.

## Защита и перенос

Секреты в клиенте, в проекте только ссылки. Отсутствие секрета, 401/403 и сбой сети
различаются. Персональные и служебные данные не входят в git и PR.
Git hook ставится идемпотентно и цепляет прежний. Проверяются реальные non-fast-forward,
удаления, my под разными именами и notes. --force не передаётся Git-хуку;
истинная защита master/team-* — сервер Bitbucket. Хук имеет документированные пределы.

Перенос — свежая цель, отдельный worktree, точный снимок (включая удаления), замкнутые
зависимости и дифф до согласия на отправку. Не branch -f, не переключение рабочей папки,
не автоматическое удаление ветки незавершённого PR. Нет инструмента создания PR —
ссылка для человека, а не вымышленный факт публикации.

## Проверка и развитие

node tools/check-all.js проверяет структуру, регрессии маршрута/зависимостей,
отчётные эталоны и настоящие push в локальные одноразовые репозитории. Сеть не нужна.
Корпоративная приёмка отдельно: С1–С7 из docs/acceptance.md, все клиенты и Windows,
права/секреты и живые ответы систем. Исходные теги/история из Repomix не восстанавливаются.

Догадки по истории, супервизор, расписания, сборка расширений, автоматическая адаптация
личных процессов, полная безопасная миграция старых результатов и гарантированный
автоповтор внешних эффектов не считаются готовыми. Не маскировать их инструкциями в чате.
