# Запрос: стори — доля выполненных по SDD

Данные действия `run-query` (шаг `fetch` процесса `sdd-stories-report`). Здесь критерии отбора,
окно, метка и папка артефактов; механика систем — в адаптере `adapters/jira.md` и
`adapters/bitbucket.md`, адреса подключений — в `config/sources.json` (на них только
ссылки: `defaults.taskStore`, `defaults.codeStore`, `repositories[]`, `projects[]`,
`modules[]` — список КЭ отбора).

Выход — артефакт `report-data` с группами `sddStories[]` (выполнены по SDD) и
`plainStories[]` (выполнены без SDD), списком `unverified[]` и счётчиками, включая
процент. Словарь полей задан шаблоном `actions/compose-report/templates/report.md`;
поля, которых нет в словаре, не выдумываются.

## Параметры

Приоритет: аргументы вызова → `параметры` шага → `params` процесса → координаты подключений.

| Параметр | Значение | Что означает |
|---|---|---|
| `startDate` | `01.01.2026` | начало окна по дате перехода в работу, включительно |
| `endDate` | текущая дата прогона | конец окна, включительно |
| `label` | `SDD` | метка, наличие которой засчитывается как «по SDD» |
| `watchPath` | `openspec/changes` | папка артефактов; PR, в котором есть изменения этой папки, = признак SDD |
| `issueType` | `Story` | тип задачи «стори» этой инстансы системы задач |
| `project` | из координат подключений: `taskStores[].projects` | проект системы задач |
| `keField` | `customfield_18300` | поле «КЭ» задачи: массив ссылок на критичные элементы |
| `inWorkFrom` | `To Do`, `Backlog`, `New` | статусы до работы; стори, которые в них сейчас, выпадают из проверки |
| `statusesWork` | `In Progress` | имя статуса «взято в работу», по которому ищется дата в истории |
| `statusesAccepted` | `IFT`, `Ready for UAT`, `Done`, `Resolved` | «тестирование и далее» |
| `keyPattern` | `[A-Z][A-Z0-9]+-[0-9]+` | шаблон ключа задачи в сообщении коммита и полях PR |
| `keyFields` | сообщение коммита, заголовок PR, описание PR | откуда берётся ключ задачи |
| `branchesToScan` | `master`, `branch/*` | базовые ветки, по которым ищутся коммиты с артефактами |

Адреса серверов, имена подключений, хранилища кода и базовые ветки из
`repositories[].defaultBranch` здесь не повторяются — они уже есть в `config/sources.json`,
и запрос берёт их оттуда.

## Правила отбора

Стори попадает в набор, только если подтверждены **все** пункты 1–4:

1. **КЭ в поле задачи.** Список КЭ отбора берётся из координат подключения к системе задач:
   `taskStores[].modules`, каждая запись — объект `{ name, code }`. `name` — название
   для человека: в запрос оно не уходит, в отчёт и в чат не выводится, потому что может
   содержать имя системы или команды. Из `code` вида `CI03296913` для поиска берётся
   **только цифровая часть без префикса `CI` и без ведущих нулей**: `CI03296913` → `3296913`.
   В поле `keField` задачи должна быть хотя бы одна из полученных цифр (`"КЭ" in (...)`).
   Проверять именно полем задачи, а не упоминанием кода в тексте: сравнение по значению
   работает только на числовой id, код `CI…` полем не находится. Стори без подходящей КЭ в
   набор не попадает и в отчёт не выводится. Запись без `name` или без `code`, либо `code`
   не вида `CI0…` — остановка: список поправляет владелец координат, а не прогон.
2. **Старт работы в окне.** В истории задачи (`get_issue` с `changelog=true`) найти событие
   `field = status`, где `to_string` равно `statusesWork`, и взять его `created`. Условие
   выполнено, если `startDate ≤ created ≤ endDate`. Стори без такого перехода в истории — в
   `unverified[]` (причина «нет перехода в работу в истории»).
3. **Сейчас задача уже в работе.** Текущий `status` не входит в `inWorkFrom`. Стори,
   вернувшаяся в `To Do` после работы, остаётся в проверке: пункт 2 подтверждён историей.
4. **Статус «тестирование и далее».** Текущий `status` ∈ `statusesAccepted`.

## Деление на группы

По каждой стори из набора проверяются два признака. Стори выполнена **по SDD**, если
выполнен **признак 1 ИЛИ признак 2**:

- **признак 1 — метка**: `labels` содержит `label` без учёта регистра;
- **признак 2 — PR с артефактами**: стори упомянута в смерженном PR, в который включён
  коммит, меняющий файлы под `watchPath`.

Стори выполнена **без SDD**, только если **не выполнены оба признака**. Достаточно любого
одного, чтобы стори попала в группу «по SDD»; проверять второй признак при выполненном
первом нужно лишь для колонки «Засчитано по» («метка», «PR с артефактами»,
«метка и PR»).

## Как ищется «PR с артефактами»

Главное правило: **важно не то, к какому объекту привязан коммит, а то, что он включён в PR,
в который включена стори.** Ключ в сообщении коммита, имя ветки и название PR значения не
имеют — решает факт входа коммита в PR и упоминание стори в этом PR. Эвристик нет.

1. **Смерженные PR за окно.** `bitbucket_list_pull_requests` с `state = MERGED`, `order = NEWEST`,
   `at` по каждой ветке из `branchesToScan`, пагинация до выхода за `startDate`. Из заголовка и
   описания PR берутся ключи по `keyPattern` (`keyFields`). PR без ключей стори дальше не
   рассматриваются.
2. **Есть ли в PR артефакты.** Для каждого PR-кандидата — список файлов PR
   (`bitbucket_get_pull_request_diff` с `path = watchPath`). Изменения под `watchPath` есть →
   PR содержит коммиты с артефактами. Пустой ответ «No differences found» → артефактов нет.
   Дифф целиком не грузить: он усекается, фильтр по пути — нет.
3. **Сверка с историей коммитов.** Дополнительно (для колонки «коммит» и для контроля):
   `bitbucket_list_commits` с `path = watchPath` по базовым веткам и `bitbucket_get_commit_changes`
   по подозрительным коммитам. Результат — вспомогательное свидетельство, а не критерий:
   коммит, который не попал ни в один PR со стори, стори не засчитывает.
4. **Один PR на много ключей.** Все ключи, перечисленные в одном PR с артефактами, получают
   признак SDD — в релизных PR перечислен раздел stories.
5. **Связи `PartOf`, имя ветки, префикс названия PR** не используются.

## Как считается результат

- `sddStories[]` — выполнены по SDD: `key`, `summary`, `url`, `status`, `inProgressAt`,
  `via` («метка», «PR с артефактами», «метка и PR»), `commit` (короткий id коммита с
  артефактом и путь, если нашёлся, иначе «—»), `assignee`.
- `plainStories[]` — выполнены без SDD: `key`, `summary`, `url`, `status`, `inProgressAt`,
  `assignee`.
- `unverified[]` — что проверить не удалось, с причиной: сервер недоступен, история статусов
  не прочиталась, список файлов коммита не получен, поле `keField` не читается, запись
  `modules` без кода или названия, координата подключения `TODO`.
- Счётчики: `storyCount` (всего в наборе = `sddCount` + `plainCount`), `sddCount`,
  `plainCount`, `labelCount` (из них с меткой), `commitCount` (из них с коммитом артефакта),
  `sddShare` — процент SDD от `storyCount` с одним знаком после запятой;
  `0`, если `storyCount = 0`. `unverifiedCount` — отдельно, в знаменатель не входит.

## Чего в запросе не бывает

- правок конфига по ходу прогона: подтверждённые имена статусов и типов агент докладывает
  человеку, а вносит их владелец уровня;
- подсчёта доли по релизным PR: артефакт привязан к задаче разработки, а не к релизу;
- подстановки другого хранилища, если сервер нужного недоступен: шаг останавливается;
- вычитывания `.md` по именам каталогов вместо самого PR: признак SDD — правка файлов под
  `watchPath` в смерженном PR.
